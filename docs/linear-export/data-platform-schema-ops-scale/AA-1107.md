## Problem

The C4.3 W47 review (S282) found that the slowest machine-facing read is the CIS catalog HTTP `places` read (`services/catalog_http/reader.py`, `catalog.v_tour_place` filtered by `tour_id = ANY($1)`, role `aa_app_user`).

* About 525 rows per call.
* New calls since W46 average about **536 ms**. W45 was about 82 ms.
* `geo.tour_place` shows about one sequential scan per call.

An EXPLAIN (ANALYZE, BUFFERS) on Dev for 50 listed tours took **606 ms** for 1,321 rows, all cache hits:

* **\~310 ms:** one `geo.tour_place` lookup per output row. The index scan on `tour_place_source_idx` (source_id, day_index) runs, then the filter `geo.name_norm(name) = geo.name_norm(place_name)` evaluates per row: 0.23 ms × 1,321 loops.
* **\~77 ms:** a parallel sequential scan and sort of all `acp_contract.tour_atoms` (\~25,900 rows). The tour filter is not pushed below the merge join with `raw_tours`.
* **\~150 ms:** the per-tour spelling window.

No C1.2 target is missed (the `catalog_views` worst p95 is \~750 ms, under 1 s), but the read grows with the catalogue.

## Scope

1. CIS migration (next free number): an index that serves the place lookup without evaluating `geo.name_norm` per row. For example, an expression index on `geo.tour_place (source_id, day_index, geo.name_norm(name))` if `name_norm` is IMMUTABLE, otherwise a stored normalised column. Classify it expand vs contract per ADR 0017.
2. If the view text can push `tour_id` into the `tour_atoms` scan without changing results, change the view (`CREATE OR REPLACE VIEW`, same columns). The security_barrier semantics stay.
3. A test proving the view output is unchanged (same rows for a fixture).

## Done when

* Merged + CI green + migration applied + deploy COMPLETED.
* On Dev, the same EXPLAIN for 50 listed tours is **≤ 200 ms** with the new plan visible: no per-row `name_norm` filter on `tour_place`, and no full scan of `tour_atoms`.
* The next C4.3 review shows the new-call mean of this statement under 200 ms.
