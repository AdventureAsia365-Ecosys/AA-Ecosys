## Problem

The tech lead asked (S279, 14/11/2026) for one place that shows what each app can do and how the apps link, including the conditions a link needs. Today the facts are spread over 30 contract files (`docs/contracts/`, registry table in its README), 97 UAT scenarios (`tools/uat/catalogue.json`), `docs/ecosystem-architecture.md`, each repo's `CONTEXT.md`, the settings registry and research pages. Nothing ties them together, and a hand-made table would drift from the code within weeks.

## Scope

1. **Two machine-readable catalogues in the root repo, the single source:**
   * `features.yaml`: stable id (e.g. `CRM-F031`), app, module, plain name, roles, status (live / beta / planned / retired), enabling conditions (plan or add-on, setting keys, tenant kind demo / pilot / agency), evidence (UAT scenario ids, tests), owner, guide page.
   * `integrations.yaml`: producer → consumer, kind (DB view, HTTP API, event / outbox, M2M), contract file and version, auth (M2M scope, RLS, role), **conditions for the link to work** (e.g. CRM add-on, agency in service, tour sellable, Book now on, synthetic only), cadence, failure behaviour and kill switch, personal data yes / no, owner.
     Modelled on the Backstage catalog format (Component / API / System, providesApis / consumesApis), C4 context and container levels and a DDD context map; no Backstage server.
2. **Traceability:** business journey → features → integrations → contracts → tests / UAT videos (start with the S279 pilot rehearsal journey).
3. **CI guards** so it cannot rot: every contract file has an integration row; every UAT scenario points to a real feature id; every setting named in a condition exists in a registry; new route groups / pages map to a feature.
4. **UI: CIS admin, Platform › Product map** (`/admin/platform/catalogue`, staff tier, UI kit), tabs Apps / Features / Links / Journeys / Graph, filters by app, role, status and condition, deep links to `/admin/docs` pages and Platform › Settings rows. Data = a generated JSON bundle published by Docs sync like the docs reader (no new table, no new API write path). Business-owner view in plain words with a VI toggle (pages default to English).
5. Later, out of scope here: a tenant-facing "what your plan includes" subset in the CRM web settings.

## Done when

* Both YAML files cover every live app (CIS, Booking, TripPlanner, CRM, Infra edge) and every contract in `docs/contracts/`; reviewed by the tech lead.
* The CI guards run as required checks on the root repo and fail on a missing row (tested).
* `/admin/platform/catalogue` on Dev lists the features and links with conditions; screenshots desktop + mobile, light + dark.
* The UAT catalogue rows carry feature ids.
