## Problem

[AA-824](https://linear.app/aa-ecosys/issue/AA-824/dataops-rds-guardrails-connection-budget-storage-autoscaling-parameter) (N3) shipped the first alarms on `aa-cis-dev-db`:

* New alarms: CPUUtilization, FreeableMemory, CPUSurplusCreditsCharged.
* Updated alarms: FreeStorageSpace, DatabaseConnections.
* Per-role `CONNECTION LIMIT` (CIS migration 234): `tripplanner` 30, `booking` 15, `aa_app_user` 15.

Data standards C4.1 (`03-scaling.md`) still lists four rows as "To build (N3)", and no issue tracks them:

* `ReadLatency` / `WriteLatency`
* `DiskQueueDepth`
* `MaximumUsedTransactionIDs` (wraparound guard)
* per-role connections above 80% of `CONNECTION LIMIT`

Without that last alarm, nothing warns before an app role reaches its connection limit. The app then fails with `too many connections` and no early warning.

The `rds-connections-high` alarm is also out of date:

* Its threshold is an absolute `> 60`.
* Its code comment estimates max_connections at "190-200". The live value is **181** after the t4g.small resize.
* C4.1 / C4.1b want 60% of `max_connections`, updated in the same change as a resize.

## Scope

All alarms go in `infra/AA-CIS-Infra/accounts/aa365/observability_ecosys.tf`, send to `aws_sns_topic.alerts`, and use `treat_missing_data = notBreaching`.

**New RDS alarms**

* `ReadLatency` / `WriteLatency` > 20 ms for 15 min.
* `DiskQueueDepth` > 10 for 15 min.
* `MaximumUsedTransactionIDs` > 1,000,000,000.

**Connection alarm retune**

* Run `SHOW max_connections` live and record the value.
* Set `rds-connections-high` to 60% of that value for 5 min.
* Fix the code comment.
* Re-check the C2.2 connection budget table against 181.

**Per-role connection metric**

* A CIS job kind (`concurrency=1`, `background=True`) reads `pg_stat_activity` per `usename`, joined to `pg_roles.rolconnlimit`.
* It publishes custom metric `AA/RDS` (dimension `Role`) for every LOGIN role that has a limit.
* An EventBridge Scheduler rule only enqueues the job, every 5 min (pattern: `accounts/aa365/dfs_balance.tf`, ADR 0003 decision 5).
* The CIS worker task role gets `cloudwatch:PutMetricData`, scoped to the namespace.
* One alarm per role at > 80% of its limit.

**Docs**

* Update the `03-scaling.md` C4.1 status column.
* Update the README enforcement table "Alarm" row.

## Done when

* `describe-alarms` lists the 4 new RDS alarms, all on the `alerts` topic and in OK / INSUFFICIENT_DATA.
* The `rds-connections-high` threshold equals 60% of the live `max_connections`, and that value is recorded in the PR.
* `list-metrics --namespace AA/RDS` shows one series each for `tripplanner`, `booking` and `aa_app_user`.
  * Datapoints are less than 15 min old.
  * They match a manual `pg_stat_activity` count.

* The `03-scaling.md` C4.1 rows are marked built, with PR numbers.
