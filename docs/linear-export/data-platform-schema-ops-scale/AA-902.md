# AA-902 — [Security] Scrub AWS account IDs and ARNs from tracked files in the public repos

## Problem

The S243 security baseline (`docs/security/baseline.md`, control "public repos content", DM-6.10 / D-25) found AWS account IDs and ARNs in tracked files of the public repos on 19/10/2026: AA-CIS-App 76 files, AA-Booking 4, AA-TripPlanner-Web 6. Public repos must not carry account IDs, ARNs, SG/VPC IDs or inventory (root CLAUDE.md). This is the open gap behind [AA-895](https://linear.app/aa-ecosys/issue/AA-895/security-security-baseline-and-vulnerability-management-policy) and the [AA-889](https://linear.app/aa-ecosys/issue/AA-889/docs-remove-stale-docs-and-agent-instruction-drift-cis-runbook-v1-root) Done-when.

## Scope

1. Inventory with the docs-lint resource-ID regex (`tools/docs/check_docs_text.py`) per repo: file, line, kind (account ID, ARN, SG/VPC/subnet, API GW ID, pool ID).
2. Replace with names or placeholders (`<acc2>`, `arn:aws:…:<account>:…`), or move the file to the private root repo / Infra when it is an investigation or inventory.
3. Code paths that need a real ARN read it from env/Secrets Manager/Terraform output, never a literal (check tests + workflows too).
4. Turn the resource-ID check from warn-only to failing in the three app repos ([AA-888](https://linear.app/aa-ecosys/issue/AA-888/ci-docs-lint-and-adr-indexes-in-every-repo-front-matter-links-resource) follow-up) so it does not come back.
5. History: decide with Nghiệp whether any hit needs a history rewrite (account IDs alone are low-risk; anything secret-like = rotate instead).

## Done when

* The regex scan reports 0 hits on `main` of CIS, Booking and TripPlanner (output attached).
* The CI check fails a test PR that adds an account ID.
* Baseline page updated with the evidence.
