## Why

The platform is split across accounts for payer reasons, not by design:

* **acc2 005097885195 (payer TrueIDC):** all infrastructure (RDS, ECS, S3, Lambda, API GW, Redis, WAF…), but it cannot use Bedrock LLMs and has tiny Bedrock quotas.
* **acc3 786888028788 (payer eCloudvalley):** runs every LLM and embedding call as a satellite (AA-296, [AA-862](https://linear.app/aa-ecosys/issue/AA-862/llm-cohere-embed-v4-throughput-fall-back-to-the-acc3-and-acc1)).
* **acc1 867490540162:** Nghiệp's personal account.

Cross-account calls, two payers, two sets of IAM/quotas/alarms and split cost reporting make operations harder. The satellite pattern is a temporary workaround. Long-term goal (Nghiệp, S239): one account, managed centrally.

This issue is **research only**. Produce a migration scenario with complexity, cost and time, then decide. Nothing is migrated here.

## Questions to answer

1. **Target:** acc3, or a newly designated account? Payer terms, LLM access and quotas, credits/programs and billing ownership for each option.
2. **Inventory of everything on acc2 that must move or be recreated** (start from Terraform `accounts/aa365` plus a live resource scan):
   * **Compute:** ECS cluster (api, worker, aa-booking-dev-api), task definitions, ECR images, autoscaling.
   * **Data:**
     * RDS Postgres 15 (shared: CIS, TripPlanner, Booking schemas; pgvector; roles aa_cis_admin / aa_app_user / tripplanner / booking / catalog_owner; RLS);
     * ElastiCache Redis (feature flags);
     * S3 (bronze, archive, artifacts, restore snapshots, TF state bucket and DynamoDB lock).
   * **Serverless:** TripPlanner Lambdas (browse, assembly), ops-probe/DFS Lambda, sweeper/canary, EventBridge Scheduler groups.
   * **Network/edge:**
     * VPC, NAT instance;
     * ALB and WAF (aa-cis-dev-waf, log redaction);
     * API Gateway (CIS 4ylo382khg, TripPlanner, Booking REST);
     * custom domains and ACM, Route 53 zone `lumiguides.it.com`;
     * Vercel CNAMEs.
   * **Identity/secrets:**
     * Secrets Manager (RDS DSN, admin secret, tenant/e2e secrets, `acp/cms/*` per tenant, DataForSEO, Jev, OpenAI);
     * KMS keys;
     * IAM roles: GitHub OIDC CI roles per repo, task roles, satellite trust with ExternalIds.
   * **Messaging/ops:** SES (verified identities, configuration sets, production access), CloudWatch log groups/alarms, Budgets, Cost Explorer tags, CloudTrail, Service Quotas.
   * **External connections that hold acc2 ids or URLs:**
     * Vercel env (3 projects);
     * GitHub Actions secrets and OIDC role ARNs;
     * WordPress/Facebook tenant integrations;
     * DataForSEO, Jev and Mapbox;
     * TrueIDC billing.
3. **Data move options and downtime** for RDS:
   * snapshot share + KMS re-encrypt + restore;
   * DMS / logical replication for near-zero downtime;
   * pgvector and roles/grants survival.

   Also: S3 copy / batch replication, Redis rebuild (flags only), secrets re-creation.
4. **Cutover plan:** order of moves, DNS/API GW domain switch, rollback window, freezes (no `shared.job` waves), verification per app (CIS, TripPlanner, Booking).
5. **Terraform:** re-point roots (new backend/state bucket, `account_id`, provider), import vs recreate. Plus what changes for the satellite pattern: it becomes same-account and the cross-account roles retire.
6. **Cost and time estimate:**
   * one-off: engineering days, a double-running period, data transfer;
   * monthly: delta between the two payers and pricing/credits.

   Risk list and a recommended window.

## First notes (not researched yet)

* The biggest pieces are **RDS (shared by 3 apps) and DNS/edge**. The rest is mostly Terraform re-apply plus secret re-creation.
* **SES production access, Service Quotas and Bedrock model agreements (Marketplace) are per account.** Request or accept them in the target well before cutover (lesson from [AA-862](https://linear.app/aa-ecosys/issue/AA-862/llm-cohere-embed-v4-throughput-fall-back-to-the-acc3-and-acc1): the acc3 Cohere agreement had to be accepted first).
* **OIDC CI roles, ECR images and KMS-encrypted snapshots** do not move as-is. Plan to recreate the roles, re-push the images and re-encrypt the snapshots.
* **Dev only today, no real users**, so a short planned downtime is acceptable and much simpler than zero-downtime replication. This is the best time to move, before a prod exists.
* Natural sequencing with [AA-860](https://linear.app/aa-ecosys/issue/AA-860/security-x1-split-the-cis-runtime-role-cis-owner-owns-tables-cis-app) **(X1 role split)** and [AA-807](https://linear.app/aa-ecosys/issue/AA-807/data-phase-1-foundation-per-app-db-owner-roles-migration-ownership)/[AA-826](https://linear.app/aa-ecosys/issue/AA-826/dataadr-new-app-integration-playbook-adr-0008-ownersyaml-registry-role) (owners): doing the role split on the target account avoids doing it twice.
* Rough guess to validate: about 1–2 weeks of focused work for Dev; the cutover itself is one planned window of a few hours.
