## Problem

The S279 thresholds audit (`docs/audits/2026-11-13-S279-session/thresholds-audit/`) found 780 thresholds, limits, caps and policy values across CIS, Booking, CRM, TripPlanner and Infra. Only 83 (11%) can be changed on an admin page:

| Where the value lives | Count |
| -- | -- |
| Hard-coded | 489 |
| Env var | 89 |
| Registry YAML | 29 |
| Database, no page | 33 |
| Terraform | 57 |

Changing any of these needs a pull request and a deploy.

**Tech lead rule (S279, 13/11/2026):** every threshold can be adjusted on an admin page, by the administrator role. All 11 proposed defaults are approved. Quality thresholds are admin-editable with a required evidence link.

## Scope

**Design: one settings pattern, stored by each owner (audit section 5).**

* `setting_definition` / `setting_value`, versioned, with bounds, approval and audit.
* One reader library with a cache and a safe fallback.
* A CIS admin page, Platform › Settings: tabs per app, write access for admin only.
* A `settings-lint` CI guard against new hard-coded or env-only thresholds.

**Lanes (audit section 6):**

| Lane | Repo | Content |
| -- | -- | -- |
| L1 | CIS | The mechanism, the page, the high-impact CIS items, the defect fixes |
| L2 | CIS | Move the quality registry (`thresholds.yaml`, `writing_policy` numbers, detector modes), with evidence required |
| L3 | Booking | `pricing_policy` groups: holds, SLA, ages, ops days, reminders, rounding; the cancellation tab; the stored-only parameters |
| L4 | CRM | AA platform limits and the platform ranges for agency settings, with a CIS tab |
| L5 | CIS + TripPlanner | The TripPlanner caps and rate limits as CIS rows behind a `catalog` view |
| L6 | Infra | Remove the env vars once read from the DB; turn literals into variables; read-only view of edge, budget and alarm values |

**Exceptions that stay in Terraform or code (audit section 4):** WAF and infrastructure throttles, AWS Budgets, log and backup retention, auth and IAM, destructive kill switches, protocol constants.

**Tech lead decisions (S279):**

* Admin-only write. `ai_ops` and `customer_success` may only tighten.
* In the dev phase the admin may self-approve, with a reason and an e-mail to the tech lead.
* Env vars stay for one release as an emergency override, then go.
* The tenant AI budget defaults to `hard_stop = true`.
* acc1 Bedrock spend is **alert only**, never stopped: warnings on the gateway connection plus a free AWS Budget with alert e-mails only.

## Done when

* Platform › Settings lists every high- and medium-impact item of the inventory with its effective value.
* The administrator changes one value per app on Dev, and the app reads it within the cache time, with no deploy.
* `settings-lint` is a required check in each app repo.
* No env var remains for a migrated setting after one release.
* A live check is recorded per lane.
