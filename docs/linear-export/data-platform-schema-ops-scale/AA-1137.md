## Problem

Work today runs from a Linear issue (Problem / Scope / Done-when) plus implementation notes. There is no agreed requirement list with ids, no task list linked to requirements, and no way to follow an issue from its acceptance criteria to the tests, the PR and the live evidence without reading chat logs. Kiro's spec flow (requirements with EARS criteria, design, tasks) gives that traceability. Advisory: root `docs/audits/2026-11-18-S284-hooks-spec-advisory/README.md` (section 5 and slice 3).

## Scope

1. Spec format, Kiro-compatible, in the owner repo `.kiro/specs/AA-<n>-<slug>/` (cross-repo specs in the root): `requirements.md` (front-matter id/issue/status/owner_repo/kind; EARS criteria R1.1… each with a Verify line), `design.md` only for migration / auth / multi-repo issues (decisions D1…, CONTEXT.md impact, docs impact, test strategy per R), `tasks.md` (checkbox T1… with `_Requirements: R…_`, carried / dropped markers). Templates: feature, bugfix, quick.
2. Spec by risk (tech lead S284): feature spec for migration / auth / multi-repo issues, quick spec (requirements + tasks) for ordinary issues, no spec for small chores.
3. Approval: the requirements are approved with the session issue list; the tech lead approves only design decisions the agent flags as hard to reverse (boundaries, grants, data deletion, ADR-level) on the decision page; tasks are not approved.
4. `trace_check.py` (task → requirement → test/live step), `lane.js` args `spec` + `tasks`, `lane-start-guard` checks only when a spec is given, lane output `trace[]`, reviewer lens "spec".
5. CI job `spec-trace` (blocks only for issues that have a spec), Linear Done-when = R ids + spec path, specs frozen after `implemented` and archived.
6. Pilot on 1–2 real issues of the next session.

## Done when

* One issue goes Linear → R → T → lane trace → PR → aa-ship evidence without reading chat, and `spec-trace` is green on its PRs.
* Templates and the approval rule are in the `aa-linear-issue` / `aa-session` skills.
