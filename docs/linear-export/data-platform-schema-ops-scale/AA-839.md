## Problem

There is no defined procedure for a real personal-data deletion request.

* **Tenants.**
  * `POST /admin/tenants/{id}/offboard` (summary "GDPR offboarding") is soft only.
  * Per [AA-797](https://linear.app/aa-ecosys/issue/AA-797/admin-tenants-bugs-status-toggle-does-nothing-plan-id-never-set) (Nghiệp, 14/10/2026), offboarding deletes nothing, and `/restore` brings the tenant back whole.
  * The docstring says "GDPR data deletion is a separate follow-up, not automated here" (`admin.py:1348`, `CONTEXT.md:438`). No issue tracks that follow-up.
* **Travellers/customers.**
  * DM-6.7 lists what an erasure must cover.
  * Booking `DELETE /customers/{ref}` only archives the customer (`customers.py:71`).
  * Roadmap L3 ("erasure runbook") has no Linear issue.
* The endpoint name suggests a compliance capability that does not exist yet.

## Scope

1. **Traveller erasure runbook (DM-6.7).**
   * Tables it must cover:
     * `booking.customers` (+ `customer_identities` once Phase 4 adds it; `customer_otps` / `customer_sessions` until Phase 4 drops them)
     * `booking.inbox_events.payload`
     * `booking.trip_cases.notes` / `inquiry_snapshot`
     * `booking.notifications`
     * `booking.audit_logs` before/after jsonb: redact, never delete
     * `tripplanner.customers`, `tripplanner.outbox.payload`, `tripplanner.sessions`
     * the Cognito EXTERNAL user
     * the S3 archives written by [AA-825](https://linear.app/aa-ecosys/issue/AA-825/data-retention-rollups-for-log-tables-llm-call-log-180-d-daily-rollup)
   * Each owner erases its own schema.
   * It runs under DRY RUN (`skill/aa-cis-schema/references/destructive-ops.md`), ends with a verification query, and writes one Booking audit row.
2. **Tenant erasure runbook.** It runs only after offboard plus a retention window that Nghiệp sets. It covers:
   * content, brand identity, planning config, T2 versions
   * users ([AA-813](https://linear.app/aa-ecosys/issue/AA-813/portal-tenant-user-accounts-invite-users-roles-ownereditorviewer-api), once built)
   * integrations/secrets (`acp/cms/*`, `acp/social/*`)
   * usage/log rows: delete or anonymise
   * the tenant's S3 prefixes

   The audit row is kept. After this step the tenant can no longer be restored, so it needs Nghiệp's explicit approval.
3. **Endpoint wording.** Rename the offboard summary/docstring so it no longer claims GDPR deletion, and point it at the runbook.
4. **Owned elsewhere (out of scope):**
   * 90-day outbox/inbox redaction (DM-6.6, [AA-825](https://linear.app/aa-ecosys/issue/AA-825/data-retention-rollups-for-log-tables-llm-call-log-180-d-daily-rollup))
   * hashed `guest_token` ([AA-827](https://linear.app/aa-ecosys/issue/AA-827/security-tripplanner-guest-token-is-the-session-id-in-plaintext-issue))
   * tenant CRM deletion (DM-6.8, [AA-821](https://linear.app/aa-ecosys/issue/AA-821/research-tenant-crm-customerlead-management-for-tenants-ms-thus-idea))
   * `pii:` column tags ([AA-807](https://linear.app/aa-ecosys/issue/AA-807/data-phase-1-foundation-per-app-db-owner-roles-migration-ownership))

**Trigger:** start when ADR 0006 Phase 4 (the customer part of [AA-680](https://linear.app/aa-ecosys/issue/AA-680/aaa-identity-customer-otp-auth-shared-with-tripplanner-staff-rbac)) begins, or before prod / the first real traveller data, whichever comes first.
