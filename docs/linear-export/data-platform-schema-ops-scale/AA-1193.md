## Goal

An API build that starts and passes health checks but breaks a real flow is rolled back automatically, like the web apps already are.

## Problem

S295 Well-Architected review, OPS06 (MRI): the smoke-red rollback job (`ecs_smoke_rollback.py`, from the earlier rollback work) runs only in the 4 web/admin deploy workflows. The `deploy-dev.yml` / `post-deploy-verify.yml` of AA-CIS-App, AA-Booking and the AA-Partner api have no rollback step. The ECS circuit breaker only catches tasks that fail to start or fail health checks, so a functional regression keeps serving the pilot environment until someone fixes forward.

## Scope

1. Reuse the existing rollback job in the post-deploy verify of CIS (api + worker together, same image), Booking api and CRM api: smoke red → roll back to the previous ACTIVE task definition revision, wait for stable, compare `git_sha` on `/health`.
2. Respect the deploy gate (job tables / waves) the same way the deploy does.
3. Alert to the ops topic with the failing smoke step and the rolled-back revision.
   Out of scope: DB rollbacks (migrations only move forward), Vercel/Lambda.

## Done when

* A deliberate smoke failure on a throwaway branch deploy rolls each of the 3 APIs back to the previous revision, and `/health` shows the old `git_sha` (run summaries as evidence).
* The alert arrives with the failing step.
* The rollback runbook (`docs/ops/runbooks/rollback-ecs.md`) mentions the automatic path.

## Verify

Workflow run summaries of the drill per app; `aws ecs describe-services` rollout state; `/health` before/after.
