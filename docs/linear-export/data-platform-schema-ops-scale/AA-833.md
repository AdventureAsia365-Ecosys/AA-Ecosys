# AA-833 — [Data/Ops] TripPlanner Lambda throttle alarms: stop paging on single 5-minute blips + cut the home-page prefetch fan-out (root cause fixed by CIS migration 235)

## Problem

`aa-tripplanner-dev-browse-throttles` flipped OK→ALARM→OK 7 times between 14/10 and 15/10, sending 14 SNS messages to `aa-cis-dev-acp-alerts`. Nghiệp got an email for every flip.

The alarm config makes it noisy:

* `Sum(Throttles) > 0` over a single 300 s period.
* `alarm_actions` and `ok_actions` are both set.
* Location: `infra/AA-CIS-Infra/accounts/aa365/observability_ecosys.tf:199-216`.
* `aa-tripplanner-dev-assembly-throttles` has the same config.

This noise trains people to ignore a topic that also carries the RDS, Booking and SES alarms.

**Root cause, fixed in S238.** The throttles were real:

* `catalog.v_tour_place ... WHERE tour_id = ANY($1)` parsed every live tour's itinerary on each call: mean 2.4 s, max 7.7 s.
* TripPlanner #77 added that read to every tour list and destination page.
* With 15 reserved browse instances busy, calls took 6–13 s and new calls were throttled.

CIS migration 235 ([AdventureAsia365-Ecosys/AA-CIS-App#746](https://linear.app/aa-ecosys/review/perf-catalogv-tour-place-parses-day-text-only-for-the-requested-tours-f44acf672f51), applied 15/10 11:33 UTC) fixed it. A burst of 8 concurrent destination pages now runs at avg 1.25 s / max 2.1 s per Lambda call, all cold starts. See the [AA-712](https://linear.app/aa-ecosys/issue/AA-712/adr-0002-move-the-place-pipeline-itinerary-places-geocoding-tour-graph) comment.

**What remains.** The home page renders 8 destination `<Link>` cards plus tour cards. Next.js prefetches each one, so after every deploy or ISR expiry, one visit fans out into many browse renders at once. A 503 page throws and is not cached, so the next visit repeats the work.

## Scope

1. **Alarm tuning, in Terraform (targeted apply, plan read first).**
   * Page only on sustained throttling, for example `Sum(Throttles) > 5` in 2 of 3 periods.
   * Drop `ok_actions`, or keep them only for the paging alarms.
   * Apply the same change to the assembly alarm.
   * Document the choice in `03-scaling.md` C4.1a.
2. **TripPlanner frontend.**
   * Set `prefetch={false}` on the home-page destination and tour cards, and on list cards where a burst is likely.
   * Add a single short retry, or a soft cached fallback, in `lib/catalog.ts` `browseGet` on 503/429, so one throttled call does not become an uncached error page.
3. **Watch for one week.**
   * The throttle alarms must not flip.
   * Lambda `Throttles` must stay near 0 at the 15 reserved instances.
   * If they do not, find the remaining burst source (crawler on the 892-URL sitemap, UI-verify runs).

## Done when

* `describe-alarms` shows the new periods / thresholds / actions for both TripPlanner throttle alarms, applied through Terraform.
* A home-page load with a cold cache triggers no `/destinations/*` renders until a card is hovered or clicked (Vercel runtime logs before/after).
* Browse `Throttles` stays at 0 and neither alarm changes state for 7 days. Evidence: `describe-alarm-history` and `get-metric-statistics`.

Created by the S238 backlog audit, after the live investigation of the alarm emails Nghiệp reported.
