## Problem

The C4.3 W48 database review (root `docs/audits/2026-11-24-S290-session/c43-w48/`) found one C1.2 target missed: CIS tenant reads p95 \~155 ms against 150 ms. The cause is `REQUEST_TOURS_SQL` (`shared/tour_liveness.py`, `request_tours`), used by the served badges on `/v1` lists and the publish / write / angle-gate 409 checks: 806 calls, mean 121.6 ms, \~29,000 buffer hits per call for \~8 rows. Most of the cost is the Subject rule subqueries evaluated per request row and the `v_tour_liveness` join on an expression key. Finding 3: the anomaly-breaker baseline query takes \~145 ms and spills \~3 GB of temp a week because its filter is not sargable.

## Scope

* `EXPLAIN (ANALYZE, BUFFERS)` of one typical call of each query through DB Migrate `run-script` (plan only, no row values in the output).
* Rewrite `REQUEST_TOURS_SQL`: compute the representative tour once per request (`LATERAL`), evaluate the Subject rule only when that tour is retired. Same result set and same 409 decisions.
* Make the anomaly-breaker baseline filter sargable (and add an index only when the plan needs one).
* Equivalence proof: old and new query return identical rows on live Dev data (read-only run-script over every request / tenant), plus unit tests for the retired / Subject-rule branches.

## Done when

* Both rewrites are live on Dev, the equivalence run shows 0 differing rows.
* The new plan for `REQUEST_TOURS_SQL` reads at least 5× fewer buffers per call and a timed sample of new calls has p95 < 150 ms; the baseline query writes no temp.
* C4.3 W49 (from 30/11) reads the new-call figures for the tenant-read target.
