## Problem

The admin cannot answer "what do we watch, of what type, for which app, who gets it, and where is the threshold".

* Overview › Apps health counts CloudWatch alarms per app by **name prefix**. It shows CIS 8 instead of 2 and misses 1 of 32 alarms.
* No total and no type are shown. EventBridge rules (16), budgets, in-app checks (CIS 23 + 9 per-stage families, CRM 19, Booking 2) and Sentry are not counted.
* In-app check thresholds are code constants (for example `JOBS_STARVED_AFTER_S = 900`, `ROLE_CONNECTIONS_PCT = 80`, `SPEND_NEAR_RATIO = 0.8`, Booking `STUCK_AFTER_S = 900`). This breaks the house rule that every threshold is editable on an admin page.
* The alerts topic has one confirmed recipient and no alarm on failed deliveries.
* The public generated `docs/generated/alarms.md` carries ALB / target group ID suffixes.

## Decisions (tech lead, S287 decision page, 10/10 as proposed)

* **D1:** extend Platform › Alerts (today only Recipients) with a **Catalogue** tab. It is the only full list. The Ecosystem status page ([AA-1140](https://linear.app/aa-ecosys/issue/AA-1140/ops-ecosystem-status-replace-adminoverview-with-one-live-period-status)) embeds a summary card from the same API.
* **D2:** CloudWatch thresholds stay Terraform-owned on purpose. The admin shows the live threshold with a "Change in Terraform" link. The agent opens the Infra PR. No PutMetricAlarm from the admin.
* **D3:** in-app check thresholds move into the settings registry (admin-editable, maker-checker) now.
* **D4:** time-boxed mute is phase P1 (with [AA-1141](https://linear.app/aa-ecosys/issue/AA-1141/ops-ecosystem-status-p1-change-annotations-alert-acksnooze-freshness)), not here.
* **D5:** two severities, `page` / `ticket`. Tag every alarm now and **create the second SNS topic for** `page` **now** (0 USD), so prod only adds recipients or channels.
* **D6:** no paging tool on Dev.
* **D7:** budgets of acc1 / acc3 / acc4 are shown statically from Terraform, with account IDs inserted at runtime. No cross-account read role on acc1.
* **D9:** add the `NumberOfNotificationsFailed` alarm on the alerts topic (0.10 USD/month). The second channel follows [AA-1110](https://linear.app/aa-ecosys/issue/AA-1110/ops-continuity-pack-second-key-holder-runbook-only-deployrollback).
* **D10:** on Dev the two SES bounce / complaint rate alarms are enough.
* **D11:** ack, noise review, burn-rate and synthetics wait for the pilot ([AA-1142](https://linear.app/aa-ecosys/issue/AA-1142/ops-ecosystem-status-p2-slo-and-error-budget-burn-incident-record)).
* Tech lead: "làm đầy đủ" (do it in full).

## Scope

**Infra (Terraform, one PR):**

* Tags `Severity` (page | ticket), `Component` and `Mutable` on every CloudWatch alarm and SNS-notifying EventBridge rule.
* A second SNS topic for `page` severity. Page alarms notify both topics.
* `NumberOfNotificationsFailed` alarm on the alerts topic.
* Read-only permissions for the CIS task role: `tag:GetResources` / `cloudwatch:DescribeAlarms` / `ListTagsForResource`, `events:ListRules`.
* Fill the coverage gaps found in the S287 inventory, each alarm stated with its cost:
  * CIS worker and Booking worker liveness (no CloudWatch alarm today);
  * CIS and Booking API 5xx rate (only CRM has one).
  * That is about 4 alarms × 0.10 USD.
* The generator of `docs/generated/alarms.md` masks ALB / target group IDs.

**CIS:**

* Apps health groups alarms by the `App` tag. Add the total and counts per type.
* New **Catalogue** tab on Platform › Alerts. One row per alert condition: name, app, component, type, severity, condition, threshold source, editable via (settings / terraform / none), channel, runbook, owner role, state, freshness.
* The catalogue covers CloudWatch alarms, EventBridge rules, budgets (static for the other accounts), CIS in-app checks, and the Booking / CRM in-app checks from a static registry each repo exports (no cross-schema reads).
* A coverage-gap column.
* An API the [AA-1140](https://linear.app/aa-ecosys/issue/AA-1140/ops-ecosystem-status-replace-adminoverview-with-one-live-period-status) status card can call.

**CIS / Booking / CRM:** every in-app check threshold read from that app's settings registry (admin-editable, maker-checker, audited), with the current constants as seeded defaults.

**Root:**

* Docs and the generated alarm catalogue updated.
* DM-7.1 rows if a new table appears (prefer the existing audit log and notifications first).

## Done when

* Platform › Alerts › Catalogue lists every CloudWatch alarm (33+ after this issue), every EventBridge rule and every in-app check. Each row has app, type and severity, and the counts match a live read.
* Apps health shows CIS = 2 (or the right number by tag), not 8, plus a total.
* Changing an in-app check threshold on the Settings page changes the check's behaviour. Proven live on one check.
* The `page` topic exists and a page-severity alarm's actions include it.
* The `NumberOfNotificationsFailed` alarm and the new coverage alarms exist in state OK.
* `docs/generated/alarms.md` has no resource ID suffix.
* No UI text shows issue IDs. English by default.
