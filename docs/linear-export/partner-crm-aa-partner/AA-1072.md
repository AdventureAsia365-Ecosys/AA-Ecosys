## Problem

The S275 study of an Odoo tour & travel app (AA-1065, report root `docs/research/2026-11-10-odoo-tour-travel-plugin-comparison.md`) found these gaps. The tech lead approved building all of them (S275, 10/11/2026). We build the features in our own code; the app's code is OPL-1 and is never copied.

## Scope

* **'Book now' on the agency's public tour page with live price** (crm-02, partly, value high, effort L).
  * Today: web/app/trip/\[tourId\] is the white-label tour page (moved from CIS) with no booking form. Intake form only captures an enquiry. Client proposal page /c/p already does hold + accept + deposit rows (crm.proposal hold\_\* columns, crm.payment_schedule).
  * Build: Add a booking widget to /trip/\[tourId\] (feature-keyed per tenant): pick an AA departure (Booking GET /products + departures), party by pax type, live price = agency retail (crm-05/06) on the Booking quote; submit creates traveller (dedupe), trip at stage proposal, a one-option builder proposal, a Booking hold, and sends the client to /c/p accept + deposit. Rate-limit + honeypot like the intake form. Data: crm.trip.lead_source='web_booking'; crm.public_booking_attempt(id, tenant_id, tour_source_id, departure_id, party jsonb, quote_id, status, ip_hash) for abuse control.
  * Depends on: crm-05, crm-06, crm-03 (or manual pay), Booking departures/quote API
* **Online deposit / instalment payment (agency's own gateway)** (crm-03, missing, value high, effort L).
  * Today: Pay window on /c/p with manual bank-transfer instructions and 'I have paid' (invoice.claimed_at, verify_transfer task). app/payments/providers.py has only 'manual'; 'stripe' (Connect Standard BYO) and 'vn_gateway' are stubs; card button returns 409 provider_not_available. crm.payment_provider_account exists. Stripe paused (ADR 0019 b14).
  * Build: Finish the provider seam: one BYO VN gateway (VNPay/MoMo/OnePay, agency's own merchant account in crm.payment_provider_account, secrets in integration_credential) creating a pay session per invoice; signed webhook writes crm.payment (provider, provider_ref) idempotently and settles the schedule row; never block on a business error (reuse paid_unfulfillable). Stripe stays behind the existing feature key until b14 is lifted.
  * Depends on: ADR 0019 b14 decision (Stripe), choice of VN gateway

S277 live check on Dev (synthetic agency Sen Vàng, VNPay **stub** mode only, invented merchant code; agency restored afterwards to base USD, Book now off, gateway disconnected). The whole flow works end to end:

- Book now is off by default.
- Stub connect: 200, account vn_gateway active, VND, mode stub. The secret is never shown back.
- `GET /crm/public/v1/book/<form key>?tour=…` returns 200 with the tour, departures and seats left.
- `POST …/price {adults:2, child_ages:[7]}` returns 200: USD total 300.00 with adult ×2 and child ×1 lines, available. In VND the total is 8,250,000.
- IPN with a dummy reference: 200 `{RspCode:"01"}`.
- Browser:
  - The booking returns 201, then /c/p with the token removed from the address.
  - The hold goes active. Accepting issues the deposit invoice.
  - Pay online leads to the stub page (1,650,000 VND), then Pay (simulated), then "Paid. Thank you."
  - Afterwards: invoice paid; payment method online, provider vn_gateway; trip booked; lead_source web_booking.
- Screenshots (tour widget, client pay box, stub page, Settings > Payments) in root `docs/audits/2026-11-11-S277-crm-live-verify/`.

**Findings, being fixed in lane l34 (one AA-Partner PR):**
1. Low: after a disconnect, `GET /settings/payment-methods/vn-gateway` still answers connected:true, because status reads the credential row. Each reconnect also adds another account row.
2. Medium: a 1-adult VND public booking answered 409 `discount_needs_approval` (`below_cost`). The owner discount gate ran on the public path. The visitor saw a generic error and lost one of the 5 attempts per hour.
3. Low risk: price check, booking, hold, accept and Pay online share one limit of 5 writes a minute, so checking the price twice and then paying returns 429.
4. Observation: the client summary showed "Balance … due" with a past date, while the schedule list said everything is due today.

The issue stays In Progress until the fix is deployed and the stub flow is re-run.
