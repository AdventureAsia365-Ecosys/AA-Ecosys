## Why

**Today's problems:**

* Long work runs as `asyncio.create_task` inside the API container: T2 rewrite, T9 write, segment research, A3 atomize.
* A deploy or restart kills it: ECS `stopTimeout` is 90 s, but a long tour takes 105–207 s.
* There is no retry, no status and no reaper.
* Bedrock Batch ([AA-606](https://linear.app/aa-ecosys/issue/AA-606/build-bedrock-batch-inference-cho-s1-rewrite-100-tourlan-xin-iam-batch)) is still blocked by AWS ([AA-624](https://linear.app/aa-ecosys/issue/AA-624/blocker-bedrock-batch-chua-enable-tren-acc3-aws-case-178979743800653)), so it cannot run the rerun.

## Design (ADR 0001, decision 3)

**Table** `shared.job`**:**

* `id`, `kind`, `payload jsonb`, `status` (`queued` / `running` / `succeeded` / `failed` / `stopped_budget` / `cancelled`);
* `attempt`, `max_attempts`, `run_after`, `locked_by`, `locked_until`, `idempotency_key` (unique);
* `progress jsonb`, `cost_usd`, `error`, timestamps;
* `parent_job_id`, used for waves (rerun → per-country → per-tour).

**Worker:**

* Same Docker image, a different command (`python -m worker`).
* Claims jobs with `SELECT … FOR UPDATE SKIP LOCKED`. A heartbeat extends `locked_until`.
* Retries with exponential backoff.
* A **reaper** re-queues or fails jobs whose lock expired.
* **Concurrency caps** per kind and per provider (for example Bedrock writer 4, DFS 1).
* Handles SIGTERM gracefully: finish or release the job.

**API and UI:**

* `POST` endpoints enqueue a job and return a `job_id`.
* `GET /jobs/{id}` returns the status.
* Progress keeps using the Redis live-writing snapshot (ADR 0004).
* Admin **Jobs** page: filter by kind/status, progress, cost so far, cancel, retry.
* Every job goes through the cost guard.

## Why Postgres rather than SQS

* Transactional with the data it changes.
* Queryable (jobs are just a table).
* No new AWS service beyond one ECS service.

SQS can be added later behind the same interface if volume demands it.

## Done when

* A sample job kind survives a forced ECS redeploy mid-run: it is re-queued and completes.
* The Jobs page is live.
* Tests cover claim, retry, reaper and idempotency.

Evidence:
- **CI integration (Postgres 15): 11 passed.** They cover claim/cap, idempotency, retry/backoff, reaper (re-queue vs fail), release-on-shutdown (attempt not counted), cancel queued/running, and the worker end to end.
- **Live on Dev:**

  - Two real research jobs, both `succeeded` on attempt 1:
    - `c18f967e`: 15/15 Bhutan places, $0.2065;

  - `force-new-deployment` was triggered 2 s after the job started, and `stop-task` 3 s after the second one started. Both jobs **finished normally**.

  - So in practice any job shorter than ~5 min finishes on the old task. A job longer than 300 s + 20 s grace is released and picked up again (proven in the integration tests).
