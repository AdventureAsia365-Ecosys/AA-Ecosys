## What happened (S207, 01/10/2026)

The job worker runs inside the API process ([AA-650](https://linear.app/aa-ecosys/issue/AA-650/p1-durable-job-runner-postgres-queue-worker-ecs-service-replaces-in)). On a deploy, ECS reports the rollout COMPLETED as soon as the new task is healthy, but the old task keeps running for \~5 min while it drains (ALB deregistration delay) — and its worker loop keeps **claiming new jobs**.

Evidence: deploy :417 (keyword-relevance fix, PR [AdventureAsia365-Ecosys/AA-CIS-App#531](https://linear.app/aa-ecosys/review/fix-s1-keyword-relevance-whole-words-no-other-country-no-departure-27c912bf7666)) COMPLETED 06:03:29 UTC. The `s1_seo_prefetch` job enqueued at 06:04:34 was claimed by the old :416 worker (`ip-10-2-10-49`, last seen 06:08:07) and wrote the old, wrong keywords ("village life bhutan", "seoul airport transfer") for the Korea trial. Running the same functions inside the new container gave the correct result.

## Fix

Each worker records its ECS task-definition revision (task metadata endpoint v4) in its `shared.job_worker` row (`caps.task_revision`). Before claiming, a worker checks whether a live worker (seen in the last \~45 s, not stopped) runs a **newer** revision; if so it stops claiming (running jobs finish normally). Workers without a revision (local runs) never yield.

## Done when

Unit tests for the yield rule; deployed; after the next deploy a job enqueued during the drain window runs on the new task (checked in `shared.job.locked_by` / job_worker).
