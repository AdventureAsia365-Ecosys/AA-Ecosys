# AA-651 — [P1][INFRA] Worker ECS service for the job runner (AA-CIS-Infra)

A Terraform change in `accounts/aa365`:

* a new ECS service `aa-cis-dev-worker` on `aa-cis-dev-cluster`;
* the same image and task role as `api`, with command override `python -m worker`;
* no ALB target;
* desired count 1, scalable;
* `stopTimeout` 120 s;
* its own CloudWatch log stream prefix;
* a CPU/memory sized for LLM I/O (not CPU-bound).

The App deploy workflow must update both services, `api` and `worker`, on every image push.

Keep the invoker IAM unchanged: the worker uses the same ECS task role, so the Bedrock satellite trust still applies.

## Done when

* The plan is reviewed and applied.
* The worker service runs the new task definition.
* The App CI deploys both services.

**Design notes:** same image / execution role / TASK role as the api (Bedrock satellite trust + secret grants unchanged, per the issue). Spot-weighted like the api (a reaped job re-queues, so Spot is safe + ~70% cheaper). Autoscaling min=1/max=3 on CPU/mem. Per-kind caps stay DB-wide exact across tasks (`queue.claim` counts running jobs table-wide under an advisory lock), so adding worker tasks never multiplies a cap — `a3_atomize` stays 1. Sizing 512/1024, ~\$6–9/mo.

This unblocks AA-652 (jobs no longer compete with HTTP serving) and relates to AA-711 (the drain/yield-on-newer-revision logic now runs in a dedicated process).
