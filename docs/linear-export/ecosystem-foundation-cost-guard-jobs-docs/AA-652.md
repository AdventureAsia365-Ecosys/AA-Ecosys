# AA-652 — [P1] Move T2 rewrite, T9 write, research and A3 atomize onto jobs; job-based status in the portal (fixes stuck "Writing…")

## Problem

**Reported by Ms. Thư:** a tour that has finished writing still shows "Writing…" in the portal.

**How the status is derived today:**

* The portal infers "writing" from `tenant_tour_versions.status='pending' AND edit_source='ai_generated'` (`CatalogTab.isAiWriting`).
* If the background task dies (deploy/restart), the row stays `pending` forever.
* The Social Content wizard polls the piece in a similar way.

\[HYPOTHESIS\] This is the root cause. There are no stuck rows in the DB today because the WanderLux data was cleaned, so the bug must be reproduced by redeploying during a write.

## Scope

* Rewrite, write, research and atomize are enqueued as jobs (depends on the job-runner issue).
* Versions and pieces get a `job_id`. The portal reads the job status: `queued` / `writing` / `checking` / `done` / `failed`, with a Retry button.
* The reaper marks orphaned rows `failed`.
* Remove the `pending` inference in the frontend.
* A regression test that redeploys during a write, in the live Dev verification.

## Done when

A write interrupted by a redeploy either completes after re-queue or shows **failed + Retry**, never an endless "Writing…".

### 2026-09-29 02:01 — nghiep pham quoc

PR-C (#464) — A3 atomize moved onto the job runner (export publish + admin re-atomize both enqueue `a3_atomize`).

**Incident on Dev (29/09, ~00:40–01:02 UTC):** the a3_atomize chain ran on the API event loop. `compute_embedding()` paces with a blocking `time.sleep(3.5)` (AA-610) and is called from async `atom_matching`, so the loop froze, `/health` failed, and ECS replaced the task twice (00:46, 00:59). The job was released on each shutdown and re-claimed, looping. Cancelled manually at 01:02. Before this change the same chain ran as an in-process asyncio task, so the blocking was pre-existing, just now visible.

**Hotfix #465** (merged 0b39d74, deployed task def :363):
- `a3_atomize_job.run` executes the chain in its own event loop on a worker thread (`asyncio.to_thread` + `asyncio.run`), so the API loop is never blocked.
- `queue.MAX_RELEASES = 3`: a job released more than 3 times on shutdown is failed instead of looping forever; the terminal hook runs on release-fail/cancel.

**Re-verification (retry of job 547d955b on :363):**
- `/health` stayed 200 for the whole 30-min watch, max latency 2.17 s; no "unhealthy" ECS task replacement.
- Atomize skipped (9/9 days already atomized), segment matching done in 4 s (23 segments from 24 atoms).
- Job then entered the PAA question-landing step (`precompute_question_landings`), ~1 Cohere embed per 3.5 s, 500+ calls so far, cost < $0.001. Final job result to follow.
