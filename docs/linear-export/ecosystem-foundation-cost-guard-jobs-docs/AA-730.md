## Problem

Kiro / Claude Code run ECS exec and other AWS commands with an 8h `aa365-admin` STS session in the agent's own shell, while the same agent reads untrusted input (supplier files, Jira, web). Approval on Terraform (S210) does not limit what the agent can reach during those 8 hours. Environment limits hold where intent checks fail (handbook Sec 20–21).

## Step 0

List the AWS actions agents actually use (ECS exec into the dev cluster, S3 runner bucket, CloudWatch logs, RDS read via exec, …) before writing the policy, so the role does not slow daily work.

## Scope

* Role for agent sessions: read logs/DB, ECS exec into dev, write to the runner S3 bucket. No IAM write, no RDS/snapshot delete.
* Terraform (already) and prod migrations go only through GitHub workflows.
* MFA'd admin profile stays with Nghiệp, not in agent shells.

## Done when

Inside an agent session, `aws iam create-user` and `aws rds delete-db-snapshot` are denied; normal session tasks still work.

**Blocker found — the role can't be assumed yet.** With a correct MFA code, assume fails:
```
User: arn:aws:iam::005097885195:user/nghiep-admin is not authorized to perform:
sts:AssumeRole on resource: role/aa-cis-dev-agent-session
```
The role's **trust** policy allows it (principal `...:root` + `aws:MultiFactorAuthPresent=true`), but a `root`-principal trust also requires the **caller's identity policy** to grant `sts:AssumeRole` on this role ARN — and `nghiep-admin`'s policy doesn't. So the trust half is in place, the permission half is missing.

**Fix (Terraform, human-applied — not an agent task):** either
- add an `sts:AssumeRole` allow on `arn:…:role/aa-cis-dev-agent-session` to `nghiep-admin`'s IAM policy, or
- change the role's trust principal from `:root` to the exact user ARN `arn:aws:iam::005097885195:user/nghiep-admin` (keeps the MFA condition), which lets the trust policy alone authorize it.

Until then the negative/positive permission tests (iam create-user / rds delete-db-snapshot → AccessDenied; ecs list-tasks / s3 ls bronze/scripts → OK; one ECS-exec script) can't run. The config side (profile) is done; the IAM side needs this one Terraform change. Keeping AA-730 In Progress.

### 2026-10-11 13:20 — nghiep pham quoc

## S227 — closed: caller grant added, Done-when verified live

### Root cause (confirmed)
The role `aa-cis-dev-agent-session` trusts `...:root` + MFA. With a `:root` trust principal AWS also requires the **caller's own identity policy** to allow `sts:AssumeRole` on the role ARN. The caller is `user/nghiep-admin` (profile `aa365-agent` chains base-user → agent-session). That user had only AWS-managed ReadOnly policies → `AccessDenied`.

### Fix applied (Nghiệp-approved, Method 1)
`nghiep-admin` is a hand-created user, not in Terraform state, so the grant was attached directly as an inline user policy `assume-agent-session` (not via Terraform import):
```json
{"Effect":"Allow","Action":"sts:AssumeRole","Resource":"arn:aws:iam::005097885195:role/aa-cis-dev-agent-session"}
```
Documented in `AA-CIS-Infra/docs/agent-session-role.md` + policy file `docs/agent-session-caller-assumerole.json`.

### Done-when — verified live with the `aa365-agent` session
`sts get-caller-identity` → `assumed-role/aa-cis-dev-agent-session/...`

| `iam create-user` | denied | AccessDenied (explicit deny) ✓ |
| `rds delete-db-snapshot` | denied | AccessDenied (explicit deny) ✓ |

The narrow agent role now covers daily work (ECS exec, runner S3, read-only describe) while IAM writes, RDS snapshot delete, and secret reads are explicitly denied. Agents can use `AWS_PROFILE=aa365-agent` instead of the full `aa365-admin` session.
