# AA-723 — [P1] Move ALL remaining in-process API background tasks onto the worker (shared.job) — S1 rewrite, revalidate, recompute; survive deploys + show on Jobs

## Problem

S1 run-tour (admin A1 rewrite) still runs **in-process in the API**: `POST /admin/run-tour-async` creates a `shared.pipeline_jobs` row and fires an `asyncio.create_task(_run_tour_job(...))` (api/routers/admin_pipeline.py). This is NOT on the durable job runner (`shared.job` + worker ECS, [AA-650](https://linear.app/aa-ecosys/issue/AA-650/p1-durable-job-runner-postgres-queue-worker-ecs-service-replaces-in)/651). Consequences:

1. **Every API deploy kills in-flight S1 jobs.** Live example S212 (05/10/2026): a Thailand rerun wave of 40 was running when PRs [AdventureAsia365-Ecosys/AA-CIS-App#564](https://linear.app/aa-ecosys/review/feat-admin-s1-rewrite-live-streaming-while-writing-aa-667-f58f2387d1e0)/#565/#566 deployed — **16 tours ended** `interrupted` **with** `cancelled (deploy/shutdown)` at 13:52, leaving 19 Thailand tours stuck `ingested`. No data loss, but the wave silently half-finished.
2. **S1 does not appear on the Jobs page.** `/admin/jobs` + `/admin/job-runner/*` read `shared.job`; S1 lives in `shared.pipeline_jobs`, so there is no way to watch/cancel/retry an S1 run from the Jobs UI. (Noted repeatedly in memory since S208.)

[AA-650](https://linear.app/aa-ecosys/issue/AA-650/p1-durable-job-runner-postgres-queue-worker-ecs-service-replaces-in)/652 moved T2 rewrite, T9 write, A3 atomize and research onto `shared.job` + the worker ECS service — **S1 run-tour was left behind.**

## Target

* Add a job kind `s1_rewrite` (services/jobs/) that wraps the existing `_execute_run_tour` executor.
* `run_tour_async` enqueues into `shared.job` (idempotency key = tour_id+model_tier+batch_id, reuse find_active_duplicate semantics) instead of an asyncio task.
* S1 then runs on the **worker ECS service** (`aa-cis-dev-worker`): survives an API deploy (worker drain + task-revision gating [AA-711](https://linear.app/aa-ecosys/issue/AA-711/bugjobs-draining-ecs-task-keeps-claiming-jobs-after-a-deploy-runs-them)), retryable, cancellable.
* Keep [AA-667](https://linear.app/aa-ecosys/issue/AA-667/admin-s1-rewrite-page-live-streaming-while-writing-reuse-livewriter) live streaming: the WritingProgress sink must bind inside the worker job (ctx.resources redis), same key `wp:{master}:tour:{job_id}`.
* S1 shows on `/admin/jobs` like every other kind (ties into [AA-721](https://linear.app/aa-ecosys/issue/AA-721/admin-ui-v2-jobs-page-rebuild-kit-react-query-worker-ecs-aware-per) Jobs rebuild).
* Migrate carefully: keep the pipeline_jobs path working until the job-runner path is verified; the S1 Rewrite page polls the new job id.

## Done when

Trigger a rewrite wave AND deploy the API at the same time → **0 S1 jobs cancelled** (they keep running on the worker); S1 jobs visible + retryable on `/admin/jobs`; [AA-667](https://linear.app/aa-ecosys/issue/AA-667/admin-s1-rewrite-page-live-streaming-while-writing-reuse-livewriter) live stream still works. Merge + CI + Dev deploy COMPLETED + live verify.

## S212 full audit — S1 is NOT the only task left in-process

Grepping `asyncio.create_task` in `api/` found every background task still running inside the API process (dies on an API deploy, invisible to `/admin/jobs`). Scope of this issue is ALL of them, not just S1 — goal: **the API serves requests only; every background task runs on the worker ECS service.**

| Task | Location | Risk |
| -- | -- | -- |
| `_run_tour_job` (S1 rewrite) | admin_pipeline.py \~1151 | killed 16 Thailand tours on deploy (S212) |
| `_revalidate_job` (human-edit re-score) | admin_pipeline.py \~3572 | pipeline_jobs + asyncio, dies on deploy |
| `_recompute` (segment/score/route after atom curate) | admin_atoms.py \~504 | fire-and-forget, \~1-2 min × 6 markets — deploy mid-run = half-computed ranking/route |
| `_run` (recompute after master_status change, [AA-713](https://linear.app/aa-ecosys/issue/AA-713/a3-atoms-follow-the-tours-master-content-status-inactivetrashed-tours)) | [admin.py](<http://admin.py>) \~46 | fire-and-forget, same data-correctness risk |
| `_s1_batch_ingest_task` | admin_pipeline.py \~1268 | asyncio; Bedrock Batch blocked ([AA-624](https://linear.app/aa-ecosys/issue/AA-624/blocker-bedrock-batch-chua-enable-tren-acc3-aws-case-178979743800653)), move for consistency |

Priority order: S1 rewrite first (broke the Thailand wave), then the two recomputes (data-correctness risk), then revalidate, then the batch-ingest shim. This is the audit [AA-651](https://linear.app/aa-ecosys/issue/AA-651/p1infra-worker-ecs-service-for-the-job-runner-aa-cis-infra) should have completed.

### 2026-10-06 00:24 — nghiep pham quoc

Two additions from the Harness Engineering review (doc sections 3.1–3.2):

1. **Read-before-write in the S1 executor.** If the worker dies mid-job, a retry must check whether `published_tours` / the version row was already written before writing again — no duplicate versions per tour.
2. **Recompute must be safe to replay and never expose half-computed state.** `_recompute` and `_run` (AA-713) should do a full recompute from live atoms (not incremental), write to a new version/staging set, then swap the "current" pointer in one transaction. Slate readers should never see segment counts drop then recover mid-recompute.

Extra verify: run a 10-tour wave, deploy the API mid-wave → 0 `interrupted`, exactly 1 version per tour; poll Slate during a recompute → totals never dip.

Related: AA-725 (CI deploy guard), AA-727 (wave object).
