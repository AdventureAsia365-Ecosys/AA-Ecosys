## Hiện tượng

Mọi trang `/portal/*` (tenant portal) tự động gọi `GET /api/admin/billing` — có vẻ nằm trong
`layout.tsx` dùng chung cho toàn bộ portal — và request này trả về **401 Unauthorized**.

Tái hiện ổn định trên cả **production** lẫn **local build**, không phải lỗi ngẫu nhiên/network.
Xác nhận qua Playwright session thật (tenant `wanderlux-travel`, login qua `/tenant-login`).

## Chưa điều tra — 2 khả năng

1. **Đúng thiết kế nhưng gọi sai chỗ:** endpoint `/api/admin/billing` đòi quyền admin, tenant user
   bình thường không có quyền → 401 là hành vi đúng của endpoint, nhưng layout chung của tenant
   portal lẽ ra không nên gọi endpoint admin-only ở đây.
2. **Bug thật:** thiếu auth header, route nhầm, hoặc endpoint đáng lẽ phải cho tenant gọi (dạng
   billing/quota riêng của tenant) nhưng đang trỏ nhầm sang route admin.

## Việc cần làm

- [ ] STEP0: đọc `layout.tsx` xác định chính xác vì sao gọi endpoint này, gọi để làm gì (hiển thị
      cái gì trên UI, nếu có).
- [ ] Xác định endpoint `/api/admin/billing` có đúng auth scope thiết kế không (đọc router, so

- [ ] Nếu là gọi sai chỗ: sửa layout gọi đúng endpoint tenant-scoped (nếu tồn tại) hoặc bỏ gọi khi
      không cần thiết cho tenant portal.
- [ ] Nếu là thiếu tính năng: đánh giá có cần build billing/quota view riêng cho tenant hay không
      (có thể liên quan [AA-489](https://linear.app/aa-ecosys/issue/AA-489/build-rewrite-quotathang-theo-tenant-chua-tung-djuoc-enforce-can-thiet), quota rewrite thật — cần kiểm tra trùng lặp trước khi quyết định).

### 2026-09-04 10:55 — nghiep pham quoc

**Shipped + live-verified, PR #299 merged (`a3cd796`), Deploy Dev green, ECS task def `:209`.**

**STEP0 finding** (confirmed possibility #1 from the issue, not #2): `GET /admin/billing` IS correctly admin-scoped by design — it accepts an arbitrary `?tenant_id=` (an admin "look at any tenant" knob, defaults to `aa_internal`), so it can never safely be exposed to a tenant session even with just a header change (tenant A could pass tenant B's id). The real bug: `/portal/*`'s `layout.tsx` + `DashboardTab.tsx` both `fetch("/api/admin/billing")` directly — that Next.js proxy runs `requireAdmin()` (real admin-JWT check) before ever attaching `X-Admin-Secret`, so a tenant portal session 401s there on every page load, for every tenant, always. Not related to AA-489 (rewrite quota — different data source, `shared.tenant_rewrite_usage` vs this endpoint's `v_tenant_monthly_usage` view — no duplication).

**Fix**: new `GET /v1/billing` (`api/routers/v1_tours.py`, same `quota_router` as AA-489's `GET /v1/quota`) — `tenant_id` always derived from the verified JWT `sub` claim, never a query param. Same `v_tenant_monthly_usage` query + response shape as the admin view, so `DashboardTab.tsx`/`BillingTab.tsx` needed zero field-mapping changes — just the URL. Both frontend call sites repointed to `/api/tenant/v1/billing`.

**Testing**: 4 new unit tests (`tests/unit/test_aa496_tenant_billing.py`), all pass; ran alongside AA-489's quota suite (11/11 pass). flake8 clean. All 5 required CI checks green.

**Real live-verify (post-deploy, actual domain, real minted tenant JWT — WanderLux Travel, `a1b2c3d4-...-001`)**:
- `GET https://api-cis.lumiguides.it.com/v1/billing` with the tenant's Bearer JWT → **200**, real data: `plan_tier=growth`, `tours_quota_monthly=200`, `tours_rewritten=4`, `llm_cost_usd=0.072`, 5 real activity rows (real tour names/countries/timestamps from `gold_aa_internal.tenant_tour_versions`).
- Cross-check `GET /v1/quota` (AA-489 sibling) → 200, consistent (`rewrites_used=2/500`).
- Confirmed the root cause is real, not hypothetical: same tenant JWT against `GET /admin/billing` directly (no `X-Admin-Secret`) → `403 {"detail":"Invalid admin secret"}` — exactly why the portal call always failed before this fix.

**Impact assessment** (issue's own open question): confirmed non-crashing but real — `billing` state stayed `null` on every real tenant's dashboard/billing page before this fix, so `BillingTab.tsx`/`DashboardTab.tsx` silently rendered hardcoded fallback defaults (`plan_tier: "growth"`, `price: 799`, `toursUsed: 0/200`) instead of the tenant's actual usage — not a crash, but every tenant's Billing page was showing fake numbers, not their real spend.

**Related, NOT fixed here (flagged, pre-existing, out of scope)**: `ApiTab.tsx`'s "API Access" doc list still shows `GET /admin/billing` / `POST /admin/brand-identity` as available endpoints — grep confirms `ApiPlayground.tsx`'s own proxy (`/api/playground/proxy/route.ts`) already blocks any path outside `/v1/tours`/`/v1/webhooks`, so those 3 lines have always 403'd through the Playground UI, unrelated to and pre-dating this bug. Not touched, to keep this fix scoped — full detail in `docs/implementation-notes/AA-496.md`.
