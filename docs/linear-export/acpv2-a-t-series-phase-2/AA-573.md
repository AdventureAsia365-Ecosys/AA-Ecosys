## Bối cảnh

Phát hiện tình cờ khi Nghiệp thử đăng nhập lại `/login` (CIS Internal staff login) trong lúc debug Claude in Chrome (09/09/2026). Nghiệp xác nhận: đây là bug thật, tự bản thân Nghiệp cũng gặp — không phải chỉ do môi trường tab tự động.

## Bằng chứng (Nghiệp tự chụp DevTools Network tab)

Chuỗi request thật khi bấm Login:

1. `POST /api/auth/login` → **200 OK**, ~1.10s — login THÀNH CÔNG ở backend.
2. `dashboard` (fetch) → **307** redirect tới `/admin/dashboard`.
3. `login` (fetch lần 2) → **200 OK**, 181ms.

Nhưng: nút Login trên UI vẫn hiển thị **"Connecting..." vô thời hạn**, không tự chuyển sang `/admin/dashboard` dù request đã hoàn tất từ lâu (quan sát ít nhất >10s không đổi). Phải tự thao tác thủ công (refresh trang hoặc tự gõ URL `/admin/dashboard`) mới vào được — session đã login thật (cookie/JWT đã set đúng, vì vào thẳng dashboard mà không cần login lại).

## Việc cần làm — STEP0 trước

1. Đọc code frontend xử lý submit login (`LoginPage`/tương đương) — xác định vì sao UI không cập nhật state sau khi nhận response 200 từ `/api/auth/login`.
2. Nghi vấn cụ thể cần kiểm tra:
   * Redirect logic có đang chờ 1 response/promise khác không tồn tại/không resolve (VD: chờ `dashboard` fetch trả về 200 nhưng nó lại trả 307, code không xử lý redirect như "thành công")?
   * Có lỗi JS runtime nào chặn state update sau `await` không (check console log thật)?
   * Có race condition giữa 2 lần gọi `/login` (thấy trong network log có 2 lần gọi `login`) không?
3. Xác nhận đây có phải regression mới hay đã tồn tại lâu (check git blame/history vùng code liên quan).
4. Fix để sau khi `POST /api/auth/login` trả 200, UI tự động chuyển sang dashboard mà không cần Nghiệp tự thao tác thủ công.

## Fixed + deployed + live-verified (real production URL)

**Root cause (STEP0, confirmed by reading code + reproducing locally before fixing):**
1. `login()` in `frontend/app/login/page.tsx` had **no double-submit guard** — both inputs' `onKeyDown` fired `login()` on Enter unconditionally, unlike `tenant-login/page.tsx` which already checks `!loading`. Live-reproduced: a scripted double-Enter fired **2** `POST /api/auth/login` + 2 `router.push("/admin/dashboard")` — exactly the "2 lần gọi /login" pattern in your Network tab.
2. `router.push` is fire-and-forget with **no `finally { setLoading(false) }`** — if the client-side transition ever stalled, the button had zero recovery path but a manual refresh. The likely stall trigger: `middleware.ts`'s own `verifyAdminToken()` re-verifies the freshly-issued JWT via an **uncached** `/auth/verify-admin` round trip — the same race shape AA-551 already fixed for `/api/admin/*` proxy calls, just never applied to `middleware.ts` itself.

Both are pre-existing since the page's original commit (`c5c35a5`) — not a recent regression.

**Fix (PR #354, merged `450d92e`):**
- `login()` guards re-entry (`if (loading) return`), Enter handlers gained `!loading`.
- Post-login redirect switched from `router.push` to `window.location.href` — a real navigation, immune to client-router edge cases.
- `middleware.ts` now shares AA-551's verify cache (`lib/auth-server.ts`, exported) so the verify-admin/verify-tenant race is closed at the source, not just papered over.

**B2B Tenant login checked** — `tenant-login/page.tsx` already had the `!loading` guard and a `finally` reset, so it did not show the "stuck forever" symptom, though it shares the same middleware race (now also closed).

**Live-verified with real Playwright, twice** (`tests/e2e/aa573-live-verify.spec.ts`):
- Local dev proxying prod backend: 3/3 passed (staff auto-redirect ~1.8s, double-Enter now 1 POST not 2, tenant auto-redirect ~1.9s).
- **Deployed production** (`https://aa-cis.lumiguides.it.com`, confirmed `READY` via Vercel deployment check for commit `450d92e`): 3/3 passed — staff 2697ms, double-Enter 1534ms (1 POST), tenant 1621ms. All well under the 3s bar, zero manual action.

Full trace: `docs/implementation-notes/AA-573.md`.
