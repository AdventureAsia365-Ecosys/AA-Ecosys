# AA-465 — [URGENT][PATCH TẠM] Tăng API Gateway integration timeout /v1/* — /goal (30.3s) và /write (57.2s) đã vượt trần 29s thật

## Bối cảnh

Từ điều tra [AA-453](https://linear.app/aa-ecosys/issue/AA-453/api-gateway-504-timeout-tren-goal-va-write-khi-llm-call-that-keo-dai) STEP0 (26/08, S159) — xác nhận qua đo thật (không ước lượng):

* `/goal` (sinh 3 angle): **30.29s** — VƯỢT 29s ngay cả khi chỉ sinh angle, chưa từng ai biết trước đây
* `/write` (T9 write + T10 9-gate blog): **57.16s**
* Cả 2 vượt trần `timeoutInMillis: 29000` xác nhận thật trên AWS (Terraform chưa từng set giá trị, chạy theo default trơ)
* API Gateway là REST API REGIONAL — đủ điều kiện tăng >29s theo chính sách AWS 2024, Account Service Quota `L-E5AE38E3` hiện = 29000ms, `Adjustable: true`, chưa từng xin tăng

**Quyết định (S159): patch tạm thời tăng timeout ngay để giải quyết 504 hiện tại, SONG SONG với issue riêng chuyển sang async+polling (kiến trúc đúng, không giới hạn tương lai) — không chọn 1 trong 2, làm cả 2.**

## Giới hạn quan trọng cần biết trước khi patch

1. Integration là 1 catch-all DUY NHẤT cho toàn bộ `/v1/*` — không tách timeout riêng theo route trong cấu trúc Terraform hiện tại. Tăng timeout sẽ ảnh hưởng ĐỒNG LOẠT mọi route `/v1/*`, bao gồm cả các route polling/đọc nhạy cảm với độ trễ: `GET .../execution/{id}` (thiết kế để trả nhanh liên tục — nếu backend treo, tăng timeout khiến FE chờ lâu hơn trước khi thấy lỗi), `GET .../slot-grid`, `GET .../requests/{id}`.
2. Việc tăng `timeout_milliseconds` trong Terraform CHƯA đủ — phải xin tăng Service Quota `L-E5AE38E3` ở tầng ACCOUNT trước, quota mới sau đó mới cho phép giá trị Terraform vượt 29000ms có tác dụng thật.
3. 1 route khác cũng khả năng chạm ngưỡng tương tự nhưng CHƯA từng đo: `POST /v1/tours/pool/{id}/rewrite` (rewrite+QA+atomize đồng bộ).

## Việc cần làm

1. Đo thêm case xấu nhất: `/write` khi T9 phải retry đủ 2 lần (theo [AA-450](https://linear.app/aa-ecosys/issue/AA-450/t9-content-writing-viet-moi-input-tu-t8-angle-gate-dja-chon-xong), tối đa 2 lần thử) — xác nhận tổng thời gian cộng dồn thật trước khi chốt giá trị timeout mới (không đoán).
2. Đo nhanh route chưa từng đo: `POST /v1/tours/pool/{id}/rewrite` — xác nhận có thật sự chạm ngưỡng không. KHÔNG đo `s1-from-atom/generate` (đã bỏ hẳn, xem ghi chú ở trên).
3. Dựa trên số đo thật, chọn giá trị timeout mới (đề xuất khởi điểm 90000ms — dựa trên 57s đo được + biên độ an toàn cho retry, nhưng XÁC NHẬN LẠI qua bước 1 trước khi chốt số cuối).
4. Xin tăng Service Quota `L-E5AE38E3` qua AWS Console/CLI (`aws service-quotas request-service-quota-increase`) — đây là thao tác account-level, có thể cần chờ AWS duyệt (thường vài phút tới vài giờ, không phải tức thời).
5. Sau khi quota được duyệt: set `timeout_milliseconds` trong Terraform cho integration `/v1/*`, plan → Nghiệp tự apply qua workflow_dispatch (MFA, theo đúng human-only gate cho Terraform).
6. Verify live: gọi lại `/goal`, `/write` thật, xác nhận không còn 504. Đồng thời verify các route polling (`execution/{id}`) vẫn hoạt động UX bình thường (không bị "treo cảm giác" lâu hơn khi có lỗi thật).

## [DUYỆT 26/08 — S159] Giá trị timeout chốt: 90000ms (90s)

Số đo thật tổng hợp (Claude Code, không ước lượng): `/goal` = 30.29s, `/write` (worst-case 2 attempts) = 57.16s, `/s1-from-atom/generate` = 48.13s (ngoài scope, đã bỏ hẳn), `/tours/pool/{id}/rewrite` = 0.34s (**đính chính Bulletin 1b: route này ĐÃ async sẵn, không rủi ro 504** — code có comment rõ "Run LLM rewrite in background", `v1_tours.py:315`).

Chốt **90000ms** — margin ~58% trên 57.16s (số lớn nhất đo được), đủ hấp thụ biến động thật của Bedrock/GPT-4.1 mà không xin quota cao hưn mức cần (tránh hại UX các route polling dùng chung integration). Không chọn trần tối đa AWS cho phép (~300000ms) vì không cần thiết cho mức độ rủi ro hiện tại.

Đã xác nhận với Nghiệp: vẫn làm patch này dù [AA-466](https://linear.app/aa-ecosys/issue/AA-466/arch-chuyen-goal-write-sang-pattern-async-202poll-thay-patch-timeout) **(async dài hạn) sẽ được xây** — [AA-466](https://linear.app/aa-ecosys/issue/AA-466/arch-chuyen-goal-write-sang-pattern-async-202poll-thay-patch-timeout) cần nhiều session để build (STEP0+design+BE+FE+verify), trong khi 504 đang xảy ra thật mỗi ngày cho tenant, không thể chờ. Sau khi [AA-466](https://linear.app/aa-ecosys/issue/AA-466/arch-chuyen-goal-write-sang-pattern-async-202poll-thay-patch-timeout) xong và cover đủ `/goal`+`/write`, patch này có thể "nghỉ hưu" tự nhiên (không bắt buộc rollback timeout ngay, chỉ là tùy chọn dọn dẹp sau này nếu muốn bảo vệ UX polling routes chặt hơn).

Bước 4 (xin Service Quota) đang được Claude Code thực hiện với giá trị 90000.

## [PHÁT HIỆN QUAN TRọNG 26/08 — S159] Fix CHƯA ĐỦ — còn 1 tầng chặn khác: ALB idle_timeout

Sau khi apply PR #33 (API Gateway 29000ms→90000ms) thành công — Claude Code KHÔNG dừng ở "config đã đổi", mà tự verify thật qua domain public (không phải localhost) và phát hiện: **504 vẫn còn**, chỉ dời từ ~29s lên **60.7s**.

**Root cause thật:** chuỗi request là `API Gateway → VPC Link → NLB → ALB → ECS`. ALB `aa-cis-dev-alb` có `idle_timeout` **mặc định 60s** (chưa từng set trong Terraform, `modules/alb/main.tf` không có thuộc tính này) — giờ là tầng chặn HẸP NHẤT trong toàn chuỗi, chặn trước khi API Gateway 90s mới có tác dụng.

**Quyết định:** tăng `idle_timeout` ALB lên **100s** (qua Terraform, PR riêng vì #33 đã merge) — cùng logic margin, trên ngưỡng 90s của API Gateway để ALB không bao giờ là nhành hẹp hơn. Đang chờ Claude Code mở PR mới, Nghiệp apply qua workflow_dispatch như thường lệ.

**Issue này CHƯA đóng** — sẽ đóng sau khi tầng ALB được fix + verify thật qua domain public xác nhận hết 504 hoàn toàn.

## ⚠️ CẢNH BÁO — margin còn lại chỉ 775ms trên trần 90000ms

`89.225s` đo được lần này KHÔNG phải cùng worst-case path đã dùng để chốt 90000ms ban đầu:
- Số dùng để chốt 90s: `/write` 2-attempt retry do `F1_grounding` = **57.16s**
- Số verify lần này: `/write` held do `F4_extreme_length` (content quá dài) = **89.225s** — một nhánh worst-case khác, chưa từng đo trước khi chốt giá trị

Biến động thật của LLM output (độ dài content, đường retry nào được chọn) có thể đẩy sát trần 90s trên 1 request khác bất kỳ lúc nào. **Không nên coi patch này là "đã giải quyết thoải mái"** — nó đang hoạt động thật, nhưng cần theo dõi, không phải kết thúc rủi ro 504 vĩnh viễn.
