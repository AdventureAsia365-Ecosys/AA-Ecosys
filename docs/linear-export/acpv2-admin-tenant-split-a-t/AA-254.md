## STEP0 (all 4 required points, real data) — recommending scope-down, not building the rule engine (04/09/2026)

Per this issue's own explicit STEP0 gate, checked all 4 points with real queries/calls before any design lock. Conclusion up front: **the data doesn't support building this** — recommending we don't build the rule engine, `pipeline_diagnoses` table, or Bedrock-escalation fallback right now. Details below, then moving to AA-489 per the chain instruction (discretionary priority, explicitly non-blocking).

### 1. Tab "Health" hiện render gì?
It doesn't exist as described. Grepped the whole `frontend/app/admin/` tree for a "Health" tab/label — nothing. The CIS PRD's §6.1 8-tab spec (Metrics/Volume/Quality/Cost/**Health**/Spot/SEO/Library/Langfuse) was never built as a tabbed page. The only real candidate is `/admin/run-health` — but that's AA-141's ACP `acp_stage_runs` page (polls `/api/admin/acp/run-health` every 30s), unrelated to CIS `pipeline_jobs`, exactly as this issue's own "Đề xuất scope" section already anticipated. No duplicate work risk — there's simply nothing there yet.

### 2. CloudWatch log group `/ecs/aa-cis-dev-api`
Confirmed via `aws logs describe-log-groups`: **only `/ecs/aa-cis-dev` exists** (14d retention, 34MB stored, actively written). `/ecs/aa-cis-dev-api` doesn't exist at all. Matches the already-documented CLAUDE.md note (not a new finding, just reconfirmed live) — the CIS PRD backlog #2 concern was correct and is already known/handled.

### 3. Real `shared.pipeline_jobs` schema
Confirmed via `information_schema.columns`: `id, job_type, status, request, tenant, result_version_id, pipeline_run_id, error, heartbeat_at, created_at, started_at, finished_at, current_stage` — 13 columns. `current_stage` and `heartbeat_at` are real and populated (46/46 rows have `heartbeat_at`, 23/46 have `current_stage`).

**Real correction to this issue's own premise**: `failure_summary` does **NOT** exist on `pipeline_jobs`. It's a real column, but on a different table — `silver_aa_internal.review_queue` (AA-241/AA-250's own subject). `pipeline_jobs` (AA-223's async run-tour job queue) and `review_queue` (AA-234/241's editorial review flow) are two separate systems; the issue's scope section conflated them when citing `failure_summary` as existing precedent on `pipeline_jobs`.

### 4. Real recent failure volume
This is the decisive one. All-time `shared.pipeline_jobs`: **46 rows total, ever. 45 succeeded, 1 failed.** The one failure (`2026-07-12`) was a real bug (`DataError: invalid UUID 'content_id', length must be between 32..36, got 10`) — a parameter-binding issue, not a recurring class of error (44 successful `run_tour` jobs since, no repeat). **Zero failures in the last 30 days.** The table hasn't received a new row at all since `2026-08-17` (2.5+ weeks) — this job queue is low-traffic to the point of near-dormancy right now.

### Bonus finding: the issue's own suggested fallback isn't viable either, right now
The issue's STEP0 contingency says "chỉ cần link Langfuse trace/job là đủ" if volume is low. Checked: `services/acp_shared/tracer.py`'s `AcpTracer` (the only real Langfuse integration in this repo) reads `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY` from env — both were **removed from the ECS task definition under AA-23** (confirmed via `aws ecs describe-task-definition`, not present in `secrets` or `environment`). `AcpTracer.__init__` silently catches the resulting `KeyError` and disables itself (`_enabled=False`) — Langfuse tracing has been a no-op in prod since AA-23. Linking to Langfuse traces isn't actually available as a fallback without separately re-enabling those credentials first (smaller, different ask — not filed here).

### What already covers the real (tiny) need
`frontend/app/admin/s1-rewrite/page.tsx` (AA-250 B2) already polls `GET /admin/jobs/{id}` and shows `job.error`/`job.current_stage` directly on the tour row the instant a job fails — an operator already sees the raw error text right where they're looking, with zero extra infrastructure. For 1 failure in the table's entire history, this is already sufficient.

### Recommendation
Don't build the rule engine / `pipeline_diagnoses` table / Bedrock-escalation fallback now — the real signal doesn't justify it (near-zero volume, existing error surfacing already covers the one real incident class seen). Suggest leaving this issue in Backlog and revisiting only if `pipeline_jobs` failure volume actually becomes real (e.g., a spike, or the job type expands beyond `run_tour`). No code changes this round.

Moving to AA-489 next in the chain.
