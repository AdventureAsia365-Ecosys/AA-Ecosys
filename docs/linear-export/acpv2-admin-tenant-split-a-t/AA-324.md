## Cập nhật S126 (25/07/2026) — chẩn đoán lại, giả thuyết gốc chưa được kiểm chứng

Đối chiếu docs Bedrock/Claude chính thức (fetch 25/07) cho thấy **giả thuyết trong title issue này ("cache_control chỉ hoạt động trên acc2 Bedrock trực tiếp") mới là 1 trong ít nhất 5 nguyên nhân khả dĩ**, và chưa nguyên nhân nào được loại trừ.

→ Đã tạo **ADR-2026-034** (Proposed) ghi lại đầy đủ. Tóm tắt dưới đây.

### ⚠️ Bước phân nhánh bắt buộc TRƯỚC mọi fix

Issue này hiện chỉ ghi `cache_read_input_tokens: 0`. **Phải xác định `cache_creation_input_tokens` bằng bao nhiêu.** Hai trường hợp có nguyên nhân hoàn toàn khác nhau:

| Quan sát | Nghĩa là | Hướng xử lý |
| --- | --- | --- |
| creation = 0 **và** read = 0 | Prompt **chưa từng được cache** | Sai cách đặt breakpoint, hoặc không đạt ngưỡng token tối thiểu |
| creation > 0 **và** read = 0 | Cache ĐƯỢC ghi nhưng không đọc lại được | Prefix không ổn định, hoặc TTL 5 phút hết hạn giữa các call |

Memory S124 có ghi `cache_write_tokens: 0` — nếu con số đó chính là `cache_creation_input_tokens` thì nhánh 1 đúng, và giả thuyết cross-account **sai**.

### 5 giả thuyết, xếp theo xác suất

| # | Giả thuyết | Bằng chứng |
| --- | --- | --- |
| **H1** ⭐ | Code dùng **automatic caching** kiểu Claude API (`cache_control` ở top-level request) | **Bedrock KHÔNG hỗ trợ automatic caching** — phải đặt `cachePoint`/`cache_control` trên từng content block. Bedrock **im lặng bỏ qua, không báo lỗi**. Đây đúng là triệu chứng "code đúng, wire đúng, nhưng zero" |
| H2 | TTL 5 phút hết hạn giữa các call | TTL mặc định 5 phút, chỉ reset khi có cache hit |
| H3 | Prefix không ổn định — có `tour_id`/timestamp nằm TRƯỚC phần cần cache | Mọi thay đổi ở prefix gây cache miss |
| H4 | Không đạt ngưỡng token tối thiểu | Prompt S1 có thể ngắn hơn ngưỡng |
| H5 | Call đi qua **Batch** — cache vô nghĩa theo thiết kế | Batch không cache giữa các record |

**H1 là khả năng cao nhất**: đây là hệ quả kinh điển của việc port code viết theo semantics Anthropic API sang Bedrock.

### Thu hẹp phạm vi — 2 kết luận đóng bớt việc

1. **N2 decompose: ĐÓNG câu hỏi caching.** N2 chạy qua Bedrock Batch, mà Batch không cache giữa các record theo thiết kế. Không phải bug, không cần điều tra.
2. **N7 là chỗ DUY NHẤT caching đáng làm** — prefix ổn định (system + brand rubric + `acp_output_rules` + atom corpus ≈ 6-8k token), gọi lặp 4/6 lần mỗi slot.

   ⚠️ **Nhưng phụ thuộc model**: S124 đã xác nhận **Palmyra X5 KHÔNG hỗ trợ prompt caching**. Nếu writer N7 chốt là Palmyra (mặc định Q8) thì caching **không tồn tại cho bước draft**. Đây là chi phí ẩn của Q8 chưa được tính — xem ADR-2026-034 §3.

### 📉 Giá trị tiền thật của việc fix — đọc trước khi ưu tiên

Ước tính ở 5 tenant: tiết kiệm ~**$4/tháng**. Prefix cache được ~7k token × 4 call/slot; có cache → tiết kiệm ~61% phần input prefix ≈ 24% chi phí slot.

**KHÔNG nâng issue này lên P0 với lý do chi phí.** Lý do đáng làm là **độ trễ** (N7 có deadline cứng thứ Ba) và **nợ kiến trúc** khi lên 20+ tenant. Xem ADR-2026-036.

### 🔒 Ràng buộc kiến trúc phát hiện thêm — đừng "tối ưu" nhầm

N7 dùng SQS FIFO với `MessageGroupId = tenant_id`. Cấu hình này **vô tình đã đúng cho cache**: nó gom các slot cùng tenant chạy tuần tự liền nhau, giữ cache sống trong TTL 5 phút.

**Không được đổi sang phân tán theo slot để tăng throughput — sẽ giết cache.**

### Cache prefix contract đề xuất (ADR-2026-034)

```
[system prompt]
[brand rubric]
[acp_output_rules]
[atom corpus]
⟨cache breakpoint⟩
[brief / SERP / slot metadata]
[instruction]
```

Luật cứng: phần TRƯỚC breakpoint không được chứa giá trị nào thay đổi theo slot/tour/thời gian (`tour_id`, `slot_id`, timestamp, run_id).

**Shipped, PR #303 merged (`3549f28`), Deploy Dev green, ECS task def confirmed post-deploy.**

**STEP0 (per the build-prompt's own directive for this issue)**: confirmed AA-518 (3-account per-stage LLM config) did **NOT** resolve this — it changed model/role routing, not the satellite request-body construction where the real bug lives.

**STEP0 also found the issue's own title hypothesis is wrong** (already flagged unconfirmed in the 25/07 comment / ADR-2026-034 — not a Bedrock cross-account platform limitation). Confirmed via direct code read, 2 concrete local bugs, nothing to do with cross-account IAM/STS:
1. **Request side** (`bedrock_satellite.py::invoke_claude()`): `system` was sent as a plain string. Bedrock's Anthropic-compatible InvokeModel body supports the same `cache_control` content-block contract as the direct Anthropic API — a plain string is valid shape too, but Bedrock silently never caches it, no error. Fixed: reuses `build_cached_system_prompt()`, the same helper the acc2-native T1 path already uses.
2. **Response side** (`client.py::_call_bedrock_satellite()`): never read `cache_read_input_tokens`/`cache_creation_input_tokens` from the satellite response's `usage` dict at all — always defaulted to 0 regardless of what Bedrock returned.

**Real live DB evidence (pre-fix)**: 51/51 most recent `generated_content` rows with a `cache_read_tokens` key show `cache_read=0, cache_write=0` **and** `model_used LIKE 'satellite-%'` — confirms this affects current real production traffic broadly (T2/S1 rewrite), not a narrow legacy N7 corner the 25/07 comment's "$4/month" estimate was scoped to (that estimate predates T7-T11/AA-449 existing).

**Testing**: 4 new unit tests (mocked Bedrock, confirm the real request body now carries a `cache_control`-bearing content block and the response now extracts real cache stats), full `tests/unit/` suite (1839) passes, 0 regressions, flake8 clean.

**Real live-verify, post-deploy — honest result, found a SECOND real gap**: triggered a genuine `POST /admin/run-tour` rewrite through the deployed API (real tour, real Bedrock Haiku satellite call, `model_used: "satellite-haiku-4-5"`) — the resulting `generated_content.metadata` still showed `cache_read=0, cache_write=0`. Investigated why (not just accepted it): the actual system prompt for this call (`SYSTEM_PROMPT` + language note, unbranded tenant) is ~764 estimated tokens; even the LONGEST real tenant brand `system_prompt` in the live DB today is only ~325 estimated tokens on top of that (~1090 total) — checked all 3 active branded tenants. Anthropic's Bedrock prompt caching has a **minimum cacheable-prefix length** (this is H4 from ADR-2026-034, not this fix's bug) — Claude Haiku's threshold is higher than Sonnet's, and the real current S1 system prompt is very likely under it for most/all real tenants today. So: **the wiring fix is real and unit-verified correct** (request now correctly shaped, response now correctly extracted), but this session's live call could not produce a genuine non-zero cache-write because the real prompt content is too short to qualify for caching at all — a separate, pre-existing, unaddressed constraint. Flagging this transparently rather than claiming a false positive.

**Recommendation for a real follow-up** (not built here, out of this fix's scope): if caching's $ value is still wanted, the system prompt needs a fatter, genuinely static prefix (e.g., folding `acp_output_rules`/brand rubric more fully into the cached block) to clear the minimum-length threshold — or scope caching to Sonnet-tier calls specifically (1024-token threshold vs Haiku's higher one) where the existing prompt is closer to qualifying.

No migration, no infra change. Full detail: `docs/implementation-notes/AA-324.md` (note: its "Should know" section's live-verify claim was written before this final check completed — the Linear comment above is the accurate, final record). Not setting Done.
