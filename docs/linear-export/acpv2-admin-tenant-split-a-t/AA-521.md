## Shipped + live-verified (04/09/2026)

**PR #295 merged** (`cdd5f2c`), CI green (5/5 required checks), deployed (ECS Dev + Lambda). Frontend on Vercel prod (auto-deploy on `main` push).

### Build
- New `POST /api/auth/admin-logout` route — mirrors AA-427's `/api/auth/tenant-logout` exactly: clears `cis_admin_token` (httpOnly, the real JWT) + `cis_role`/`cis_user`/`cis_api_token` via `cookies().set(name, "", {maxAge:0})`.
- `AdminSidebar.tsx`'s `logout()` now calls it (async, best-effort) before redirecting to `/login`.
- **Scope widened beyond the literal issue text**: `(internal)/_components/InternalSidebar.tsx` had the byte-identical bug — reviewer-role sessions (`/upload`, `/review`, `/catalog`, `/brand`) go through the same `/auth/admin-login` JWT flow and carry the same `cis_admin_token` cookie. Fixed both call sites with the same route, otherwise the exact same vulnerability would've stayed open via that entry point.

### Live verify (real HTTP, real backend, real DB — not `/health`)
Vercel preview is SSO-gated (can't curl it directly), so verified the same way AA-435 did: built `main` post-merge locally, ran it as a real production server pointed at the real `API_URL`. Created one temp real admin row in `shared.admin_users` (bcrypt) via the standard S3-mediated ECS exec pattern — deleted after, along with the S3-staged scripts.

Real login (`POST /api/auth/login` → real 200, real httpOnly `Set-Cookie: cis_admin_token=...`) both times, `cis_role=admin` added to the jar to reproduce what `login/page.tsx` does client-side:

- **Cookie state matching the pre-fix logout** (only `cis_role` removed, `cis_admin_token` left alone — all the old client-only clear could ever do): `GET /admin/dashboard` → **200** even after "logout," once `cis_role` is present again. Confirms the bug exactly as described — the real session survives logout.
- **Real `POST /api/auth/admin-logout`**: response carries 4 `Set-Cookie: ...=; Max-Age=0` headers, jar empty after. Re-adding `cis_role=admin` post-logout → `GET /admin/dashboard` → **307 → /login**. `cis_admin_token` is genuinely gone from the browser's cookie store this time, not just the display cookie.
- `POST /api/auth/admin-logout` also confirmed live on the actual prod domain (`aa-cis.lumiguides.it.com` → 200, real `Set-Cookie` headers).

Full trace: `docs/implementation-notes/AA-521.md`.

### Known, disclosed limitation (unchanged, out of scope here)
No server-side JWT revocation list was added. A JWT copied out of the browser before logout (e.g. replayed directly via curl, bypassing the browser entirely) stays cryptographically valid until its natural 24h expiry regardless of this fix — this closes the "same browser after clicking Logout" vector the issue described, not a stolen-token-replay vector. Would need a revocation table; not asked for here.
