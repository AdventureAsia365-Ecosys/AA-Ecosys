# AA-342 — [Platform] Rà soát ngược: cơ chế ghi trạng thái đã đánh Done nhưng chưa từng persist thật (ADR-2026-037)

## Vì sao có issue này

ADR-2026-037 (29/07/2026, S128). Trong 1 phiên phát hiện **4 cơ chế ghi trạng thái được thiết kế, build, đánh Done — nhưng chưa từng ghi được gì xuống DB thật**:

| Cơ chế | Thực tế trong DB | Phát hiện |
| -- | -- | -- |
| `raw_tours.review_status` | Không UI nào gọi `POST /v1/s0/approve`, 791/793 row kẹt `pending_review` | [AA-316](https://linear.app/aa-ecosys/issue/AA-316/acp2-n0-sua-v-trip-registry-bo-review-statusapproved-chet-khong-co-ui) |
| Gate B QuarterPlan | Duyệt xong mất theo run, không persist | [AA-320](https://linear.app/aa-ecosys/issue/AA-320/acp2-n5n6-persist-quarterplan-gate-b-that-quarter-plan-quarter-plan) |
| `silver_aa_internal.tour_content_versions` (ADR-016) | Schema đủ, code INSERT/UPDATE có (`v1_s1.py:181/211`), **0 row từ trước tới nay** | S128 |
| `s1_from_atom` output ([AA-306](https://linear.app/aa-ecosys/issue/AA-306/acp2-n2b-s1-from-atom-thay-s1-rewrite-tu-do-bang-lap-rap-tu-atom)) | `_log_run` chỉ INSERT metric, **không có cột content** — nội dung chỉ nằm trong HTTP response rồi mất | S128 |

Cả 4 đều có code đúng và test pass. Cái thiếu là **chưa ai gọi nó trên production rồi kiểm DB**.

Hệ quả đã xảy ra thật: đề xuất sinh hàng loạt 763 tour (S128) dựa trên giả định *"nhiều bản nhưng chỉ 1 bản active cho B2B thấy"* — giả định đó sai, bảng version rỗng. Đã hoãn sau khi phát hiện.

## Phạm vi — rà soát ngược

**Xác định trước:** liệt kê mọi cơ chế **ghi trạng thái** (gate / version / approval / output persist / audit) đã đánh Done trong AA-CIS-App, AA-ACP-App, AA-ACP-Core. Không rà cơ chế thuần tính toán không ghi DB.

**Với từng cơ chế, kiểm đủ 3 điều (theo ADR-2026-037):**

1. Query đếm trên DB thật → **> 0 row** ở đúng bảng/cột nó phải ghi
2. Ít nhất 1 row đọc tay được, dán nguyên nội dung — chứng minh dữ liệu có nghĩa, không phải row rỗng
3. **Đường đọc ra**: VIEW / endpoint / UI nào thật sự đọc dữ liệu đó. Có ghi mà không ai đọc = gate chết (đúng ca `review_status`)

**Phân loại kết quả 3 nhóm:** ✅ hoạt động thật · ⚠️ có ghi nhưng không ai đọc · 🔴 chưa từng ghi.

## Ứng viên đã biết cần kiểm (không giới hạn ở đây)

* `pipeline_runs`, `quality_scores`, `generated_content.fix_pass_fields`
* `acp_shared.acp_output_rules` — cơ chế Data Flywheel, có row thật không hay cũng rỗng
* `audit_log` (thiết kế 7 năm retention)
* `webhook_deliveries` — đã biết = 0 trong CIS production, ghi trong tech debt registry
* `gold_aa_internal.tenant_tour_versions` — **đã verify hoạt động thật** (10 row, 7 tour), giữ làm ví dụ đối chứng
* Mọi bảng `acp_*` sinh ra bởi N0–N8
* Code path S1 thứ ba `api/routers/v1_s1.py` (`/acp/s1`, dựa `acpcore`) — ghi vào `tour_content_versions` đang 0 row ⇒ **path này chưa từng được gọi thật, có thể là code chết trong production**

## Phần thứ hai — chặn tái phát

Đề xuất cơ chế để lỗi này không tự tái sản xuất. Ít nhất một trong:

* Mục bắt buộc trong Definition of Done của Linear issue thuộc loại này
* Query kiểm persist chạy định kỳ, cảnh báo khi bảng lẽ ra phải có dữ liệu mà đếm = 0
* Bổ sung vào checklist review PR

Trình phương án, **không tự implement** khi chưa có xác nhận của Nghiep.

## Ràng buộc

* Bước rà soát là **READ-ONLY**. Không sửa code, không migration, không tự vá cơ chế nào phát hiện hỏng — mỗi cái hỏng ghi thành phát hiện riêng để Nghiep xếp ưu tiên.
* Không gọi LLM.
* Không tự đóng bất kỳ issue nào dựa trên kết quả rà soát.
* Nếu số lượng cơ chế cần kiểm quá lớn cho 1 lượt, chia đợt và báo, không làm ẩu cho hết.

## Done when

* Có bảng đầy đủ: cơ chế · bảng/cột · số row thật · đường đọc ra · phân loại 3 nhóm
* Mỗi ca 🔴 và ⚠️ có bằng chứng query dán kèm
* Có đề xuất cơ chế chặn tái phát
