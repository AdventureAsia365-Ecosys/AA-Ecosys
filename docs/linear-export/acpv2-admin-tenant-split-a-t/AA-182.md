# AA-182 — [CIS] Verify aa-cis-dev-pipeline SM works → migrate CIS to SM or retire it (currently ECS-direct)

## Goal

Verify whether the CIS Step Functions state machine `aa-cis-dev-pipeline` actually works, and decide: migrate CIS rewrite to use it, OR formally retire it and keep the ECS-direct path.

## Background (from [AA-174](https://linear.app/aa-ecosys/issue/AA-174/investigation-acp-e2e-attempt-discovered-s1s42-pipeline-is-not))

CIS content rewrite currently runs **directly in ECS/FastAPI** via `_rewrite_tour()` (`api/routers/v1_pipeline.py`), invoked from `admin_pipeline.py` + `v1_tours.py`. This is the path that produced the 32 published tours in `gold_aa_internal.published_tours`.

Meanwhile SM `aa-cis-dev-pipeline` exists (SEOIntelligence→ContentGeneration→Validation→CheckQualityScore→HITLWait→Export) and `v1_pipeline.py:302` + `services/ingestion/handler.py:257` contain `start_execution` calls into it — but **all 83 historical executions FAILED** (\~0.05s, same `States.ReferencePathConflict` family). The SM has never run successfully.

This is a latent inconsistency: two rewrite paths (ECS-direct used in prod, SM unused/broken). Nghiep wants it resolved so CIS uses one correct, working path rather than the current ambiguous state.

## Tasks

- [ ] Run a clean test execution of `aa-cis-dev-pipeline` with CORRECT input shape `{"tours":[{...}]}` (the SM expects ItemsPath `$.tours` array). Confirm whether the iterator stages (seo/content/validation/export Lambdas) actually succeed end-to-end.
- [ ] If it works: evaluate migrating CIS rewrite from ECS-direct `_rewrite_tour` to the SM (benefits: retry, X-Ray, HITL waitForTaskToken, observability). Cost/latency trade-off vs current ECS path.
- [ ] If it does NOT work or isn't worth migrating: formally retire the SM + remove dead `start_execution` calls in `v1_pipeline.py` / `ingestion/handler.py` to eliminate the broken path and confusion.
- [ ] Document decision as ADR (CIS rewrite orchestration: ECS-direct vs SM).
- [ ] Clean up 83 failed executions noise / confirm whether `STEP_FUNCTIONS_ARN` should even be set for the CIS API task.

## Note

This is CIS scope, separate from ACP orchestration ([AA-180](https://linear.app/aa-ecosys/issue/AA-180/epic-acp-pipeline-orchestration-s1s42-stage-runners-eventbridge-chain)). The CIS SM is a CIS concern; ACP needs its own orchestration regardless of this outcome. But the input-shape lesson is shared: the same `STEP_FUNCTIONS_ARN` env var is (mis)used by both CIS and ACP S1 — decoupling them is part of the fix.

**DECISION SCOPING (added 12/06, session 60):** Decide CIS rewrite orchestration — keep ECS-direct vs migrate to SM — as a standalone ADR. This does NOT block [AA-183](https://linear.app/aa-ecosys/issue/AA-183/acp-orch-1-s1-acp-entry-runner-stop-calling-cis-sm-build-correct-s1) (B2B S1). [AA-183](https://linear.app/aa-ecosys/issue/AA-183/acp-orch-1-s1-acp-entry-runner-stop-calling-cis-sm-build-correct-s1) is a Lambda per ADR-2026-013 and its B2B event-driven chain is independent of whether CIS internal rewrite runs on ECS or SM. Do [AA-182](https://linear.app/aa-ecosys/issue/AA-182/cis-verify-aa-cis-dev-pipeline-sm-works-migrate-cis-to-sm-or-retire-it) after the [AA-180](https://linear.app/aa-ecosys/issue/AA-180/epic-acp-pipeline-orchestration-s1s42-stage-runners-eventbridge-chain) critical path; it is "house-cleaning" for the CIS internal flow only.
