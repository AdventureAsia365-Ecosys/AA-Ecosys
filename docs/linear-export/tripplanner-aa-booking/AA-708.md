The marketing photos already exist in Google Drive, linked from the Jira CON board's PHOTOS column (CON-18 Korea, 19 Mongolia, 24 China, 28 Taiwan, 30 Philippines, 31 Laos, 32 Bhutan, 36 Sri Lanka). Layout seen on 01/10/2026: **country folder → one folder per tour → images named by place** (e.g. `Olkhon Island1.jpeg`).

## Proposed design (to approve before build)

1. **Access** — a GCP service account with Drive API read-only; the CON photo folders (or their parent) shared with it as Viewer. Key in Secrets Manager `aa-cis/dev/gdrive-photo-reader`. (The Claude Drive connector only sees files someone opened, so it cannot enumerate.)
2. **Job kind** `photo_sync` in the CIS job runner (CIS owns `shared.*`): walks country → tour folder → images, incremental by Drive file id + modifiedTime; downloads, makes web sizes (1600w + 600w WebP), uploads to S3 `photos/<country>/<tour>/<file>`; served through CloudFront (Infra).
3. **Table** `shared.place_photo` (migration): drive_file_id (unique), country, tour folder name, matched `raw_tours.tour_id` (folder name ↔ tour name), place label (file name without digits/extension), matched `shared.destinations.id` (label ↔ destination name within the country; ambiguous → unmatched), S3 keys, size, sha256, credit, status (matched / unmatched / rejected).
4. **Use** — fill `shared.destinations.cover_image_url` from the best matched photo; atom media and tour cover next.
5. **Admin page "Photos"** — coverage per country/place, unmatched queue with manual assign (observability rule).

## Cost

S3 + CloudFront only (no model calls). A vision model for ambiguous matches is optional, later.

- `POST /admin/photos/sync/schedule` (admin secret) enqueues one incremental `photo_sync` job per day.

- The admin Photos page shows the last scheduled run.
