## Problem

Only 2 of 892 Booking trip plans can be sold with a price today (`GET /booking/catalog/price-readiness`: 890 `no_components`). The cause is missing data, and entering that data is slow:

* each tour needs its day-by-day components (hotel and room type, services), its supplier contract rates, a pricing rule, the sellable switch and departures;
* every one of these is a separate form or PUT, one tour at a time;
* nothing maps the CIS itinerary (which already names the hotels, meals, transfers and guides per day) to Booking components;
* the CIS reference price is free text (`raw_tours.price_raw`) and feeds nothing; 281 live tours have none.

The tech lead (S278) wants everything ready so the customer-service team can enter prices in Booking and CIS easily and quickly.

## Scope

**Booking (staff app)**

1. **Price setup workbench:** one page listing every trip plan with its readiness: components, rates in force, rule, sellable, departures, price. It has filters (country, readiness state, missing item), and each row says the next step.
2. **Components suggested from the CIS itinerary:** per day, match the hotel and room type and the services to existing `HTL-` / `SVC-` codes. Staff accept, edit or reject each suggestion. Nothing is applied without a click. Unmatched items are listed so the supplier can be created.
3. **Bulk Excel import with a DRY RUN:**
   * one template for many tours: components per day, sellable, hand prices per pax band and season, departures;
   * row-level validation and errors;
   * maker-checker where today's single forms have it.
4. **Provisional price from the CIS reference price:** optional per tour, clearly flagged "no supplier price yet". It is never quoted to agencies as a contract price; only the RRP display uses it.

**CIS**

5. **Structured reference price:** amount, currency and basis, parsed from `price_raw`, with bulk edit and an Excel export/import in admin. The text is kept for audit.
6. **Staff access:** a CIS Staff page grant of the Booking roles the team needs (`booking-contracting` / pricing) to a customer-service staff member, so no engineer is needed.

**Both:** a short how-to guide for the team in docs (EN + `.vi.md`), and EN UI with VI.

### 2026-11-12 03:31 — nghiep pham quoc

Scope addition (tech lead, S278): **price versions**. Every price the customer-service team enters or changes is a version, not an overwrite. This covers supplier rates, hand prices per season and pax band, pricing rules, and provisional prices.

Each version records:
- its validity window (valid from / to, travel dates vs booking dates);
- the season it belongs to;
- who entered it and who approved it (maker-checker);
- a reason;
- a diff to the version before.

How versions are used:
- Quotes and agency tariffs pin the version they were priced on.
- A booked or quoted trip never changes price when a new version is published; re-quoting is an explicit action.
- The workbench shows the version history per tour and what changes for which future departures.
- Export and import carry the version.

Pending: an industry-practice review (seasons, contracting cycles, rate validity, release and stop-sale, net vs commissionable) will refine this before the lane builds versions.
