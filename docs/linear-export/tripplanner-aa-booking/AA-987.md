## Problem

[AA-986](https://linear.app/aa-ecosys/issue/AA-986/tour-retirement-propagation-a-tour-deleted-at-s0a0-hides-every) E2E (S248, 23/10): the backend refuses a retired tour at once, but TripPlanner's public site lags by up to 30 min:

* The tour page keeps answering 200 until the per-instance retired-suffix list refreshes (`frontend/lib/goneTours.ts`, `GONE_TTL_MS` = 30 min). Measured: retire at 14:33:41 UTC, page 410 at \~14:49.
* The browse list is served from the Vercel CDN with `cache-control: public, max-age=1800`. Measured: the tour left the list at 15:03 UTC.
* The same lag applies in reverse after a restore.

Nghiệp approved fixing this (S248 decision page, card e06: "Tạo issue và làm ngay").

## Scope

1. CIS: when `services/tour_lifecycle` records a served-state change (retire / pause / restore), notify TripPlanner. Options, pick in the PR:
   * a signed webhook to a TripPlanner revalidate route (secret in Secrets Manager); or
   * TripPlanner polls `catalog.v_tour_lifecycle_outbox` by `event_id` cursor every minute.
2. TripPlanner: on a lifecycle event, refresh the retired-suffix cache and revalidate the tour page and its country's browse list (on-demand revalidate / cache tag purge).
3. Idempotent and safe on replay; a failed purge only falls back to today's 30-min bound.

## Done when

* On Dev, retire a synthetic tour: the public TripPlanner tour page answers 410 and the browse list drops it within 2 minutes. Restore: back within 2 minutes.
* Tests cover the event → purge path and the replay case. No new AWS cost beyond the existing services (state it in the PR if not).

Refs [AA-986](https://linear.app/aa-ecosys/issue/AA-986/tour-retirement-propagation-a-tour-deleted-at-s0a0-hides-every) (ADR 0015).
