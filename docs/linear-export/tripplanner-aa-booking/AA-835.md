## Problem

ADR 0004a (hybrid supply content) splits hotel and activity data between two apps:

* **Booking** owns the supply facts and the rates.
* **CIS** writes the customer-facing description, highlights and photos.

[AA-823](https://linear.app/aa-ecosys/issue/AA-823/aaa-wave-2b-hotels-services-supply-records-per-adr-0004a-bk-010-api) (bk-010) shipped only the Booking side: `booking.hotels`, `hotel_room_types`, `services` and `supplier_rates`. These tables deliberately have no customer-facing columns.

Nothing yet sends those facts to CIS or brings the published content back to Booking. So Booking proposals cannot show the same published hotel and activity text that TripPlanner and tenant sites show.

The ADR's "Follow-ups" section still says "no Linear issue created yet", and `apps/AA-Booking/CONTEXT.md` lists this work as "own issue".

## Scope

Build in the cross-repo order set by the ADR: Booking `bk-NNN` → CIS migration → CIS consumer → Booking UI read-back.

**Contracts (root repo)**

* Add `docs/contracts/supply.hotel.v1.json` and `supply.service.v1.json`. They carry facts only, never net rates or internal notes.
* Add both to `docs/contracts/README.md`.

**Booking** `bk-NNN`

* A supply outbox emits `supply.hotel.*` / `supply.service.*` events with a monotonic `supply_version`.
* `v_supply_*` views expose only the supply contracts. The CIS reader gets SELECT on these views only, so customer and payment events never reach CIS.
* A material change bumps `supply_version`. Deactivating a hotel or service emits an event.

`docs/database/schema-ownership.md`

* Add rows for the new views.

**CIS migration + consumer job (**`shared.job`**)**

* Idempotent upsert keyed by (`source_system='booking'`, `source_id`).
* A `supply_version` ordering check, so an older event never overwrites newer content.
* Supply facts are treated as untrusted LLM input.
* The job produces a draft that a human must review.
* A material change marks the content `stale`.
* Human edits are never silently overwritten; the reviewer sees a diff.
* Deactivate unpublishes the content.
* LLM calls go through `LLMClient` with cost logged. Paid runs follow the subset rule.

**CIS read-back view**

* A view such as `shared.v_supply_content` with:
  * description, highlights, photo URLs;
  * `content_status`, `content_version`;
  * an edit URL.
* SELECT granted to role `booking`.

**Booking UI**

* Hotel and service detail pages show the CIS content read-only, with an "Edit in CIS" link.
* Proposals read only `published` rows.

`entity_media`

* A Booking-owned S3 prefix that CIS can read.
* Media passed as ids.
* A usage-rights flag that gates publishing.

Out of scope: running CIS as a non-owner role ([AA-817](https://linear.app/aa-ecosys/issue/AA-817/security-cis-api-runtime-role-aa-cis-admin-is-not-filtered-by-rls)).

## Done when

* **Schema and contracts.** Both contracts, the README entries and the ownership rows are merged. The Booking `bk-NNN` and CIS migrations are applied on Dev through DB Migrate.
* **Create and publish.** On Dev, a hotel created in Booking produces a CIS draft within one job run. After a reviewer approves it, `v_supply_content` returns it as `published`. The Booking hotel detail page shows the content read-only, with a working "Edit in CIS" link. Screenshots on desktop and mobile.
* **Change handling.**
  * Renaming the hotel marks the content `stale` and queues a new draft.
  * Replaying an older event changes nothing.
  * Deactivating the hotel unpublishes the content.
* **Proposals.** A proposal shows only published text. A hotel whose content is draft or stale shows no description.
* **Media rights.** A photo without the usage-rights flag is not published. With the flag, it appears in the read-back.
* **Ship.** CI is green; api, worker and Booking are deployed; evidence is posted here.
