# AA-673 — [TripPlanner] Tour Graph read model — destinations, within-tour day adjacency, cross-tour junctions (from CIS published tours)

## Why

Nghiệp (28/09): suggestions must follow the routes and itineraries of **tours we actually have**, so every trip can become a bookable Trip Case. Combining **several tours** is allowed.

Today, `backend/assembly/suggestions.py` ranks the next place by 0.6 × taste + 0.4 × distance. It checks only that the country is already in the trip, never tour coverage.

## Data available

* `tripplanner.itinerary_components`: `source_tour_id`, `source_day_index`, `destination_id`, activity, intensity, duration hint, embedding.
* `shared.destinations`: name, country, lat/lng.
* CIS `acp_contract.route`: 2–5-day spans.

## Model — schema `tripplanner`, rebuilt by a job after each CIS rerun wave

* **Node** = destination, with its activities, intensity range, seasons, and the list of tours visiting it.
* **Leg** = a contiguous day-span of one tour, `(tour_id, day_from, day_to, destinations[])`. This is the unit an advisor can actually sell.
* **Edge (within-tour)** = consecutive days in the same tour, weighted by the number of tours sharing that step.
* **Junction (cross-tour)** = tour A's destination at day *i* and tour B's destination at day *j* are the same destination, or within a transfer threshold (km/hours; default: same destination or ≤ 150 km, tunable). This is where two legs can be chained.

Output tables: `tour_graph_node`, `tour_graph_edge`, `tour_leg`, `tour_junction`, with indexes for neighbour lookups.

## Done when

The graph is built for the current published set, and stats are reported: nodes, edges, legs, junctions per country. A sample query "neighbours of Paro that keep the trip coverable" returns in under 50 ms.
