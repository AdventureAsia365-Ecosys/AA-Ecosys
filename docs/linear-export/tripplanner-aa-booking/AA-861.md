## Problem

`tripplanner.outbox.payload` keeps traveller PII (inquiry contact data) with no time limit. Data standards DM-6.6 and DM-7 set redaction after 90 days. Per ADR 0003a, each owner runs its own TTL kinds, so this must not run from the CIS worker.

## Scope

A TripPlanner-owned job kind `tp_retention_outbox_redact`, built the same way as Booking's `bk_retention_inbox_redact` (AA-Booking #23):

* rebuild the payload from an allowlist;
* keep the row, idempotency key and contract version;
* DRY RUN by default;
* counts in the job result;
* first real run per destructive-ops.md.

Blocked until `tripplanner.job` exists (X6 / [AA-751](https://linear.app/aa-ecosys/issue/AA-751/jobs-adr-0003-nac-6-let-a-second-repo-tripplanner-aa-booking-enqueue)).

## Done when

* A DRY RUN on Dev with its counts.
* After approval, one real run: outbox rows older than 90 days carry no name, email or phone (verification query), and the outbox relay and dedupe still pass.
