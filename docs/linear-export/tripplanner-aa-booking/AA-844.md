## Problem

Split from [AA-708](https://linear.app/aa-ecosys/issue/AA-708/photos-sync-aa-marketing-photos-from-google-drive-jira-con-photos-to) (Nghiệp decision S239, 16/10). Jira PR-11 comment 10447 (01/10) promised "CloudFront, daily sync". Neither exists today (S239 read-only checks):

* `aws cloudfront list-distributions` on acc2 returns null. AA-CIS-Infra main has no `aws_cloudfront_distribution`.
* `/content/photos/{id}` (`api/routers/admin_photos.py`) returns a 302 to a presigned S3 URL that expires after 1 hour.
* AA-CIS-App main has no photo-sync schedule endpoint. `photo_sync` runs only from the admin Photos button.

## Scope

1. **infra/AA-CIS-Infra**: CloudFront distribution with OAC on the `photos/` prefix of the photos bucket; ACM cert in us-east-1 for a [lumiguides.it.com](<http://lumiguides.it.com>) host (e.g. `img.lumiguides.it.com`) + DNS record; long TTLs (WebP keys never change); bucket stays private, policy allows only the OAC.
2. **apps/AA-CIS-App** `api/routers/admin_photos.py`: `/content/photos/{id}` redirects to the CloudFront URL instead of a presigned URL; stored URLs keep working. Catalog / TripPlanner photo URLs (catalog.v_tour `cover_photo_path`, v_tour_photo, v_destination_photo consumers) resolve to the CloudFront host.
3. **apps/AA-CIS-App**: `POST /admin/photos/sync/schedule` (admin secret) enqueues one incremental `photo_sync` job per country per day; skips when a `photo_sync` job is already queued or running. Admin Photos page shows the last scheduled run.
4. **infra/AA-CIS-Infra** ops-probe Lambda: call the schedule endpoint daily, same pattern as the [AA-825](https://linear.app/aa-ecosys/issue/AA-825/data-retention-rollups-for-log-tables-llm-call-log-180-d-daily-rollup) retention schedule.

Out of scope: Laos (CON-31) sync, photo usage rights / credit (product questions), destination cover backfill.

## Done when

* Photos are served via CloudFront on Dev: `curl -I` on a cover image through the CloudFront host returns 200, and a repeat request returns `x-cache: Hit from cloudfront` with the long `cache-control` header.

* `shared.job` shows a scheduler-created `photo_sync` run (schedule target invoked with the schedule's own input) that succeeded with 0 errors. (Changed S246: Dev has no real traffic, so no multi-day watch — owner rule "Dev: no waiting"; the nightly 21:00 UTC schedule keeps running.)
