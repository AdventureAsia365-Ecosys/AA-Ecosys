# AA-830 — [TripPlanner → AA-Booking] Tour key fix (X3): inquiry.submitted v1.2 with source_system + source_id per leg, trip_case_legs key columns, backfill, contracts registry

## Problem

TripPlanner hands inquiries to AA-Booking with `inquiry.submitted` v1.1. Each leg carries only `source_tour_id`. Historically that field has held either the stable catalog key (`source_id` = `COALESCE(raw_tours.source_group_id, tour_id)`) or a version `tour_id`. `booking.trip_case_legs` (bk-002) stores only `source_tour_id TEXT`.

After a CIS re-upload, the version `tour_id` changes, so a trip case leg can silently point at a superseded or dead tour. Nothing can check this, because legs have no `(source_system, source_id)` pair to compare with `catalog.v_tour`.

* Nghiệp approved decision E7 in S237 (additive v1.2).
* The fix is cheapest now, while Booking has only a few trip cases on Dev.
* The DM-4.2 orphan-rate check waits on these columns.
* The work has no Linear home today. The roadmap lists it only as "related [AA-679](https://linear.app/aa-ecosys/issue/AA-679/aaa-catalog-sync-from-cis-templates-activities-destinations-via)", and [AA-679](https://linear.app/aa-ecosys/issue/AA-679/aaa-catalog-sync-from-cis-templates-activities-destinations-via) is close to Done with a different scope.

## Scope

**Contract.** Add `docs/contracts/inquiry.submitted.v1.2.json`, additive over v1.1:

* Each leg gains `source_system` (`cis`) and `source_id` (the catalog key, text).
* `source_tour_id` is kept for compatibility.
* Consumers must accept 1, 1.1 and 1.2.

**TripPlanner.** `backend/assembly/handoff.py` resolves each leg to the catalog key through `catalog.v_tour`:

* It accepts either key type.
* It emits `source_system` + `source_id`.
* It sets `SCHEMA_VERSION = 1.2`.

**AA-Booking.**

* Add migration `bk-NNN` with `source_system` / `source_id` on `booking.trip_case_legs`, nullable, then backfilled.
* `bk_inquiry_process` validates v1.2 and fills the new columns.
* For a v1/v1.1 payload, it resolves `source_tour_id` against `catalog.v_tour`.

**Backfill.** A one-off, re-runnable backfill of existing TripPlanner drafts/outbox rows and Booking legs:

* It matches both key types (`source_group_id` or `tour_id`).
* Run it as a DRY RUN first and report the unmatched rows.

**Docs.**

* Update the `docs/contracts/README.md` registry: add the v1.2 row, mark CIS 225/228 as applied, and mark the tp-009 grant as done.
* The glossary in `02-data-management.md` §3.3 already exists. Adjust it only if wording changes.

**Orphan check.** Then enable the DM-4.2 orphan query in the nightly dump: legs whose `(source_system, source_id)` is not in `catalog.v_tour`.

## Done when

* `docs/contracts/inquiry.submitted.v1.2.json` is merged, and the registry rows for v1.2, 225, 228 and tp-009 are current.
* A live "Send to advisor" on Dev produces an outbox row with `version` 1.2. Every leg in it has `source_system = 'cis'` and a `source_id` present in `catalog.v_tour`.
* Booking processes that row:
  * The resulting `booking.trip_case_legs` rows have non-null `source_system` / `source_id`.
  * `/booking/health` shows the new `bk-NNN`.
* After the backfill, every existing Dev trip case leg either has the key columns filled or appears as unmatched in the DRY RUN report.
* The orphan-rate query returns 0, or a listed count, for `booking.trip_case_legs` against `catalog.v_tour`.
