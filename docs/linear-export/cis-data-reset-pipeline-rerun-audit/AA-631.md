# AA-631 — [Enhancement] Debate stage for Slate — contested metric + brand-fit filter before tenant sees candidates

## Context

Follow-up from [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu) (rank-sum 4-axis, Done). While investigating gaps against Ms. Thư's full model (`aa-social-media`), found a "Debate stage" (`src/aa_social/stages/slate_debate.py`, ADR-0025) that [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu)'s scope deliberately did not cover — Debate is a judgement mechanism (LLM-based cut), not a rank-sum axis, and [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu)'s own description was explicit: "rank-sum, deterministic, KHÔNG LLM". Tracked as a separate issue per that scope boundary, not folded into [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu).

## What Debate does in the origin (Ms. Thư)

4 standards a Segment/Route can be cut on, AFTER rank-sum has already ranked it, BEFORE it reaches the tenant:

1. **only here** — `contested` (SERP-domain share by "claims-everything" aggregator domains, e.g. Wikipedia/TripAdvisor) near 1.0 means "every operator has already written this" — cut unless the itinerary does something distinctive.
2. **enough to say** — `said` (already ported, [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu) Sub 1) reused as cut evidence, not just a rank axis.
3. **not already on slate** — two Subjects on the same Channel claiming the same place/keyword; cut the weaker one.
4. **sounds like this operator** — Brand Identity fit (Critic reads the tenant's Brand Identity document).

Origin mechanism: 1 Critic LLM call + 1 Judge LLM call over the WHOLE slate (not per-Segment), returns a `Ruling` (accept/change/cut) per segment_id, capped at "never cut more than half a Channel's list in one run" (safety rail). Debate is explicitly advisory: any failure/malformed ruling and the rules-based list stands unchanged — this stage must never be able to make the Slate empty by erroring.

## Where this fits in AA-CIS-App today (traced end-to-end, see `services/acp_shared/slate.py`)

```
atom (per-tour) → Segment/Route (platform-wide, AA-545)
  → atom_ranking (platform-wide rank-sum, AA-610)
  → [per-tenant boundary starts here]
  → _fetch_segment_candidates() / _fetch_route_candidates()  (slate.py — scope to tenant's own tours+markets)
  → _choose()  (existing filter: Bar thresholds + place de-dup + most_per_hub — SEO-signal only, no brand/contested check)
  → acp_shared.subject (state: proposed → picked → used/cut)
  → tenant manually picks 1 via UI
```

`_choose()` already does part of standard #3 ("not already on slate" — place de-dup within one Channel) — nothing currently does #1/#2/#4.

Debate's insertion point: between candidate-fetch and `_choose()`, inside `propose_slate()` (`services/acp_shared/slate.py`) — the earliest point data is per-tenant (tenant_id, markets known) but not yet narrowed by Bar/hub-cap.

## Design decision: Hybrid architecture (Nghiệp approved, not the origin's literal Critic+Judge mechanism)

Rejected: porting Ms. Thư's Critic+Judge verbatim — `propose_slate()` runs on EVERY `GET /v1/slate` (not on a schedule), so 2 LLM calls per page view would repeat the exact performance mistake [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu) Sub 2 made before its scope fix (PR [AdventureAsia365-Ecosys/AA-CIS-App#420](https://linear.app/aa-ecosys/review/aa-610-sub-2-scope-fix-scope-paa-landing-to-the-triggering-tours-fd320dc2ddec)) — recomputing real signal on every read instead of caching what hasn't changed.

Chosen instead — split by whether the signal is measurable or a judgement call:

`contested` **— deterministic, no LLM.** SERP-domain data is already being fetched today for PAA/related-searches (`services/seo_intelligence/dataforseo_client.py::_serp_advanced()`, endpoint `serp/google/organic/live/advanced`) — the response's `organic` items (domain per rank position) are currently parsed away. No new DFS cost: same call already being made, just also read the field. Cached per Segment (persisted column, same cache pattern as [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu)'s `atom_segment.questions_count` — migration 163), applied as a simple threshold in `_choose()` (e.g. contested > 0.8 → deprioritize/flag), not an LLM judgement.

**Brand-fit — LLM, but reuse the EXISTING brand-fit judge, not a new Critic/Judge mechanism.** `services/content_generation/judge_node.py` already scores brand-fit with GPT-4.1 for T2 rewrite (reads `brand_core_idea`/`brand_customer_segment`/`brand_customer_mindset`/`brand_voice_examples`/`brand_good_examples` — same 5 fields Brand Identity already has, `shared.tenant_brand_rules`), with a guard that skips the LLM call entirely when the tenant has no brand signal set (`has_brand_signals` check). Reusing this instead of a separate Debate-specific brand check keeps ONE standard of "brand-fit" across the platform — a Segment judged brand-fit by Debate but then rejected by judge_node after writing (or vice versa) would be a real inconsistency a second, parallel LLM judgement invites.

**"not already on slate" across Channels** — no LLM needed; `_choose()`'s existing place de-dup is scoped to one Channel at a time (fresh `seen_places` per `_choose()` call) — extend to dedupe across Channels too. Small, independent of the Debate LLM question, can land separately/first.

## Trigger frequency (Nghiệp confirmed, 22/09/2026)

Cache key: `(segment_id_or_route_id, tenant_id, brand_version)`. `propose_slate()` (runs on every `GET /v1/slate`) must NEVER call the LLM for a candidate that already has a cached result under the CURRENT brand_version — only compute for what's actually new or actually changed:

| Event | LLM call? | Scope recomputed |
| -- | -- | -- |
| Tenant reopens Slate page, nothing changed | No | none |
| Tenant adds a new tour to their pool | Yes, only for that tour's Segments | new Segments only |
| An existing tour is re-atomized (new Segments appear) | Yes, only for the new Segments | new Segments only |
| Tenant edits Brand Identity (new `tenant_brand_rules.version`) | Yes, for everything currently in that tenant's candidate pool | all Segments/Routes currently candidates for that tenant |
| DFS re-harvests a keyword (`contested` input changes) | No (contested is a separate deterministic cache, not tied to brand_version) — needs its own invalidation design, see [AA-630](https://linear.app/aa-ecosys/issue/AA-630/tech-debt-questions-count-cache-aa-610-never-invalidated-when-search) for the identical problem already flagged for `questions_count` | — |

## Open design questions to resolve before building (not yet decided)

1. `contested` **data source**: new table (`acp_contract.serp_domain_result` or similar) vs. a JSONB column added to `search_demand`? Needs a migration either way — none exists yet (grepped `api/migrations/`, confirmed empty).
2. `everywhere_domains()` **scope**: platform-wide (every harvested keyword) or scoped some other way? Ms. Thư's origin computes it over the whole harvested pool — needs the same decision [AA-545](https://linear.app/aa-ecosys/issue/AA-545/archspec-redesign-segmentscoreroutehub-thanh-platform-wide-1-pr1) made for Segment/Route (platform-wide, not per-tenant) confirmed here too.
3. **Where exactly the brand-fit reuse call lives**: `judge_node.py`'s brand-fit scoring is currently embedded inside the T2 rewrite LangGraph (`content_generation/graph.py`) — needs to be callable standalone from `slate.py` (extract into a shared function both call, not a copy-paste fork).
4. **Threshold for** `contested`: 0.8 is illustrative from this discussion, not researched — needs a real number decided the same way `CHANNEL_BARS` was (Ms. Thư's own `reference/*.toml`, if it has one for this) rather than invented.
5. **Safety rail equivalent**: origin caps Debate at "never cut more than half a Channel's list per run" — does the hybrid design need an equivalent cap now that `contested` is a hard threshold rather than an LLM judgement with its own restraint?

## Implementation summary

## Threshold measured against real data (not invented)
Spent ~$0.06 on 30 real DFS SERP calls (keywords already in `search_demand`) to measure `everywhere_domains()`/`contested` before shipping — see `atom_ranking.py`'s own docstring for the full distribution. Chose `CONTESTED_CUT_THRESHOLD=0.5`: a conservative floor above the entire observed range (max=0.33 in the sample) rather than a number fit to a 30-keyword single-region sample.
