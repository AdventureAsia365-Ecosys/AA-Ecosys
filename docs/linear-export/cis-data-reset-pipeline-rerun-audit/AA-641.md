## Background: how a tour rewrite is checked today

1. **Writer** (Sonnet) writes the whole tour as JSON: name, subtitle, summary, highlights, itinerary, seo_title, seo_meta. It takes about 60s and costs about $0.08 for an 18-day tour.
2. **validate_node** scores it and lists failure codes. Some codes are **hard** (`_HARD_BLOCK_CODES`: SEO length, FORBIDDEN_WORD, MISSING_FIELD). Others are soft advice (HIGHLIGHTS_TOO_GENERIC and similar).
3. **flag_fix** (Haiku, about 35s and about $0.02) is a *cheap, targeted* repair: it rewrites only the flagged **fields** (e.g. `itineraries`, `seo_meta`), not the whole tour.
4. **T3 QA** re-checks the final content. If a **hard** code remains, it re-runs the whole writer (step 1). That is the expensive step we want to avoid.

## Problem (seen live after [AA-639](https://linear.app/aa-ecosys/issue/AA-639/t2-pipeline-tour-rewrite-needs-3-full-revisions-before-passing-checks), Manaslu 18-day tour, 25/09/2026)

The first draft was good (score 9.75), with only `SEO_META_TOO_LONG`, and the itinerary was flagged for polish. flag_fix then:

* **introduced a forbidden word** while rewriting the itinerary (`FORBIDDEN_WORD` appeared *after* the fix, not before), and
* **did not bring** `seo_meta` **under the length limit** (an LLM counting characters is unreliable).

Both are hard codes, so T3 re-ran the whole writer: one extra full rewrite (about $0.08 and 60s) caused by the *repair step itself*.

## Scope

### A. Deterministic seo_meta fit (no LLM)

* Same idea as `fit_seo_title()` from [AA-639](https://linear.app/aa-ecosys/issue/AA-639/t2-pipeline-tour-rewrite-needs-3-full-revisions-before-passing-checks) ([AdventureAsia365-Ecosys/AA-CIS-App#447](https://linear.app/aa-ecosys/review/fix-t3-shortens-an-over-long-seo-title-instead-of-rewriting-the-tour-b8121507022c)).
* **Reuse the existing helpers in** `services/content_generation/seo_meta_utils.py`**.** `best_meta_candidate` / the sentence-salvage logic (AA-205/AA-239) already pick the longest complete-sentence prefix inside the band. Do **not** write a second trimmer.
* Apply the fit before T3 decides whether to rewrite, as `fit_seo_title` already does. Keep the existing rules:
  * the band is 140–155 characters;
  * it must be a complete sentence;
  * it must be forbidden-word free (AA-238 D1).
* **If no valid candidate exists** (for example a meta that is too *short*), leave it and let the existing path handle it. Never produce an invalid meta.

### B. flag_fix must not introduce forbidden words

* Pass the tenant's forbidden-word list, plus the platform list `_VALIDATE_FORBIDDEN`, into the flag_fix prompt as an explicit "never use" list.
* **Guard after the fix:** if a field returned by flag_fix contains a forbidden word that the *original* field did not contain, keep the original field value for that field (revert that field only) and log `flag_fix_introduced_forbidden`.

### Out of scope

* Changing which codes are hard or soft.
* Changing the writer prompt.
* Changing the judge.

## Risks to watch ("don't make it worse")

* Reverting a field could bring back the problem flag_fix was fixing. That is acceptable only because the original problem was **soft** or length-related. If the original field had a **hard** failure, log it and let T3 decide as it does today.
* The seo_meta fit must never shorten below 140 characters or cut mid-sentence. Reuse the band guard.

## Done when

* Unit tests:
  * a meta over 155 characters is fitted into the band, as a complete sentence;
  * a meta with no valid candidate is left untouched;
  * a flag_fix output that adds a forbidden word is reverted per field;
  * an unaffected field passes through unchanged.
* Live: 3 runs of a long tour (Manaslu, 18 days) average **≤ 1.3 writer calls**. The baseline after [AA-639](https://linear.app/aa-ecosys/issue/AA-639/t2-pipeline-tour-rewrite-needs-3-full-revisions-before-passing-checks) is 1–2. No FORBIDDEN_WORD or SEO length codes remain in the persisted content.
