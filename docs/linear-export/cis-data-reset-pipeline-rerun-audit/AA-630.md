# AA-630 — [TECH DEBT] questions_count cache (AA-610) never invalidated when search_demand/PAA data changes

## Context (found during [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu) Sub 2 scope-fix verification, PR [AdventureAsia365-Ecosys/AA-CIS-App#420](https://linear.app/aa-ecosys/review/aa-610-sub-2-scope-fix-scope-paa-landing-to-the-triggering-tours-fd320dc2ddec))

`acp_contract.atom_segment.questions_count` (migration 163) caches the last-computed PAA-landing count per Segment. It is only recomputed when a tour containing that Segment's atoms triggers `recompute_segment_score_route()` (a PATCH or an atomize run) — `precompute_question_landings()` scopes recomputation to the triggering tour's own `segment_ids`, reading every other Segment's `questions_count` back from cache instead of re-landing it (this is the fix, not a bug — it's what makes a tour-triggered recompute fast instead of scanning the whole platform every time).

## The gap

`questions_count` depends on TWO things: (1) the Segment's own atoms (tracked — a tour change always recomputes its own Segments), and (2) `acp_contract.search_demand`'s PAA data (the People-Also-Ask questions harvested via DataForSEO for a keyword). If (2) changes — DFS re-harvests a keyword and finds new/different PAA questions — no mechanism marks the Segments that keyword's PAA would land on as needing recomputation. Their `questions_count` stays whatever it was, indefinitely, until some unrelated tour change happens to touch that same Segment.

Concretely: a Segment claims keyword "Wat Phou" with `questions_count = 5` computed 3 months ago. DFS re-harvests "Wat Phou" today and finds 8 PAA questions now. Nothing re-lands them onto this Segment unless a tour containing this Segment's atoms is separately PATCHed/re-atomized for an unrelated reason. The `questions` rank-sum axis silently uses stale data.

## Why this is Low priority right now

DFS re-harvest frequency is currently low (small platform, DFS calls cost money, not run continuously) — the practical risk of a Segment's `questions_count` going meaningfully stale is low today. Flagging so it isn't forgotten if DFS harvest frequency increases later (e.g. a future scheduled re-harvest job).

## Possible fix direction (not designed yet)

Whenever `search_demand.people_also_ask` changes for a keyword (new DFS harvest write), find the Segments whose `canonical_place`/`canonical_action` would claim that keyword (same `_candidate_questions()` logic already in `atom_ranking.py`) and set their `questions_count = NULL` — the next tour-triggered recompute that scope-includes them will then recompute for real (already-existing "never computed" path treats NULL as always-recompute regardless of scope, migration 163's own comment). This ties the invalidation to the DFS write, not a separate scheduled sweep — needs design before building.
