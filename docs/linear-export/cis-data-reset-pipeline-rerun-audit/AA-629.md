## Context (found during [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu) Sub 2 investigation)

While investigating why `run_atom_ranking()` loops over a fixed 6-market list (`DFS_LOCATION_MAP`: US/UK/AU/DE/FR/NL), traced the full write/read path for tenant `target_market` and found a real bug, not a hypothetical.

## What "market" actually is

DataForSEO has no concept of "market" — it takes a `location_code` + `language_code` pair per request (1 request = 1 location, confirmed via DFS docs, `docs/claude_audit/AA-515-step0c-multimarket-schema.md` Q4). "Market" is this codebase's own 2-letter shorthand name for one such pair, defined in `services/seo_intelligence/seed_builder.py::DFS_LOCATION_MAP` (currently 6 entries).

## The bug

Tenants declare `target_market.countries` freely (JSONB column, `shared.tenant_seo_config`, no validation against any fixed list — `shared/services/tenant_config_service.py:168-198`). But when a tenant's declared country is **not** in the 6-entry `DFS_LOCATION_MAP` whitelist:

* `resolve_buyer_market()` (`seed_builder.py:152-165`) and `resolve_buyer_markets()` (`seed_builder.py:168-190`) silently fall back to **US** — no error, no warning log, no distinction from "tenant declared nothing at all" (which is the ONE case this fallback is actually meant for).
* `slate.py::_tenant_market_codes()` (lines 161-173) mirrors the same fallback when reading ranking data for that tenant.
* Net effect: the tenant reads **US market ranking data** — data about a completely different market than the one they configured — with no indication anything is wrong.

This already happened for real: tenant `exploreasia-co` (declared DE/FR/NL, all outside the map at the time) silently read US data until [AA-515](https://linear.app/aa-ecosys/issue/AA-515/rankingatom-score-stage-xep-hang-atom-djieu-kien-tien-quyet-cho-aa-510) expanded the whitelist. The fix at the time was "add the missing markets to the list," which papered over this specific case but left the underlying fallback bug in place for the *next* unmapped market.

## Root cause

`resolve_buyer_market()`/`resolve_buyer_markets()`/`_tenant_market_codes()` conflate two different situations into one fallback:

1. Tenant declared **no** countries at all → defaulting to US is a reasonable product decision.
2. Tenant declared **real** countries, all outside the current whitelist → silently substituting US data is wrong; the tenant should see "no ranking data for your market(s)," not someone else's market's data.

## Proposed fix (not yet built — investigate-first per team convention)

* Distinguish "empty input" from "non-empty input, all unmatched" in both resolvers — only case 1 keeps the US default.
* Case 2: return empty (no market resolved) instead of `[US]`/`US`, and log a warning (tenant_id + the unmapped countries) so this is visible operationally instead of only discoverable by manual audit.
* `slate.py` read path: when a tenant has zero resolved markets, the UI/API should show "no ranking data yet for this market" — not silently render US numbers as if they were the tenant's own.
* Out of scope: adding new markets to `DFS_LOCATION_MAP` — that's a cost/business decision (buying more DFS data), not part of this bug fix.

## Not to be merged with [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu) Sub 2 work

This is a behavior/correctness fix (tenant-visible data changes), separate in kind from [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu) Sub 2's performance/architecture fixes (embedding pacing, market-loop dedup, candidate capping) even though both touch the "market" area of the code. Keep as separate issue/PR so each can be reviewed and rolled back independently.

## Scope update (Nghiệp chốt) — 3-tier design, not just a silent-fallback fix

Just returning "no data" for an unmapped market still leaves the tenant stuck with no path forward. Chốt hướng xử lý đầy đủ hơn:

**Tier 1 — detect + record (fully automatic, zero cost)**

* When `resolve_buyer_market()`/`resolve_buyer_markets()` hits a country outside `DFS_LOCATION_MAP`, write a row to a new small table (e.g. `unmapped_market_requests`: tenant_id, country_code, requested_at, resolved_at) instead of only logging a warning.
* Tenant-facing message when this happens: not a bare empty state — something like "Market \[X\] chưa được platform hỗ trợ nghiên cứu SEO. Đã ghi nhận yêu cầu." so the tenant knows they were heard, not silently dropped.

**Tier 2 — admin visibility (automatic)**

* Admin UI surfaces "N tenants waiting on market X" (same pattern as [AA-627](https://linear.app/aa-ecosys/issue/AA-627/dfsops-canh-bao-so-du-dataforseo-thap-djoc-balance-1-lanngay-alert)'s DFS balance alert) — no manual DB digging needed to know demand exists for a new market.
* This also gives admin a real, data-driven way to track/manage which tenants have distinct market needs — not just a bug fix, a real operational tool.

**Tier 3 — activation (human-approved, cost gate stays manual)**

* Adding a market to `DFS_LOCATION_MAP` means buying DataForSEO search volume + PAA for that market going forward — a real, ongoing cost decision, not something to trigger automatically off one tenant's typo or one-off request.
* Admin reviews the Tier 2 queue and explicitly approves adding a market (how many tenants need it, is it worth the spend) — once approved, the technical steps (add to `DFS_LOCATION_MAP`/`MARKET_RANK`, trigger `run_segment_research()` for the new market) can be automated, but the approval itself stays human.

Original fix (distinguish empty-input default from non-empty-unmatched, stop silently substituting US data) is still Tier 1's foundation — this just extends it into a full feedback loop instead of stopping at "log it and move on."
