# AA-743 — [A3] Incremental recompute — scoped Score/Route on tour removal + one debounced recompute per wave

## Problem

Measured in S218 (08/10/2026):

* **Removing/trashing one tour recomputes the whole platform.** `recompute_rankings_and_routes()` runs `precompute_question_landings(pool, None)` (all segments), `run_atom_ranking` for all 6 markets and `run_route_detection` over every tour. Trashing one Japan duplicate on 08/10 triggered a 5.7 min recompute. The full post-backfill recompute took 813 s (866 tours, 14,340 segments) and grows with the catalog.
* **A wave recomputes the platform after every tour.** `a3_atomize` calls `recompute_segment_score_route()` after each tour, so India (236 tours) ran 236 platform-wide Score + Route passes in sequence. This is why `a3_atomize` must stay at concurrency 1, which makes A3 a fixed tail of every wave. It is also the source of most of the `decision_log` growth ([AA-742](https://linear.app/aa-ecosys/issue/AA-742/jev-decision-log-growth-stop-writing-a-full-row-per-cache-hit-a3): `a3_activity_type` \~392 rows per segment in 7 days).
* Segment matching itself was fixed in PR [AdventureAsia365-Ecosys/AA-CIS-App#595](https://linear.app/aa-ecosys/review/perf-segment-matching-cost-no-longer-grows-with-the-catalog-same-8f2393d8b657): same-country candidates only, \~0.5 s per tour instead of 36 s.

## Scope

1. **Tour removal, scoped** (trash / inactivate / restore, [AA-713](https://linear.app/aa-ecosys/issue/AA-713/a3-atoms-follow-the-tours-master-content-status-inactivetrashed-tours)/[AA-716](https://linear.app/aa-ecosys/issue/AA-716/a3-raw-tour-discontinuation-cascade-trashing-a-source-tour-must) paths):
   * delete or supersede that tour's `atom_ranking` rows and its current `route` rows directly;
   * recompute score only for the segments the tour's atoms belonged to (their recurrence changes);
   * rebuild only the hubs that referenced the tour's routes.

   No platform-wide landing pass.
2. **One recompute entry, debounced:**
   * `a3_atomize` does atomize + segment matching for its tour only;
   * Score + Route run as a single `recompute` job, enqueued with a coalescing idempotency key, so N atomize jobs in a burst produce one recompute once the queue is quiet or every N minutes;
   * `a3_atomize` concurrency can then rise (e.g. per country).

   This is ADR 0003 nấc 3 ("ONE entry into the platform recompute"), split out of [AA-735](https://linear.app/aa-ecosys/issue/AA-735/jobs-job-model-modularization-follow-ups-adr-0003-nac-3-6).
3. Question landings: only for new or changed segments (cache the rest).
4. The wave report counts segment/ranked/route per tour (the S218 regression, segments silently not built for 566 tours, was only caught by an audit).

Out of scope: ranking formula and weights; route rules for long tours (separate).

## Done when

* Trashing one tour on Dev updates its ranking/route rows in < 10 s, with no platform-wide recompute in the logs.
* A 50-tour wave enqueues ≤ 3 `recompute` jobs, and the A3 tail after the last S1 is < 15 min.
* After the wave, every active Master has segment + ranking rows (reconciliation query = 0 missing).
