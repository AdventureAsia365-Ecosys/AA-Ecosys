# AA-739 — [Review Queue UX] A high score + hard-code block reads as contradictory — lead with the block reason, not the score

## The observation (S217, Nghiep)

In the Review Queue, tours show **score 8.0 / 7.0 but still land in review** (e.g. "Everest Base Camp Trek with Helicopter" 8.0 + FORBIDDEN_WORD). It looks odd: a high score, yet not published.

## Why it happens (not a bug)

As of [AA-736](https://linear.app/aa-ecosys/issue/AA-736/s1-pipeline-hard-failure-codes-must-block-master-one-shot-haikusonnet), the publish gate is TWO independent conditions:

1. `quality_score >= 7.0` (the quality floor), AND
2. no surviving **hard-block code** (FORBIDDEN_WORD, SEO length, MISSING_FIELD, ...).

The score is a weighted average; a single FORBIDDEN_WORD only deducts 0.5, so a strong tour can score 8.0 and STILL carry a hard code. Pre-[AA-736](https://linear.app/aa-ecosys/issue/AA-736/s1-pipeline-hard-failure-codes-must-block-master-one-shot-haikusonnet) that tour published silently with the forbidden word in its body; [AA-736](https://linear.app/aa-ecosys/issue/AA-736/s1-pipeline-hard-failure-codes-must-block-master-one-shot-haikusonnet) now blocks it. So "score 8.0 + in review" is the gate doing its job — the score and the hard-code check are orthogonal.

## Why it still feels wrong (the real UX gap to fix)

The Review Queue surfaces a big green **score** as the headline, which reads as "this is good, why is it blocked?". The score is the wrong headline for a hard-code block. The reviewer needs to see WHY it is blocked, not how high it scored.

## Options to decide (advice)

**A. UX-only (recommended first, cheap):** In the Review Queue, when a tour is blocked by a hard code, lead with the BLOCK REASON (badge: "Blocked: forbidden word in summary") and de-emphasize the numeric score, or show a derived "publishable: no" state. The score stays as secondary info. This removes the confusion without changing pipeline logic. Reasons chips already exist — make the hard-code ones visually dominant (e.g. red) vs soft advice (grey).

**B. Separate the two signals in the data model:** expose `publishable` (bool) + `block_reason` distinct from `score`, so UI and any API consumer stop conflating "quality" with "publishable". Larger change.

**C. Do nothing to the gate.** The gate logic is correct and must NOT be loosened — a forbidden word must block regardless of score. Only the presentation is the issue.

Strong recommendation: **A** (presentation), explicitly NOT loosening the gate. Most of these resolve once [AA-738](https://linear.app/aa-ecosys/issue/AA-738/s1-pipeline-deterministic-forbidden-word-strip-on-body-tighter-writer) (deterministic strip) lands and far fewer forbidden-word tours reach review at all.

## Done when

* Review Queue clearly communicates WHY a high-scoring tour is blocked (hard-code reason is the headline, not the score).
* No change that lets a hard-code tour publish.

Refs [AA-736](https://linear.app/aa-ecosys/issue/AA-736/s1-pipeline-hard-failure-codes-must-block-master-one-shot-haikusonnet), [AA-738](https://linear.app/aa-ecosys/issue/AA-738/s1-pipeline-deterministic-forbidden-word-strip-on-body-tighter-writer).

### 2026-10-08 02:20 — nghiep pham quoc

**Scope added (Nghiep, S218 08/10): list-page pagination + filter bugs on Review Queue AND Master Content.**

Reported from the UI (Review Queue, 54 pending): only 20 rows show, "Page 1/1" never changes, choosing 100/page still shows 20, and the country filter lists only the countries on the loaded rows (only "Sri Lanka"). Master Content has the same symptoms. Filters do not show every enum value they have.

Root cause (code read):
- **Review Queue**: `frontend/app/admin/review/reviewApi.ts:20` calls `/api/admin/review-queue?status=…` with **no `page`/`page_size`**. The API defaults to `page_size=20` (`api/routers/admin_pipeline.py:2380`), so the FE receives 20 of 54 rows. The DataTable then paginates client-side over those 20, which is why it is always 1/1 and the page-size selector has no effect. The country options come from the loaded rows (`review/page.tsx:195`).
- **Master Content**: server-side paging with a hard-coded `PAGE_SIZE = 20` (`master-content/page.tsx:19`). The DataTable page-size selector / pager is not wired to the server `page` state. Country/status options are built from the current page's rows (comment there: "a dedicated distinct-country endpoint is out of scope").

Fix direction:
1. Wire the DataTable pager + page-size to server `page`/`page_size` on both pages (true server pagination, `pagination.total` → page count).
2. The API returns full filter facets (distinct countries, status/score/master_status enum values), independent of the current page.
3. Verify with `aa-ui-verify`: 54 pending → 100/page shows all, page 2 works, country list complete.

Also in scope from S218: `_derive_field_failures` on the Review Queue endpoint does not get the brand's forbidden words yet (the run path does since AA-738), so markers can miss brand words like "explore".
