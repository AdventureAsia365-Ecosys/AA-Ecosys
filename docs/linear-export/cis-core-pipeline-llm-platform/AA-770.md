# AA-770 — [T2/T9] Tenant always receives the content — no held/blocked state, scores or gate codes on the tenant side

## Problem

Product rule (Nghiệp, S232, repeated many times): a rewritten tour (T2) and a written piece (T9) must always be delivered to the tenant whatever the gates decide. The tenant reads it, decides whether to use it, and exports/publishes. Today a `held` T9 piece cannot be published (`api/routers/v1_publish.py` \~281: 422 "edit it in My Content first"), editing never re-runs anything, and tenant-facing responses still carry status semantics. T2 versions that fail the T3 gate follow their own status path. QA belongs only to admin (see the new Content Quality tab issue).

## Scope

1. T9: remove the held block in `v1_publish` and export; tenant APIs (`/v1/content-writing/*`, My Content) return the content with a neutral ready state — no held reason, gate ledger, flags or scores in tenant-safe payloads (`_tenant_safe_piece`).
2. T2: a tenant tour version whose gates fail is still delivered as a usable version (content visible + exportable); gate outcome kept internally for admin.
3. Portal: My Content / Catalog show content only — no held badges, no technical wording.
4. Keep every internal field in the DB for admin QA.
   Out of scope: changing gates themselves ([AA-768](https://linear.app/aa-ecosys/issue/AA-768/t9-writer-source-fidelity-the-writer-invents-numeric-facts-55-pilot) / [AA-701](https://linear.app/aa-ecosys/issue/AA-701/t-series-jev-t10-gates-f8-rubric-f9-split-cannibalization-promises-an)).

## Done when

* On Dev, a T9 piece with status `held` is shown in My Content and exports/publishes without a 422 (curl + UI).
* A T2 version whose T3 gate failed is visible and exportable in the portal.
* Tenant API responses contain no gate/held/score fields (checked on 3 pieces).
