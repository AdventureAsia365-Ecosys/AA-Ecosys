# AA-756 — [Jev] System-wide effectiveness audit + recalibration — thresholds, grey zones, questions to add or retire

## Problem

Jev (TypeSafe) now answers 24 questions across A0 / A1 / A3 / T-series with enough volume to judge it (30 days to 10/10/2026: \~240k decisions). Nobody has checked since [AA-661](https://linear.app/aa-ecosys/issue/AA-661/research-jev-confidence-thresholds-when-may-jev-block-content) whether each question earns its place. First look (S223):

* `a1_claim_supported` (S1 grounding, enforce): 71k decisions, **56% grey**, **$6.2 / 30 days** = 74% of all Jev spend ($8.40 of $130 total LLM spend in 30 days). Grey only becomes a soft reviewer note — there is **no LLM fallback** (the `s1_grounding` rows in `llm_call_log` are the same Jev calls, provider `typesafe`). Only `reject` blocks (→ `UNSUPPORTED_CLAIM`) and the question has **no reject ceiling**, so in practice it only clears novel numbers (`accept` ≥ 0.90). `grounding_repair` still runs on 86% of tours ([AA-747](https://linear.app/aa-ecosys/issue/AA-747/s1-pipeline-trim-llm-calls-per-tour-seo-meta-out-of-flag-fix-cap) wave).
* `a3_atom_in_text` (enforce, reject ≤ 0.30): 18k decisions, **94% grey** — almost never decides.
* `a3_same_place` (enforce, reject ≤ 0.10): 69% grey; calibrated only to keep places apart, not to merge (needed by [AA-695](https://linear.app/aa-ecosys/issue/AA-695/a3-segment-jev-measure-borderline-segment-merges-then-decide-on-a)).
* `a1_keyword_about_tour` (shadow, 18k, 94% grey) never promoted; 9 T-series questions in shadow with little volume.
* Thresholds are one-sided on most questions, and `decision_log.outcome` **is never written (0%)** — there is no stored ground truth to recalibrate against.

## Scope

1. **Inventory** every question: purpose, stage, mode, thresholds, what each zone does downstream (block / pass / LLM fallback / rule), 30-day volume, zone split, Jev cost, downstream LLM cost it saves or causes.
2. **Effectiveness per question** against the best available truth: LLM fallback verdicts on grey items (where linkable), existing calibration files (`docs/calibration/*.md`), and a fresh human-labelled sample where neither exists (Sheet, \~100 per question, Nghiệp labels).
3. **Recalibrate**: proposed accept/reject thresholds per question with the precision they keep, the grey share and the cost change; apply on Dev only after Nghiệp's approval (`threshold_version` + 1, calibration file updated).
4. **Add / retire**: questions to retire (never decides, or no downstream effect), shadow questions to promote or drop, new questions (e.g. `a3_same_moment` for [AA-695](https://linear.app/aa-ecosys/issue/AA-695/a3-segment-jev-measure-borderline-segment-merges-then-decide-on-a)).
5. **Close the loop**: start writing `decision_log.outcome` where a later step knows the truth (LLM fallback verdict, human review), so future recalibration does not need a manual sample.
6. Report in `docs/audits/` (same method as the S218 A-series audit) + artifact.

## Done when

* Audit report published with one row per question (keep / recalibrate / promote / retire / add) and the numbers behind it.
* Approved threshold changes applied on Dev with updated calibration files; before/after grey share and decision cost measured on the next wave.
* `decision_log.outcome` written for at least the LLM-fallback questions.

A reject/accept threshold is meaningless on its own — what matters is **what the system DOES at that threshold**, and it differs per question:
