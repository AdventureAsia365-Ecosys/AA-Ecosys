## Problem

[AA-741](https://linear.app/aa-ecosys/issue/AA-741/t-series-audit-end-to-end-t0t11-test-run-on-controlled-tenants-per) phase 3 (S276, `docs/audits/2026-11-10-S276-aa741-phase3/` §4.6, §4.7) found three places where a failure looks like a success:

* **Failed piece:** blog piece e16fbbfb failed, but its job reports `succeeded` with no error code and no retry.
* **flag_fix limit:** `t2_flag_fix` runs on Haiku 5.5 with the 4,096-token output default. 4 of 6 calls were cut. In 1 of 3 jobs the fix was lost, and the job still reported passed. The same pattern can hit `s1_flag_fix`.
* **Job cost:** `shared.job.cost_usd` is always 0.

## Scope

* A typed failure code in the job result when the piece fails, and the piece status in the job views.
* `stage_model_params` rows for `t2_flag_fix` / `s1_flag_fix` with an output limit sized to the field. A "fix not applied" flag when the reply is cut, plus the task tag in the quality signal.
* `shared.job.cost_usd` filled from `shared.llm_call_log` per job.

## Done when

* A test reproduces each of the three cases.
* On Dev, one forced failure shows its code in the admin job view.
* 0 cut flag_fix replies over 24 h of normal traffic, read from `llm_call_log.stop_reason`.
* Job cost matches the ledger sum for the last 24 h of jobs.
