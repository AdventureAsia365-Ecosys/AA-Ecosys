## Problem

On 04/11/2026 (S267) acc3 Bedrock came back only partly: Claude Sonnet 4.6, Claude Haiku 4.5 and Cohere answer, but Claude 5.x and the GPT models on Bedrock are refused ("not available for this account", quota 0, AWS case open). The routes had gaps:

* some stages had no fallback;
* others fell only to a model that was also refused;
* no route used the Claude 4.x models that work.

Today, changing the order or the preferred provider needs a migration or an env var. Nobody is told when a stage runs on a fallback model.

Tech lead decisions (S267):

* **AWS preferred, not AWS only.** This replaces T-3.
* **Model-first fallback:** the same model on each provider first, then the next model.
* **One Anthropic API key.** Per-product spend is tracked in our ledger.
* **Prefer the Anthropic API for Claude while it is sponsored.**
* **acc3 cap:** 100 USD/month.
* **Every routing setting is editable in the admin**, and every fallback is logged, traced and alerted.

Design page (private artifact): [https://claude.ai/artifact/AgTQX7AwiRYAPj2SSYGjsX](<https://claude.ai/artifact/AgTQX7AwiRYAPj2SSYGjsX>). Copy in the root repo: `docs/audits/2026-11-04-S267-llm-routing/`.

## Scope

* **Family chains (CIS 366, contract):** the agreed chain per stage, the Converse rows for Sonnet 4.6 / Haiku 4.5, the acc3 cap and the breaker fix (refused models no longer keep the acc3 connection circuit shut). Rules are enforced on the server:
  * judge family ≠ writer family;
  * check pairs use different makers;
  * at most 6 attempts per request;
  * every stage keeps at least one live model.
* **Availability matrix (CIS 367):** disabled candidate models on acc3, a manual sweep of every feasible model (< 0.01 USD) and a per-deployment probe state.
* **Stage coverage alarm:** "NO LIVE MODEL" card, bell and e-mail.
* **Admin controls (AI gateway):**
  * drag-and-drop chain per stage;
  * provider order per model (API or acc3 first);
  * order mode as a DB setting, no longer an env var;
  * presets "Prefer Anthropic API for Claude (sponsored)" and "Prefer AWS";
  * a preview of the first model that would serve, before saving;
  * validation shown in the UI;
  * version history with one-click revert, audited.
* **Route trace:** per request, the attempts with their reason, latency and cost; per stage, the share of requests served by each rung. Every call also records the route config version it used.
* **Alerts** (bell + e-mail, deduped):
  * fallback rate above a threshold, or the last rung reached;
  * primary model recovered;
  * cost shift caused by a fallback;
  * a daily digest.
* **Quality guard:** content written by a fallback model is marked in QA, with an optional hold-for-review per stage.

## Done-when

* On Dev, every active stage resolves to a live model (the $0 route check prints the first model that would serve), and the coverage card shows no "NO LIVE MODEL".
* An admin changes a provider order and a chain on the AI gateway page with no deploy. The change is audited, previewed and revertible.
* A forced refusal of a primary model shows in Route trace with every attempt, raises a fallback alert (bell + e-mail), and the recovery raises a "primary back" notice.
* The availability sweep result (every feasible model, ok or refused with its reason) is saved in the root audit folder.
* Screenshots at 1440/390, light and dark.
