# AA-736 — [S1 pipeline] Hard failure codes must block Master; one-shot haiku→sonnet upgrade, else route to review queue

## Problem (found live, S217 Nepal pilot)

A tour went through the S1 admin pipeline (`POST /admin/run-tour-async` → `s1_rewrite` job → `services/content_generation/graph.py`), its `quality_scores.failure_codes` contained `FORBIDDEN_WORD`, the published body still contained the forbidden word `breathtaking`, yet it ended up `master_status='active'`.

**Root cause — a publish-gate bug, not a validate bug.** `validate_node` correctly fires `FORBIDDEN_WORD` (−0.5 to the `quality` sub-score). But the automated rewrite→publish path never consults the hard-code set:

* `graph.should_retry` routes only on `score >= 7.0`; a single `FORBIDDEN_WORD` can't pull a high-baseline tour under 7.
* `flag_fix_node` does not handle `FORBIDDEN_WORD` (not in `STAGE2_FIX_MAPPING` / `_DETERMINISTIC_SEO_CODES`), so the word is never removed — and `_revert_introduced_forbidden` ([AA-641](https://linear.app/aa-ecosys/issue/AA-641/t2-pipeline-stop-flag-fix-from-creating-new-hard-failures)) only reverts words flag_fix NEWLY adds, not pre-existing ones.
* `_is_publishable()` (`api/routers/admin_pipeline.py:74-86`) checks only `quality_score >= 7.0` + brand_audit; it never reads `failure_codes`.
* `_HARD_BLOCK_CODES` ([graph.py](<http://graph.py>), incl FORBIDDEN_WORD, since AA-234) is wired ONLY into `human_edit_gate_node` (reviewer-edit re-validation graph), never into the main `build_graph()` publish flow.

This is a long-standing design gap (AA-211/AA-234), **not** introduced by [AA-724](https://linear.app/aa-ecosys/issue/AA-724/s1-writer-cyclebike-tours-fail-brand-fit-writer-emits-hypepersona-tone) (PR [AdventureAsia365-Ecosys/AA-CIS-App#579](https://linear.app/aa-ecosys/review/s1-writer-neutralize-promotional-source-copy-deterministic-seo-meta-eea85fc1da6d)/#580 only changed the writer prompt, verified via git log). [AA-641](https://linear.app/aa-ecosys/issue/AA-641/t2-pipeline-stop-flag-fix-from-creating-new-hard-failures) is a separate, correct fix (flag_fix doesn't introduce new forbidden words + deterministic seo_meta fit).

## Scope — S1 admin path first (T2 investigated separately, see Notes)

### A. Block Master on surviving hard codes

`_is_publishable()` must also require `not (set(result['failure_codes']) & HARD_BLOCK_CODES)`. Reuse `graph._HARD_BLOCK_CODES`. This is the core fix: hard codes that survive flag_fix must NOT reach Master.

### B. One-shot haiku→sonnet upgrade on surviving REWRITE-class hard codes

After the first (haiku) run, if hard codes remain, re-run the writer ONCE with `model_tier="sonnet"` (reuse the existing `_rewrite_tour(model_tier='sonnet')` / AA-237 block, but trigger on surviving hard codes, independent of `allow_auto_upgrade` and independent of the 8.5 score threshold). Keep the sonnet result if it clears more hard codes.

**Two hard-code classes (tuning so we don't waste a Sonnet run):**

* **Deterministic-fixable (do NOT upgrade):** `SEO_META_TOO_LONG`, `SEO_TITLE_TOO_LONG`, `META_INCOMPLETE_SENTENCE`, `META_TOO_SHORT` — [AA-641](https://linear.app/aa-ecosys/issue/AA-641/t2-pipeline-stop-flag-fix-from-creating-new-hard-failures) `fit_seo_meta`/`fit_seo_title` already fix these without an LLM. Run the deterministic fit; if that clears them, no upgrade needed.
* **Rewrite-class (DO upgrade to sonnet):** `FORBIDDEN_WORD`, `BRAND_SEO_META_VIOLATION`, `MISSING_FIELD` — content/voice problems only a rewrite can fix (confirmed S216: haiku plateaus, sonnet clears).

### C. Still failing after sonnet → review queue, NOT Master

If rewrite-class hard codes remain after the sonnet retry, route to `review_queue` (do not publish). Extend `_build_failure_summary` so the summary states explicitly e.g. `retried with sonnet, still FORBIDDEN_WORD in <field>` (use `_derive_field_failures` / `_CODE_FIELD_MAP` to name the field). The reviewer must see we already tried sonnet.

### Decisions (Nghiep, S217)

* `ITINERARY_STILL_COMPRESSED` stays **soft** (not hard-block): it reflects thin raw data, not a writing fault — sonnet can't invent days the source lacks; forcing it hard would flood review queue.
* Fix stays **purely deterministic** (`failure_codes ∩ _HARD_BLOCK_CODES`). **Jev is NOT involved in this gate** — its only S1 touchpoints (s1_grounding, s1_judge_tiebreak) are shadow-mode content checks that run earlier and never read the publish gate. Keep Jev's current role unchanged.

## Done when

* Unit tests: a surviving rewrite-class hard code (a) triggers exactly one haiku→sonnet retry; (b) a sonnet result that clears it publishes to Master; (c) a sonnet result that still has it routes to review_queue with the 'retried with sonnet' summary; (d) a deterministic-fixable code does NOT trigger an upgrade (fit handles it); (e) `_is_publishable` returns False when any hard code remains.
* Live (via the Sri Lanka / India waves, not a separate run): tours with a surviving FORBIDDEN_WORD no longer reach Master — they are either sonnet-cleaned or in review_queue with an explicit reason. No published body contains a platform forbidden word.
