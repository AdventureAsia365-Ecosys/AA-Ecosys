## Problem

Each app has its own sign-in and none can serve the others (ADR 0006, Context). CIS staff use shared.admin_users username + password with an HS256 JWT (no email, no MFA). CIS tenant users sign in with the tenant API key (one shared key per tenant). AA-Booking staff use the interim CIS bridge (CIS PR [AdventureAsia365-Ecosys/AA-CIS-App#721](https://linear.app/aa-ecosys/review/feat-cis-issues-rs256-staff-tokens-for-aa-booking-audbooking-and-10a6dd8bfdd7), RS256 token aud=booking). Booking customers have an unfinished home-made OTP stack (bk-001). TripPlanner travellers cannot prove an email.

Status at S239 (16/10/2026): ADR 0006 Accepted (root PRs #66, #67). ACM certs + auth custom domains merged (Infra #123). Infra PR #105 (Cognito pools) still open; no pools on acc2. No app code yet. Jira PR-14 (report there only after ship).

## Scope

Target per ADR 0006: Amazon Cognito on acc2 (us-west-1), Essentials plan, two pools.

1. aa-workforce pool (CIS + Booking staff): admin-create only. Staff sign in by email one-time code only (company mail is on DreamHost, not Google Workspace, so no Google IdP for staff). One break-glass account: password + TOTP, own client, disabled between uses, every token issue alarmed. Roles via Cognito groups `<app>-<role>`.
2. aa-external pool (tenant users + travellers): tenant users by invitation (email code, Google once linked by verified email). Travellers by email code, Google or Facebook (Facebook once the Facebook app is live). Tenant scope stays in the CIS database.
3. Lambda triggers (pre sign-up, pre token) fail closed. WAF web ACL with per-IP rate rules on sign-up and code requests.
4. Every app (CIS API + BFF, AA-Booking, TripPlanner) verifies JWTs via JWKS (iss/aud). The PR [AdventureAsia365-Ecosys/AA-CIS-App#721](https://linear.app/aa-ecosys/review/feat-cis-issues-rs256-staff-tokens-for-aa-booking-audbooking-and-10a6dd8bfdd7) bridge is swapped by config.
5. Legacy login: staff password login and tenant API-key human login behind a config flag, off by default after cutover, kept 30 days as rollback. Tenant API keys stay for machine access.
6. Update apps/AA-CIS-App/CONTEXT.md and docs/ecosystem-architecture.md to the Cognito target.

Phases (ADR 0006 Migration plan):

* Phase 0, pools + triggers + break-glass + first staff email-code login: child issue (S239).

**Original title:** [AUTH] Passwordless login for admin + tenant — Google/Facebook sign-in and 8-digit email code

Requested by Nghiệp (S207, 01/10/2026). Jira: PR-14.

Goal: replace username/password on the CIS admin login (`/login`) and the tenant portal login (`/tenant-login`) with social sign-in (Google, Facebook) and an 8-digit email one-time code.

Scope to design: identity model (one account per email, linked providers, match on verified email only); who may sign in (staff allow-list, tenant users only if invited; social sign-in never creates an admin); OTP rules (8 digits, short expiry, single use, attempt limit + lockout, resend cooldown, rate limit, hashed codes); email delivery (SES); session (signed JWT, fold in AA-656); build vs buy (Cognito / Auth0 / Clerk vs own); migration (password login behind a flag, break-glass admin); one login page design.

Original Done when: admin and tenant can sign in with Google, Facebook, or an 8-digit email code on Dev; password login disabled by default; abuse limits tested; CONTEXT.md + an ADR record the decision.
