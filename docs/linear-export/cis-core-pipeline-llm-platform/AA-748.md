# AA-748 — [S1 writer] Feed the writer structured source facts (days, places, numbers) instead of raw source text

## Problem

S218 audit v4: most versions need at least one grounding repair (a sentence with a detail that is not in the source), and itineraries are often compressed. Both trace back to the writer getting raw source text and paraphrasing it freely. Day tours with short sources (\~600–1,500 chars) are where grounding fails most (6/9 grounding holds). Japan's Foodie's Bike Tour was held for inventing meal times.

## Scope (design first, then a measured trial)

1. Extract per-day facts from the source once: day number, places, transport/distances, durations, named sites, meals actually listed, numbers. This can reuse the A3 atomize output or a lighter deterministic parse plus one LLM call.
2. The writer prompt gets the facts table plus a short raw excerpt, with an explicit rule: no numbers, times or meals outside the facts.
3. A/B on the golden set ([AA-729](https://linear.app/aa-ecosys/issue/AA-729/eval-golden-set-30-tours-human-labels-regression-script-pass-rate)) or 30 tours from the S218 waves. Measure grounding repairs per tour, ITINERARY_STILL_COMPRESSED, judge score, and cost.

Out of scope: changing the judge or the gate.

## Done when

A/B report with the numbers above. Adopt only if grounding repairs drop by ≥ 30% at equal or better judge score.

## Design (S224, Claude Code) — contract for the build

**Flag:** `S1_STRUCTURED_FACTS` (env) with a tenant-flag override, same pattern as `S1_PER_DAY_TARGETS` (`prompts.py` `s1_per_day_targets_enabled`). **Default OFF** — with the flag off the writer prompt is byte-identical to today.

**1. Extract per-day facts — new `services/content_generation/source_facts.py`**
- `extract_day_facts(tour) -> {"days": [{"day", "places", "activities", "transport", "distances", "durations", "altitudes", "times", "meals", "other_numbers"}], "used_fallback": bool}`.
- Split the source with the existing `prompts.parse_source_day_word_counts(...)["day_text"]` (the one day splitter — no second one). Parser fallback (no day markers) → return `used_fallback=True` and no facts; the prompt stays as today.
- One LLM call per tour through `LLMClient.generate()` on a new stage **`s1_source_facts`** (role `writer`, a cheap model — Haiku/Luna via Bedrock acc3), JSON output, cost logged to `shared.llm_call_log` like every S1 stage. Add the stage to `SAFE_DEFAULTS` in `shared/llm_client/role_config.py`; if a `shared.llm_role_config` row is required for routing, add a seed migration 210 (Claude applies it).
- **Honesty guard (deterministic):** drop any number/time in the extracted facts that does not appear in the source (`grounding.source_number_parts(tour)`); drop meals not literally present in the raw source. Extraction failure → no facts, prompt as today (fail open).

**2. Writer prompt — `build_rewrite_prompt(..., structured_facts=None)`**
- When facts exist: add a `SOURCE FACTS BY DAY` block (compact, one line per field per day) before `PER-DAY SOURCE LENGTH`, plus a rule: *numbers, distances, durations, altitudes, clock-times and meals may appear ONLY if listed in SOURCE FACTS for that day; each day's places and activities come from that day's facts.*
- Keep the raw itinerary in the prompt (removing it risks more compression); the facts constrain, the raw text gives prose detail.
- Wire it in the S1 path that builds the prompt (`batch_prompt.py` / `graph.py`) behind the flag.

**3. Tests**
- Unit: day split reuse; honesty guard drops a fabricated number/meal; fallback → None; flag off → prompt identical to today; flag on → facts block + rule present.

**4. Measurement (Claude, after deploy with the flag still OFF globally)**
- A/B on 30 tours from the S223 India wave-2 set, both arms run now with the flag set per process (`run_detached` env), same code path as `s1_rewrite`.
- Metrics per arm: grounding violations per tour (first check), grounding-driven `flag_fix` calls, `ITINERARY_STILL_COMPRESSED`, judge score, $/tour (incl. `s1_source_facts`).
- Adopt (turn the flag on) only if grounding repairs drop ≥ 30% at equal or better judge score (the Done-when above).

## A/B report (S224) — 30 tours, S223 India wave-2 set, same deployed code (a090e18), flag set per process, arms run back to back

| Metric | A (flag off) | B (`S1_STRUCTURED_FACTS` on) | Δ |
|---|---|---|---|
| Grounding violations found (first check) | 150 (5.00/tour) | 83 (2.77/tour) | **−45%** |
| Still unsupported after repair | 0 | 0 | — |
| Itinerary days off-band / versions still compressed after nudge | 91 / 1 | 84 / 0 | slightly better |
| s1_flag_fix calls | 25 | 22 | −12% |
| Judge score (mean) | 7.83 | 7.60 | **−0.23** (paired: 11 worse, 4 better, 15 equal; sd 0.68, se 0.12); all 30 ≥ 7 in both arms |
| Cost per tour | $0.0296 | $0.0370 | **+25%** — `s1_source_facts` (Haiku) $0.0078/tour |
| Wall time | 11.3 min | 13.0 min | |

Judge feedback on the 11 lower-scored tours is the same kind as arm A (promotional/loaded phrasing, distance ambiguity), not grounding; B itineraries are somewhat shorter on several tours.

**Verdict vs Done-when:** grounding repairs drop ≥ 30% ✅, judge score equal or better ❌ → **not adopted**; flag stays OFF (code merged #638, migration 210 applied).

Proposed next round (pending Nghiệp): extraction on a cheaper model (Luna 0.6×), soften the prompt rule to "numbers only from facts; keep register and length", re-run 30 tours with the judge scored twice to separate judge noise.

- **Control repeat A2 vs A (same code, flag off): grounding −36%, judge −0.20** — the same size as round 1's B vs A. At n=30 the run-to-run noise is as large as the effect.

### 2026-10-10 12:36 — nghiep pham quoc

**Closed (S224, Nghiệp): not adopted.** Two rounds + a repeated control show no benefit beyond run-to-run noise at n=30, and the final output already has 0 unsupported sentences in every arm (grounding + flag_fix fix them), so the upside is only fewer repair calls (~$0.003/tour). Code stays merged behind `S1_STRUCTURED_FACTS` (default OFF); `s1_source_facts` runs on GPT-6 Luna if ever enabled.

Follow-up chosen instead: the S1 writer runs at the provider default temperature (1.0, `s1_generate` sets none) — likely the main source of the variance. Round 3 tests a lower writer temperature with a repeated control arm (tracked under AA-756 / next comment).
