## Problem

The tech lead asked (S279, 13/11/2026) for a standard kit of technical and process documents. The aim: when a new project starts, the team applies the kit at once and runs the full product lifecycle quickly, without reinventing the rules.

The AA ecosystem has already built most of these practices, but they are written for AA's own repos and spread across many files:

* trunk-based flow, PR rules and self-merge phases;
* Definition of Ready / Done (`docs/templates/definition-of-ready.md`, skill aa-ship);
* ADR placement, contract-first interfaces (`docs/contracts/`), MIG-4 migration order, data standards and retention;
* pre-push guards, code-health ratchets ([AA-1097](https://linear.app/aa-ecosys/issue/AA-1097/code-health-complexity-and-file-size-ratchet-guards-in-every-app-repo)), the settings registry rule ([AA-1096](https://linear.app/aa-ecosys/issue/AA-1096/platform-every-threshold-limit-and-cap-editable-on-an-admin-page)) and the session ritual (skill aa-session);
* Linear quota rules, Jira reporting, cost discipline, the security and secrets register, the UAT harness, DRY RUN first for destructive operations, and the lesson log.

None of it is packaged so another project can adopt it on day 1.

## Scope

**Phase 1: advisory and deep research.** Write to `docs/research/new-project-playbook/` plus an artifact:

1. A lifecycle map from idea to retirement: discovery, architecture, setup, build, test, release, operate, scale, retire. For each phase, list the deliverables, the gates, the roles and the documents/templates AA already has, and what is missing.
2. A practice inventory, each item linked to its AA source and judged as general (reusable as is) or AA-specific (needs a generic version):
   * technical: repo layout, CI, pre-push, ratchets, migrations, contracts, settings, job runner, observability, IaC, accounts, secrets;
   * process: session ritual, DoR/DoD, ship, waves, DRY RUN, incident and lessons;
   * governance: ADR, merge rights by phase, maker-checker, data standards, security, cost;
   * management: backlog and master plan, Linear/Jira, reporting to the business owner, vendor handling.
3. A benchmark against well-known frameworks: ISO/IEC 12207 lifecycle, PMBOK/PRINCE2 governance, Scrum/Kanban, DORA/SRE practices, the C4 model and arc42 for architecture docs, and Twelve-Factor. Keep what fits a startup-scale team (memory: lean infra, 2 environments).
4. The kit design:
   * `docs/playbook/` with an index per lifecycle phase;
   * fill-in templates: project charter, CONTEXT.md, ADR, DoR, runbook, contract, migration, risk register, cost sheet, release checklist;
   * a repo template (scaffold with CI, pre-push, ratchets, settings, docs lint);
   * a day-1 checklist and a 30/60/90-day adoption plan;
   * how the agent skills (aa-session, aa-ship, aa-lessons…) become generic skills for a new project.
5. A recommendation and an effort estimate. Then a follow-up issue to build the kit after approval.

Out of scope in phase 1: building the templates and the scaffold repo.

## Done when

* `docs/research/new-project-playbook/README.md` (plus `.vi.md`) holds the lifecycle map, inventory with sources, gap list, benchmark and kit design, merged in a root PR.
