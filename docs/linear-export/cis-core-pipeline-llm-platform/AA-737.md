# AA-737 — [Jobs] Raise s1_rewrite worker throughput for waves (concurrency / worker scale) — CPU is idle at ~20%

## Why

S217 wave Nepal (83 tours) took far longer than needed. Measured during the wave:

* Worker ECS **CPU avg 17-24%, peak \~79%; memory \~23%** — the worker is NOT CPU/mem bound.
* `s1_rewrite` is pinned at **concurrency=4** (`services/jobs/s1_rewrite_job.py` `@job_kind(KIND, concurrency=4, ...)`) and `worker.max_parallel=4`, so only 4 tours rewrite at once even though the box is mostly idle. s1_rewrite is I/O-bound (waiting on Bedrock), so it is safe to run more in parallel.
* Net effect: Sri Lanka (126) + India (236) at the current rate would take many hours.

## Scope (S1 wave throughput only)

* Raise `s1_rewrite` concurrency (e.g. 4 → 8) and/or `worker.max_parallel`, OR scale the worker ECS `desired_count` (autoscaling min1/max3 already exists, [AA-651](https://linear.app/aa-ecosys/issue/AA-651/p1infra-worker-ecs-service-for-the-job-runner-aa-cis-infra)). Pick based on a quick measurement, not a guess.
* Re-measure worker CPU/mem after the change; keep headroom.
* Confirm Bedrock satellite throughput / rate limits can absorb more parallel s1 calls before raising (don't just move the bottleneck to 429s).

## Explicitly OUT of scope

* **Do NOT raise** `a3_atomize` **concurrency (stays 1).** Verified in `services/jobs/a3_atomize_job.py`: each atomize triggers a PLATFORM-WIDE Segment/Score/Route recompute and paces Cohere embeds with a blocking `time.sleep(3.5)` on its own thread/loop. Running two in parallel risks platform-set write races (the thing [AA-734](https://linear.app/aa-ecosys/issue/AA-734/jobs-atom-ranking-versioned-swap-so-recompute-never-dips-the-live) versioned-swap had to fix) and Cohere 429s. Its cap is deliberate, not a CPU limit.
* The atomize phase (cap 1, \~1-2 min each, serialized) is the real tail of a wave. If that tail matters, the lever is NOT more atomize parallelism but fewer/cheaper recomputes — a separate design question, not this issue.

## Done when

* A wave of N tours shows measurably higher s1_rewrite throughput with worker CPU still within safe headroom and no Bedrock/Cohere rate-limit errors.

Context: found in S217 while running wave Nepal through the new [AA-736](https://linear.app/aa-ecosys/issue/AA-736/s1-pipeline-hard-failure-codes-must-block-master-one-shot-haikusonnet) gate. Deploy only when no wave is running.
