# AA-817 — [Security] CIS API runtime role aa_cis_admin is not filtered by RLS — tenant isolation relies on app code only

## Problem

S236 (14/10/2026), verified live on Dev RDS (PG 15.17) while applying migration 225:

* `aa_cis_admin` (the CIS API/worker runtime role and migration runner; owner of the tenant tables; member of `rds_superuser`; `rolbypassrls=false`, `rolsuper=false`) reads **all rows** of `gold_aa_internal.published_tours` under `app.tenant_id = <foreign uuid>` and under `''`, even though the table has `ENABLE` + `FORCE ROW LEVEL SECURITY` and policy `tenant_isolation` TO public.
* `aa_app_user` under the same settings is filtered correctly (master 892 / foreign 0 / empty 0).
  So for every request served as `aa_cis_admin`, tenant isolation depends only on `WHERE tenant_id = …` in application SQL. Today the table holds only the AA master tenant's rows, so no cross-tenant leak is observable yet, but tenant-scoped data (T2 versions, content pieces, tenant facts) will be exposed by any missing filter.
  Root cause not yet confirmed: candidates are `rds_superuser` membership semantics on RDS, an inherited role with BYPASSRLS, `row_security` handling, or the API connecting as the table owner.

## Scope

1. Confirm the mechanism (pg_auth_members chain, `SET ROLE` experiments, RDS docs) and list every table with RLS + which roles actually get filtered (aa_cis_admin, aa_app_user, tripplanner, booking, catalog_owner).
2. Inventory which code paths connect as `aa_cis_admin` vs `aa_app_user` (api, worker, jobs, admin routes, tenant /v1 routes).
3. Design: tenant-facing routes run as a non-owner, non-privileged role (e.g. `aa_app_user` or a new `cis_tenant_rw`) so RLS is enforced; migrations/admin keep the owner role; table ownership separated from runtime role. ADR if it changes the connection model.
4. Tests: integration test that a tenant-scoped request cannot read another tenant's rows even with a deliberately missing WHERE filter.
   Out of scope: rewriting every query.

## Done when

* On Dev, a request through the tenant API path with a forged foreign `app.tenant_id` returns 0 rows of another tenant from every RLS table (evidence query per table), and the integration test guards it in CI.

### 2026-10-15 00:34 — nghiep pham quoc

S237 step 1 — role × table matrix on Dev (read-only probe, `docs/audits/2026-10-14-S237-lane-backlog/aa817/probe.json`):
- Runtime role `aa_cis_admin`: not superuser, **not BYPASSRLS**, member of `rds_superuser` (inherits pg_read_all_data / pg_write_all_data). It **owns** the tenant tables, and RLS is ENABLE **without FORCE**, so the owner is exempt: under any `app.tenant_id` (unset / empty / foreign / own) the main pool reads every tenant's rows — e.g. `content_piece` 193 rows / 4 tenants, `tenant_tour_versions` 29 / 4. This is the S236 finding's mechanism (owner exemption, not BYPASSRLS).
- `aa_app_user` is isolated correctly where it has grants: `content_piece` own 74 / foreign 0, `angle_gate_request` own 6 / foreign 0, `published_tours` master-only under the master GUC.
- `aa_app_user` has **no privilege** on: tenant_tour_versions, content_exports, webhook_deliveries, acp_output_rules, shared.pipeline_runs, generated_content, quality_scores, seo_context. `content_exports` policy lacks NULLIF (uuid cast error on an empty GUC).
- `acp_shared.facts` policy is FOR ALL without a separate WITH CHECK → a tenant writer could insert `scope='platform'` rows once facts move to the tenant pool (latent; fix in 229).
Decision D2 stands: migration 229 = ENABLE (no FORCE) + NULLIF policies + explicit WITH CHECK + grants to aa_app_user, then move tenant route groups to the aa_app_user pool one at a time behind a flag. CI guard test (11 cases) on branch `chore/aa-817-role-matrix`.
