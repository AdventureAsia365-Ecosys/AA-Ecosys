## Problem

The S273 system picture (`docs/audits/2026-11-08-S273-session/system-picture/system-picture.vi.md`, §3 and §5 items 3 + 8) found two recompute gaps:

* After the retire/restore pair of 05/11, the next recompute finished about 74 hours later (266,724 s). During that time a restored tour can be missing from the Slate and from tenant Subjects. The metric `events_not_followed_by_recompute` reported 0/12, so it hid the delay.
* Recompute has no job release delay and no cross-process lock (a3_atomize has both). Two runs can overlap after a deploy, and failures have no fixed error code.

## Scope

* Read `shared.job` and the logs around 05/11 12:05 first (read only) to confirm the cause.
* A sweep every 2 hours: a lifecycle event (retire_source / restore_source) with no recompute after it enqueues one.
* Replace the metric with a latency measure (event → recompute finished), alert when over 30 minutes.
* Recompute gets a release delay and a cross-process lock like a3_atomize, plus fixed error codes.
* Tests for retire_source / restore_source → recompute.

## Done-when

* On Dev, a retire then restore of one test tour is followed by a finished recompute within the sweep window. Shown with job rows.
* The latency metric shows the real delay on the admin page or report.
* Two recompute jobs queued together never run at the same time (test + one live check).
