## Why

`recompute_segment_score_route()` → `precompute_question_landings()` → `land_questions_for_segment()` embeds one candidate question at a time. It calls `compute_embedding()` → `embed("f10_embed", [text])`, and each call waits the [AA-610](https://linear.app/aa-ecosys/issue/AA-610/enhancement-nang-cap-score-ranking-atomsegment-theo-rank-sum-4-chieu) pacing sleep of 3.5 s.

On Dev (29/09/2026, job 547d955b, a 9-day tour) the a3_atomize job:

* made about 1,530 single-text embed calls in 2 hours and was still running;
* cost almost nothing (under $0.001), so the problem is speed, not spend.

Segments with `questions_count IS NULL` are also recomputed, which widens the scope beyond the tour's own segments.

Cohere Embed v4 on Bedrock accepts up to 96 texts per request, and `shared/llm_client/embed.py::embed()` already takes a list.

## Scope

* Collect the uncached candidate questions (and atom texts) first, then embed them in batches of up to 96 per call. Keep the pacing per call, not per text.
* Keep the question-embedding cache, and write the whole batch into it.
* Log one `llm_call_log` row per batch call. `job_id` attribution already works (PR [AdventureAsia365-Ecosys/AA-CIS-App#466](https://linear.app/aa-ecosys/review/fix-attribute-llm-spend-to-the-job-that-caused-it-aa-652-58241b812887)).
* Measure before and after on the same tour: wall time, number of calls, cost.
* Report progress (n of total) through `JobContext.progress`, so the Jobs page can show an ETA (see the Jobs observability issue).

## Done when

* The same tour's landing step drops from hours to minutes on Dev, measured.
* Results (`questions_count`) match the unbatched run on a sample of segments.
