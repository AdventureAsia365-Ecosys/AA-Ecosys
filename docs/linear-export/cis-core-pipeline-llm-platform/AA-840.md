# AA-840 — [T7 Slate] Normal planning never proposes Facebook (or other non-LinkedIn social) pieces — shared seen_places + LinkedIn first; tenant channels do not filter the Slate

## Problem

Tenants can connect a Facebook Page and publish to it ([AA-815](https://linear.app/aa-ecosys/issue/AA-815/portal-facebook-connect-ui-tenant-self-unpublish-wire-existing), [AA-831](https://linear.app/aa-ecosys/issue/AA-831/portal-facebook-page-connect-tenant-connection-guide-promised-on-pr-7)). But normal T7 planning almost never proposes a Facebook piece, so there is nothing to publish. S237 had to clone a LinkedIn piece to channel='facebook' to test T11. The S238 lane B traced the code ([AA-831](https://linear.app/aa-ecosys/issue/AA-831/portal-facebook-page-connect-tenant-connection-guide-promised-on-pr-7) report):

* `propose_slate()` loops over every channel in `CHANNEL_BARS` (`services/acp_shared/slate.py:447`). It never reads the tenant's channel config. That config only feeds `compute_slot_grid()` (`services/acp_planning/allocator.py:198`), which has no production caller (`allocator.py:8-14`).
* One `seen_places` set is shared across all channels (`slate.py:446`). `linkedin` comes before `facebook` and has the same bar (`needs_said=150`, `slate.py:83` vs `:85`). `atom_segment.canonical_place` is NOT NULL, so every segment has a place. LinkedIn therefore takes every place that would clear Facebook's bar (`slate.py:387`, `:399`). Facebook only gets the overflow past LinkedIn's `most_per_hub=99` cap.
* A local `_choose()` run on 5 synthetic segments that all clear the bar gave LinkedIn 5. Facebook, Instagram, TikTok, email, landing_page and ads each got 0.
* Downstream works when a Facebook proposal exists: `pick_subject` copies the channel onto the request (`slate.py:688-692`), and T9 writes it to `content_piece.channel` (`services/acp_content_writing/service.py:1044-1046`, `:1108`).

## Scope

1. The Slate respects the tenant's enabled channels. A tenant without a channel gets no proposals for it, and a tenant with facebook gets facebook proposals.
2. Replace the shared `seen_places` with a per-channel rule, so one place can appear once per channel and is not starved across channels. Keep a cap so one place does not dominate a tenant's Slate. Document the rule.
3. Decide what happens to `compute_slot_grid()`: wire it in as the per-channel quota source, or delete it. Record the decision in the implementation notes.
4. Unit tests: the synthetic 5-segment case gives non-zero proposals for each enabled channel; a tenant with only blog + linkedin gets no facebook.
5. Live check on Dev on a controlled tenant with facebook enabled. Slate is read-only and free; writing the piece is a paid T9 run, which follows the paid-run rule.

## Done when

* `GET /v1/slate` for a Dev test tenant with facebook enabled returns at least one facebook proposal. A tenant without facebook returns none.
* A planner-made facebook piece (not cloned) is written, then published and unpublished through T11 on the test Page. The publish_log rows are posted here. This closes [AA-831](https://linear.app/aa-ecosys/issue/AA-831/portal-facebook-page-connect-tenant-connection-guide-promised-on-pr-7) item 3.
* Unit tests above are green in CI.
