# AA-742 — [Jev] decision_log growth — stop writing a full row per cache hit; A3 ranking re-asks every segment on each recompute

## Problem

`shared.decision_log` holds \~780k rows (495 MB), \~700k of them from the last 7 days (S218 rerun waves, measured 08/10/2026). It caused the `/admin/decisions/summary?days=7` 504 (patched on the read side in PR [AdventureAsia365-Ecosys/AA-CIS-App#591](https://linear.app/aa-ecosys/review/fix-jev-decisions-summary-504-concurrent-reads-covering-indexes-94acc799e680)).

About 85% of the rows are **cache hits**. A cache hit means no Jev call and $0 cost, but `_write_logs()` (`shared/llm_client/decide.py`) still inserts a full row for it (`cached=true`):

| question | rows / 7d | cached | distinct subjects | rows per subject |
| -- | -- | -- | -- | -- |
| a3_demand_belongs | 239,524 | 209,958 | 2,201 | \~109 |
| a3_activity_type | 232,510 | 206,136 | 593 | \~392 |
| a1_claim_supported | 112,063 | 54,161 | 51,610 | \~2 |
| a3_landing_belongs | 39,975 | 29,817 | 6,809 | \~6 |

Root of the A3 volume: `run_atom_ranking()` / `resolve_exclusions()` (`services/acp_contract/atom_ranking.py`) re-run over **every segment platform-wide** on each recompute. Each recompute (after each tour's atomize in a wave) asks the same question again for every segment. The answer comes from cache, but it still costs one cache-lookup query plus one inserted row per segment.

Side effect: `_CACHE_SQL` does not filter `cached`, so a re-logged cache hit refreshes `created_at`. In practice `CACHE_MAX_AGE_DAYS = 180` never expires a verdict that keeps being re-read.

## Scope

1. Stop inserting a full `decision_log` row for a cache hit. Count the hits instead in a small rollup (e.g. `shared.decision_cache_hits_daily(day, stage, question_key, hits)`, upsert +n), so the admin page can still show "answered from cache".
2. Make cache expiry real: the age check uses the original (non-cached) verdict.
3. A3 recompute: ask only for segments that are new or whose keyword/wording changed since the last ranking (or memoize per recompute run), instead of every segment every time.
4. Retention: one-off cleanup of existing `cached=true` rows older than N days (DRY RUN → snapshot → Nghiệp approval, per destructive-ops).
5. Update readers that count rows: `/admin/decisions/summary` (cached column), the S218 audit scripts (Jev coverage reads zones per subject).

Out of scope: changing which questions are asked, Floors, or enforce/shadow modes.

## Done when

* A full A3 recompute on Dev adds ≤ (new or changed segments) rows to `decision_log`, not one row per segment (query before/after).
* `/admin/decisions/summary?days=7` shows the same verdict counts plus a cache-hit count from the rollup, and loads in < 5 s.
* A verdict older than `CACHE_MAX_AGE_DAYS` is asked again (unit test).
