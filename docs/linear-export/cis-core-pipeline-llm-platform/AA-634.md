# AA-634 — [RESEARCH] TypeSafe AI "Jev" (System One Model) — khảo sát toàn diện A/T-series + TripPlanner + AAA cho quyết định có cấu trúc

## What is Jev

[TypeSafe AI's "System One Model"](<https://typesafe.ai/blog/introducing-system-one-models-and-jev>) — a new model class distinct from chat LLMs. Takes unstructured state as input, returns **type-safe structured probabilistic decisions** (not free text). Trained with "Reinforcement Learning for Calibrated Decisions" (RLCD) instead of RLHF/RLVR. Key properties vs a normal LLM (Claude/GPT):

|  | LLM (current stack) | Jev |
| -- | -- | -- |
| Output | Free text, can hallucinate, needs parsing | Typed value matching a pre-declared schema — **cannot type-error**, ships calibrated confidence |
| Sampling | Sequential (token-by-token) | Parallel — all outputs in one pass |
| Latency | 3-329s | 70-500ms (40-200x faster claimed) |
| Cost | Input $0.20-10/MTok, output \~5x input | Input $0.042/MTok, **output free** |
| Best for | Chat, narrative generation, open-ended reasoning | classify / route / score / extract / branch — "a smart if-statement" |

Not a drop-in LLM replacement — it gives up string generation entirely. Only relevant where the LLM call today produces a **structured decision** (fixed schema, enum, score, boolean), not where it writes prose.

Status: **early access only** (per the announcement), not GA. No Bedrock integration — separate vendor/API.

## S196 update — corrections after reading TypeSafe docs + candidate re-ranking

Sources: [Jev with coding agents](https://docs.typesafe.ai/introduction/coding-agents), [Models](https://docs.typesafe.ai/models), [Primitives](https://docs.typesafe.ai/primitives), [Pre-parsed value extraction cookbook](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook).

### Key constraint the original survey under-weighted
Jev only answers three question types over a given `state`: **Choice** (pick 1 of a defined set, with per-option probabilities), **Score** (position on ordered levels you define), **Noul** (probability a statement is true). It **cannot emit any free string** — not even a short span. Text extraction is only possible via "select, don't generate": code proposes candidate spans, Jev picks one, code copies it verbatim.

### Correction: A3 Atomize is NOT the top candidate
Each atom carries string fields (`place`, `action`, `evidence`, `emotional_hook`, `season_note`). Jev cannot produce these. Using Jev here means a redesign, not a model swap: code splits itinerary text into candidate sentences/spans → Jev Choice/Noul selects atom-bearing spans → Jev classifies `activity_type` (Choice, 7), `visual_potential` (Score, 3), `persona_fit` (one Noul per persona). `emotional_hook` would still need an LLM or be dropped. High effort — deprioritize.

1. **T10 judges (F8 / F9 / N7 gates) + A1 brand audit — "verify & escalate" cascade.** Jev scores each rubric criterion (Noul per 1/0 item, Choice/Noul per failure code). Confident pass → skip GPT-4.1. Uncertain or fail → call GPT-4.1 as today to get `evidence` / `feedback` / `flagged_phrases` (strings the repair loop needs). Matches TypeSafe's documented cascade pattern and keeps the existing repair contract intact.

## S196 follow-up — A3 Search Demand ReAct loop: NOT a Jev candidate (code read)

Read `services/acp_contract/segment_research.py` on `main` (`_research_place()`, `:379-484`; prompt `:81-121`; parser `:147-164`).

**What each LLM turn actually returns:** `{"thought": str, "tool": "volumes"|"serp"|"suggestions"|"done", "keywords": [str]}`. The `keywords` list is **LLM-invented search phrasing** (prompt rules: "what a traveller types… `nakasendo trail`, `magome to tsumago hike`", "qualify with the activity once the place has volume"). Those strings are exactly what gets bought from DataForSEO (`_volumes_tool`, `_serp_tool` uses `keywords[0]`, `_suggestions_tool` seed). Keyword generation is the real work of this loop; the tool pick is secondary.

**Why Jev can't replace it:**
- Jev cannot emit strings, so it cannot produce `keywords`. A Haiku call per step would still be needed → no call removed.
- The tool choice is already mostly constrained by code: `serp` refused without measured volume (`:442-449`), `suggestions` refused once anything has volume or budget spent (`:455-459`), hard caps `MAX_STEPS=4`, `MAX_KEYWORDS=8`, `MAX_SERPS=2`, `MAX_SUGGESTIONS=1`. Jev would only be picking inside an already-narrow rule envelope.
- Cost is already tiny: Haiku, ≤4 calls/place, and whole loop skipped for 182 days per `(canonical_place, market)` platform-wide via `segment_research_log` (`_stale_markets`, `:487-497`).

**Only viable Jev shape = redesign ("select instead of generate"), not a swap:** code builds candidate keywords deterministically (place, place × `canonical_action`, DataForSEO `keyword_ideas`/related searches — real queries people type) → Jev Noul "a traveller would type this to find <place/activity>" + Score for relevance → code buys the top-N. Would remove the LLM from this stage entirely and arguably ground keywords in real search data, but changes the loop's design (Ms. Thư's reference port) and likely increases DataForSEO suggestion calls. Low priority given current spend; parked, not proposed.

**Updated ranking:** (1) T10 F8/F9/N7 + A1 brand-audit judges via verify-and-escalate cascade — only real candidate. (2) Atomize — redesign. (3) Search Demand — redesign, lowest value. AAA/TripPlanner — none.

### 2. Architecture proposal (if we adopt Jev)

1. **One decision seam, separate from `LLMClient`**, following Ms. Thư's `Judge` protocol: `shared/decision_client/` with `noul()` / `choice()` / `score()`, a `RecordedDecider` for tests, and plain HTTP. Every call is logged to `shared.llm_call_log` (provider `typesafe`; the role CHECK constraint needs a decision: reuse `judge` or add `decide`).
2. **Decision ledger table** (`shared.decision_log`): stage, subject key, question id, probability, model, floor at the time. Floors can then move without paying again. The ledger becomes the calibration set by joining to A2/T10 human outcomes.
3. **Cascade per decision point:** rules (free) → Jev (≈$0) → cheap LLM (Luna) → strong LLM → human. Thresholds are per stage in `llm_role_config` (admin UI, AA-518), not hardcoded.
4. **Put a gate before every spend:** DataForSEO buys, full-tour rewrites, GPT judge calls. This is where Jev saves money; elsewhere the win is latency and quality.
5. **Split mixed calls into generate + decide:** T8 (Sonnet generates angles; Jev + code rank them), atomize (LLM extracts spans; Jev classifies enums), TripPlanner extraction likewise.
6. **Uncertainty-ordered review:** sort the A2 / T10 review queues by Jev uncertainty so humans read the most doubtful items first. This fits ADR 0007/0023: advisory, never a veto.
7. **Keep out of Jev:** `score.py` (ADR 0014), segment ids unless the verdict is stored once (ADR 0002), and anything whose value is a quote.

**Risks to check before switching:**
- **Admin UI is misleading.** Switching the model in the UI today only affects `s1_brand_audit`; the other two paths ignore it. A code change is required to route them through the stage config.
- **Reasoning-model parameters.** GPT-5/6-family reasoning models may reject `temperature` / `seed` and require `max_completion_tokens` instead of `max_tokens`. This would break the AA-209 determinism contract. Verify on the real API with `reasoning_effort="none"` or `"low"`.

- **Recalibration.** `MIN_QUALITY=7.0`, `_MISSION_ABSENT_CAP` and F9 pass rates were tuned on GPT-4.1's score distribution. A new model shifts pass/hold rates, so re-judge stored pieces before switching (reuse the AA-351 compare script: same content, both judges).
- **Vendor diversity.** ADR-2026-014/027 (judge vendor ≠ writer vendor) is still satisfied, since OpenAI ≠ Claude.
