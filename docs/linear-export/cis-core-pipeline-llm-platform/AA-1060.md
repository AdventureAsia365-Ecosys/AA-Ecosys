## Problem

S273 system picture (§5 item 5): 254 approved tenant pieces, only 6 ever published, 1 live. The WordPress publish path and the retire → restore check on a real post need a WordPress site that stays up. Free hosted test sites (TasteWP) expire in days, so they cannot back recurring evidence.

## Scope

* A small WordPress container (SQLite, no MySQL) added to an existing ECS task with spare memory (for example `aa-booking-dev-admin`: 512 MB, max \~14 % used over 3 days). `essential = false`, so a WordPress fault never stops the host app. $0 extra Fargate cost (the task size does not change).
* ALB host rule `test-wp.lumiguides.it.com` → its own target group. DNS record.
* A start script that re-installs the site and sets a fixed Application Password from Secrets Manager on every start (data is ephemeral: a redeploy of the host task resets the site).
* CIS WordPress integration of the E2E test tenant points at it.

## Done-when

* `https://test-wp.lumiguides.it.com/wp-json/` answers 200 and survives a redeploy of the host service (site re-created, same Application Password).
* One E2E piece publishes to it through the normal CIS channel, and the retire → restore check runs on that post.
* Tech lead approved the design and $0 cost on 09/11/2026 (S274).
