# AA-843 — [LLM gateway] Legacy writer chain wastes one guaranteed-failing acc2-native call per request (~2,382 in 7 days) — start at the satellite, keep acc2 only if it ever works

## Problem

[AA-842](https://linear.app/aa-ecosys/issue/AA-842/observability-investigate-opentelemetry-gen-ai-tracing-for-every-llm) (S238) found that every call on the legacy `haiku`/`sonnet` keys first tries the acc2-native Bedrock path. That attempt always fails, and only then does the call go to the acc3 satellite:

* `_legacy_chain`, `client.py:238-329`, through `_call_bedrock` at `:360`
* the failure is `ValidationException … not available for channel program accounts`

All writer stages use these keys: `s1_generate`, `s1_flag_fix`, `s1_itinerary_nudge`, `t2_generate`, `t2_flag_fix`, `t2_itinerary_nudge`, `t9_write`, `t9_repair`, `t8_angle_gen`, `a0_column_map`, and `a3_place_days` / `a3_place_locate`.

CloudWatch Logs Insights on `/ecs/aa-cis-dev`, last 7 days:

| Event | Count |
| -- | -- |
| `t2_failed_trying_t2_5a` | 1,428 |
| `t2_5a_satellite_used` | 1,427 |
| `t1_failed_trying_t2` | 954 |
| `t1_5a_satellite_used` | 954 |

That is about **2,382 wasted round-trips**. Each adds latency to writer calls (and to the live-writing UX), and adds log noise on every call. The acc2 account is a channel-program account, so this path cannot succeed.

## Scope

1. Change `_legacy_chain` to start at `primary_acct` (the `account_route`, default acc3), then try the other satellite. Drop the acc2-native tier, or keep it only behind an explicit flag or catalog setting that is off by default, so it can come back if acc2 ever gains model access.
2. Do not change the order of the catalog (`_call_route`) chain or of the OpenAI T3 step.
3. Keep `llm_call_log` semantics unchanged: account, `fallback_used`, cost.
4. Unit tests:
   * no acc2-native attempt by default;
   * the flag restores the old order;
   * the stream path is unaffected;
   * shadow behaviour is unaffected.
5. Check that nothing else depends on the acc2 attempt: for example the `bedrock_satellite` metrics TODO, and log-based alerts on `t1_failed_trying_t2`.

## Done when

* Merged and deployed (api + worker on the same SHA).
* Over a 24 h window after deploy, Logs Insights shows **0** `t1_failed_trying_t2` and `t2_failed_trying_t2_5a`, and `llm_call_log` rows for the writer stages still show `account = acc3` with a normal error rate.
* One live `s1_rewrite` or `t9_write` job succeeds, and its p50 latency per writer call is equal to or lower than before. Report the numbers.
