## Problem

The CIS worker runs every `background=True` job kind in one group capped at **one running job** (`BACKGROUND_MAX_RUNNING = 1`, `shared/jobs/worker.py`, [AA-712](https://linear.app/aa-ecosys/issue/AA-712/adr-0002-move-the-place-pipeline-itinerary-places-geocoding-tour-graph) / S217: background batches must not take a wave's slots). Short monitoring kinds (`ops_status_sample` 60 s, `llm_route_watch` 60 s, `ai_usage_rollup`, `compliance_db_checks`, `llm_model_lifecycle`, …) are background too, so they queue behind any long background job.

Seen on Dev 25/11/2026 (S292): the paid T9 re-measure (`writing_memory_r2`, expected 5,400 s) ran from 02:32Z; at 03:13Z 7 `ops_status_sample`, 2 `llm_route_watch`, 2 `ai_usage_rollup` and 1 `compliance_db_checks` were queued behind it. For that whole time the Ecosystem status page and the route / spend watchers did not refresh: an incident would not have shown up.

## Scope

* A separate lane for short monitoring kinds (for example a `monitor=True` flag on `@job_kind`): they never count toward and are never held by the background group cap; they get their own small cap so they cannot take a wave's slots either.
* The caps are admin settings (Platform › Settings, EN + VI guide), not constants; the ops metrics sampler (`shared/jobs/backlog.py`) uses the same pure rule as the worker.
* Tag the existing monitoring kinds; long batch kinds keep `background` behaviour unchanged.

## Done when

* Unit tests: with a long background job running, a monitoring job is claimable; a second long background job is still held; wave kinds keep their reserve.
* Live on Dev: while a long background job runs, `ops_status_sample` keeps running on schedule (no queue build-up in `shared.job`).

+++ Agent notes

Root cause read in S292: `claim_caps_for()` drops every background kind once `running_background >= BACKGROUND_MAX_RUNNING`. Kinds: `services/jobs/*_job.py` `@job_kind(..., background=True)`. R2 is also `deploy_blocking=True`, so a code deploy waits for it too (separate, expected).
