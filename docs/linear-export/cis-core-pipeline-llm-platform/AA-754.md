# AA-754 — [Cleanup] Remove atom distinctiveness end to end (T5 scoring, planning weights, portal, admin API) — concept dropped in the source repo

## Problem

[AA-749](https://linear.app/aa-ecosys/issue/AA-749/a3-platform-atom-distinctiveness-is-always-med-score-it-per-country-or) hid atom `distinctiveness` on the admin side (platform atoms are never scored; Atom Curation no longer shows it). Nghiệp (S222, 09/10/2026): the concept was dropped entirely in Ms. Thư's source repo, so the tenant side should drop it too instead of keeping a half-used signal.

Where it still lives on `main` (checked S222 with `git grep` on origin/main; tests excluded):

* **T5 scoring:** `services/acp_produce/tenant_pipeline.py` (two call sites, \~L522–563 and \~L677–759) builds a `CompetitorIndex` and calls `score_distinctiveness()`; `services/acp_shared/competitor_index.py` exists only for this.
* **Planning (T7):** `services/acp_planning/quarter.py` (`distinctiveness` term, weight 0.20 in `constants.py::QUARTER_SCORE_WEIGHTS`; "big rocks" pick `distinctiveness == "HIGH"`), `allocator.py:132` (weight multiplier HIGH 1.5 / MED 1.0 / LOW 0.6), `models.py`, `tenant_pool.py`.
* **APIs:** `api/routers/admin_atoms.py` (field, filter, `distinctiveness_breakdown`), `api/routers/v1_marketplace.py:91` (`high_atom_count`), `api/routers/v1_planning.py` (`distinctiveness_score`).
* **Portal:** `PlanningTab.tsx` (`distinctiveness_score`), `CompetitorsTab.tsx` (copy says competitors are used to score distinctiveness).
* **Docs / helpers:** `services/acp_shared/dfs_relevance.py` (comments mirror the 3-bucket shape), `atom_extraction.py` (comment).

**Not the same concept — do not touch:** the T2/A1 judge's `cross_brand_distinct` score (`services/content_generation/judge_node.py`, `brand_fit.py`, [AA-698](https://linear.app/aa-ecosys/issue/AA-698/a1-judge-gpt-56-luna-scores-default-brand-master-rewrites-30-cross)).

## Scope

1. Stop computing it in T5 (both call sites); stop reading it in planning and re-normalize `QUARTER_SCORE_WEIGHTS` over the remaining terms (runway / richness / dfs_relevance / engagement). "Big rocks" must pick by a remaining signal. Remove the allocator multiplier.
2. Remove it from the admin atoms API (field, filter, breakdown), `v1_marketplace` (`high_atom_count`) and `v1_planning`, plus the portal Planning and Competitors copy.
3. Delete `competitor_index.py` and `acp_shared.competitor_index_cache` usage **only if** nothing else reads them after step 1 (verify with grep and `llm_call_log` / DFS logs).
4. Column `acp_contract.tour_atoms.distinctiveness`: stop writing it. Dropping the column (and the cache table) is a migration: DRY RUN, restore file in S3, Nghiệp approves before the real run.

## Decision (Nghiệp, S222): remove the Competitors feature too

The tenant **Competitors** tab (`CompetitorsTab.tsx`, `api/routers/v1_competitors.py`, table `acp_silver_s2.competitor_inputs`) has no consumer other than distinctiveness. Remove it with this issue so tenants are not misled into thinking their competitor list does something. Before removing, re-check with grep that nothing else reads `competitor_inputs` / `competitor_index_cache`. The UI tab, router and nav entry go in code; dropping the tables is part of the step-4 migration (DRY RUN + restore file + approval).

## Done when

* `git grep -i distinctiveness` on main returns only history/comments and the unrelated `cross_brand_distinct`.
* Quarter plan for a test tenant still ranks trips (unit test on the new weights; ranking of a fixture is explained in the PR).
* Admin + portal smoke green; no API returns a distinctiveness field.
