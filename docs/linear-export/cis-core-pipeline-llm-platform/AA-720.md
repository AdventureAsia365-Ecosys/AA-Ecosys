# AA-720 — [Jev] Credit monitoring — 402 billing_error alert + circuit breaker + daily canary (TypeSafe has no balance API)

## Problem (found S209, 03/10/2026)

During the China rerun the Jev Decisions page showed many `a3_demand` / `a3_segment_type` verdicts (mode **enforce**) in zone `error` with `Client error '402 Payment Required'` from `api.typesafe.ai/v1/systemone`. TypeSafe credit ran out and nobody noticed: `shared/llm_client/decide.py` fails open (stage falls back to its existing rule), so the pipeline kept running silently without the Jev layer.

Unlike DataForSEO ([AA-627](https://linear.app/aa-ecosys/issue/AA-627/dfsops-canh-bao-so-du-dataforseo-thap-djoc-balance-1-lanngay-alert): free balance endpoint → `shared.dfs_balance_snapshot` → low-balance bell), **TypeSafe has no balance/credits endpoint** — the official OpenAPI (`api.typesafe.ai/openapi.json`, v0.2.0) only exposes `POST /v1/systemone` and `GET /v1/models`; the response only carries per-call token usage.

## Scope

1. **402 alert (detect it happened).** When a TypeSafe call returns 402, emit a `platform.jev_credit.exhausted` notification (admin), throttled to one unread alert per 24h like `platform.dfs_balance.low`. Also a daily check that counts 402 errors in `shared.decision_log` over the last 24h.
2. **Circuit breaker.** After a 402, stop calling TypeSafe for N minutes (stages use their existing rule explicitly, verdict `skipped`/`error` with reason `credit_exhausted`) instead of paying \~200–2000 ms latency on every failed call.
3. **Decision (Nghiep S209): NO auto-reload, NO burn-rate/ledger.** Auto-reload on the TypeSafe console is considered too risky (uncapped spend); the owner (Ms. Thu) tops up manually when the alert fires. Scope is only items 1 + 2 (alert + circuit breaker) and item 4 (daily canary). OpenRouter is out of scope.
   Evidence from the live probe (03/10, 15:35 UTC, our key): `GET /v1/models` 200; `POST /v1/systemone` 402 `{"detail":{"error_type":"billing_error","message":"Your organization has no available TypeSafe API credits ..."}}`; no balance headers; `/v1/balance`, `/credits`, `/usage`, `/account`, `/billing` all 404. Detection keys on `error_type == billing_error`.
4. **Daily canary probe.** One tiny `/v1/systemone` call per day so a 402 is caught even on days with no pipeline traffic.

## Done when

A 402 raises a bell notification within minutes; the circuit breaker stops repeated failing calls; a daily canary catches billing_error even with no traffic; verified on Dev.

**What landed**
1. *Circuit breaker* (`shared/llm_client/decide.py`): detects a TypeSafe 402 `billing_error` (`is_billing_error`, keyed on `error_type`) and trips a per-process breaker (`JEV_CREDIT_COOLDOWN_MIN`, default 15m) so a credit outage no longer bleeds ~3s per call across tens of thousands of verdicts. Still fails open (stages keep their existing rule).
2. *402 alert*: one throttled `platform.jev_credit.exhausted` bell (1 unread / 24h, roles admin+content), mirroring AA-627's `_maybe_alert_low_balance`.
3. *Daily canary + 402 sweep*: `POST /admin/jev-canary/check` (one real probe via `decide._call_jev`; resets the breaker on success) and `POST /admin/jev/402-sweep` (counts `decision_log` 402s in the last 24h). Both driven once a day by the existing AA-627 ops-probe Lambda (phương án b: one Lambda now POSTs all three paths, each independent).

Per the S209 decision: no auto-reload, no burn-rate/ledger, no OpenRouter.
