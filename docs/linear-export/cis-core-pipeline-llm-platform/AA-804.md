## Problem

S235 AI-first review: the Model Gateway is single only inside CIS; TripPlanner runs a 269-line fork (no shadow, success-only logging, NULL price → 0); Booking has none yet. llm_call_log is written by callers and only on success (billed failed attempts missing), has no app / status / attempt / prompt_hash / shadow columns; some stages are undeclared or pin model_tier.

## Scope

* Root ADR 0006 "AI platform and governance": gateway = versioned in-process library + shared control plane in acc2 RDS (CIS-owned); data-class egress policy (Bedrock only — S235 decision); numbers-never-from-model and human-gate rules; AI Use Register (owner, golden set, budget, kill switch per stage); mapping of AI items to blueprint phases.
* CIS migration: llm_call_log v2 columns (app, is_shadow, status, attempt_no, prompt_hash, is_experiment); gateway writes every billed attempt; alarm on log-write failure.
* Declare the undeclared/pinned stages (a3_search_demand, s1 upgrade, eval runs); unknown stage = error, not silent Haiku.

## Done when

* ADR accepted; 100% llm_call_log rows have app; failed attempts logged; register covers every stage; Cost Explorer vs ledger ≤5%.

**Scope addition (S238 backlog audit): PII on the LLM path** (DM-6.4, data-standards open item #6)

**Current state.** DM-6.4 is enforced by review only. Identifying personal data must stay out of:
- LLM prompts and Jev requests;
- `llm_call_log` (including `quality_signal`), `llm_shadow_log`, `decision_log`, and app logs.

The protected classes are contact, name, address, profile, online_id, payment and `conf:credential`. Nothing checks any of this automatically today.

**Added to this issue, as part of the AI platform ADR and ledger v2:**

**(a) Decision.** Record Nghiệp's call: keep DM-6.4 review-only, or add a gateway-side check. Update DM-6.4 and open item #6 to match.

**(b) If a check is approved,** add a deterministic detector to the gateway library:
- It matches email, phone and card-number-like patterns.
- IDs from `booking.customers` or `tripplanner.customers` are never passed in the request context.
- It runs on the prompt before the call, and on ledger fields before the write.
- On a match, it either blocks the call, or redacts the text and increments a counter such as `llm_pii_detected` by app/stage. It never logs the matched value.

**(c) AI Use Register column.** Each stage declares which data classes it may send:
- travel / free_text only where the feature needs them;
- never any of these to Jev.

**Done when:**
- The decision is written into the ADR and into DM-6.4.
- If enforcement is approved:
  - a unit test shows that a prompt containing a synthetic email or phone is blocked or redacted;
  - a live check on Dev shows 0 `llm_call_log` rows from the last 7 days matching the email or phone patterns.
