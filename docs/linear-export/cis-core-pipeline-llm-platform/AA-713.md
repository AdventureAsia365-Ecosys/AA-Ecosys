# AA-713 — [A3] Atoms follow the tour's Master Content status — inactive/trashed tours leave segments, ranking and tenant slates

## Problem

Setting a Master Content tour to **inactive** or **trashed** (admin Master Content page → `gold_aa_internal.published_tours.master_status`) does not touch its atoms. Checked in code (S207, 01/10/2026):

* Atom reads only filter on the atom's own flags (`NOT deleted AND NOT is_empty_marker`). Nothing reads `master_status`.
* `services/acp_contract/segment_matching.py`, `atom_ranking.py` (segment members, demand, landing), route detection: atoms of inactive/trashed tours still count.
* Tenant side — `services/acp_planning/tenant_pool.py`, `services/acp_shared/slate.py`, `api/routers/v1_marketplace.py`: join `published_tours` with no `master_status` filter, so a tenant can still be offered atoms from a tour the admin removed.
* Admin endpoints `trash/restore/activate/deactivate` (`api/routers/admin.py`) only flip `master_status`; no recompute.

Nghiệp (S207): this is important — a removed tour must disappear from the social branch too.

## Proposed rule

Only atoms of tours with `master_status = 'active'` are used anywhere downstream. Atoms stay in the DB (soft), so re-activating a tour brings them back without re-atomizing.

## Scope

1. Filter at read time in every atom consumer listed above (one shared SQL predicate / view, e.g. `acp_contract.v_live_atoms`, so the rule lives in one place).
2. On status change (deactivate / trash / restore / activate): recompute Segment/Score/Route for that tour (same chain as A3 publish), as a durable job.
3. Admin Atom Curation + Dashboard counts: show live vs hidden atoms.
4. Tests: inactive tour's atoms absent from segment matching, ranking, slate and tenant pool; re-activate brings them back.

## Done when

Merge + CI + Dev deploy COMPLETED + live check: deactivate one Taiwan tour → its atoms leave its segments and a tenant slate; re-activate → back.

## Shipped — #546 (`4414587e`), ECS :431 COMPLETED, migration 203 applied

**Problem:** setting a tour inactive/trashed never touched its atoms — the A3 reads filtered only on the atom's own flags, so an inactivated tour kept feeding segments, ranking (said/demand/recurrence) and tenant slates.

**Fix:**
- **Migration 203** — view `acp_contract.v_active_tour_atoms` = `tour_atoms` INNER JOIN `published_tours` on `master_status='active' AND deleted_at IS NULL`, plus `NOT deleted AND NOT is_empty_marker`. One gate. (v_trip_registry is tour-grained + LEFT JOIN since #195, can't be reused.)
- The 4 A3 atom reads (segment_matching, atom_ranking ×2, route_detection) read the view.
- `recompute_rankings_and_routes()` — platform-wide Score + Route recompute (no per-tour segment matching; deactivating never adds atoms). The 5 admin status endpoints fire it in the background, so an inactivated tour's atoms leave atom_ranking/route — and the tenant Slate that reads those caches — not just future reads. Segments are UPSERT-only so members stay, but every consumer reads them through the gated view.

TripPlanner out of scope (frozen per ADR 0002/AA-712; its extraction already filters master_status='active').

- Unit 2,326 pass, CI 5/5 + Vercel green, ECS :431 rollout COMPLETED.
- Migration 203 applied to Dev; view resolves to 1513 rows = all non-deleted atoms (no tour inactive yet, so 0 excluded today — the gate is in place for when one is).
- Live image confirmed: all 4 reads reference the view, recompute helper present.

### 2026-10-03 08:51 — nghiep pham quoc

Live-verified on Dev (S209, 03/10/2026). Ran a fully reversible deactivate→reactivate cycle on a real master tour (China "1-Day Highlights of Xi'an", baseline 4 atoms / 24 ranking rows).

**Deactivate (master_status active → inactive):**
- atoms in `v_active_tour_atoms` for that tour: 4 → **0**
- `atom_ranking` rows for that tour: 24 → **0**
- rest of the platform untouched: other tours' view atoms 2622 → 2622, other ranking rows 15090 → 15090
- `master_status='active'` total: 113 → 112 (exactly -1)
- notification `tour.master.deactivated` emitted

**Reactivate (inactive → active):** recompute restored the tour to 4 view atoms / 24 ranking rows.

So the master→atom direction works and is correctly isolated: deactivating one tour evicts only its atoms from the view + ranking caches the slate reads, leaving every other tour's segments/ranking intact; reactivating brings them back without re-atomizing. Matches the "Done when" acceptance.

Shipped in PR #546 + migration 203 (`acp_contract.v_active_tour_atoms`); 4 A3 reads go through the view; `recompute_rankings_and_routes` fires from the 5 status endpoints. ECS aa-cis-dev-api:431 (image contains the view + recompute). Marking Done.

Note: this issue covers the master_status→atom direction only. The upstream link (raw-tour trash/delete → auto-inactivate its master + warn the tenant) is a separate gap found while testing — tracked in a new issue.
