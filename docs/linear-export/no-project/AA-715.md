# AA-715 — [OPS] GitHub Actions "Ops" workflow — AWS status/logs/read queries/migrations/scripts from cloud Claude sessions

## Why

Cloud Claude Code sessions ([claude.ai/code](<http://claude.ai/code>)) can reach the live domains but hold no AWS credentials (MFA-gated `aa365-admin` stays on WSL). That blocks the last two steps of the "Done" definition (ECS rollout COMPLETED, DB-level verification) and any migration / one-off script from a cloud session.

## What

One `workflow_dispatch` workflow in AA-CIS-App (`.github/workflows/ops.yml`) that reuses the existing OIDC role (`secrets.AWS_ROLE_ARN`, environment `dev`) — no new IAM, no static keys, no new GitHub Environment.

Actions:

* `status` — ECS service (task def, rolloutState, deployments) + TripPlanner Lambda versions. Read-only.
* `logs` — CloudWatch `/ecs/aa-cis-dev` (or a TripPlanner Lambda log group) for the last N minutes, optional filter. Read-only.
* `sql-read` — runs `scripts/ops/*.sql` inside a one-off ECS task (same task def/network as the service), READ ONLY transaction, one statement per prepared execution, only SELECT/WITH/EXPLAIN/SHOW.
* `run-script` — runs `scripts/ops/*.py` in a one-off ECS task. **main only.**
* `migrate` — applies one `api/migrations/NNN_*.sql`, skipped if already in `shared.schema_versions`. **main only.**

Approval model: write actions refuse to run unless dispatched from `main`, so merging the PR that adds the script/migration is the human approval.

Tour re-runs go through the admin API (`/admin/run-tour-async`, `/admin/jobs/*`) using `CIS_ADMIN_SECRET` in the cloud environment, not through this workflow.

## Done when

PR merged, `status` and one `sql-read` dispatched from a cloud session and their output read back from the job log.
