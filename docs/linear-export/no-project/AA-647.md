# AA-647 — [P0][BUG] DFS failures poison the search_demand cache (NULL stored as fresh, places marked researched for 182 days) + repair 25/09 data

## Problem (verified S199)

When the DFS balance ran out during the 25/09 run, nothing stopped the loop and the failures were saved as if they were answers:

* `fetch_volumes_bulk()` never raises; on error it returns `{}`.
* `_VolumeBatcher` resolves every keyword to `None`.
* `_volumes_tool()` stores `search_volume = NULL` with `retrieved_on = now()` (counted as fresh for 182 days).
* `_research_place()` writes `segment_research_log` for every market, even if nothing was bought.

**Evidence** (`acp_contract.search_demand` by hour, 25/09 UTC):

| Hour | Rows | NULL volume | Volume > 0 |
| -- | -- | -- | -- |
| 05 | 1,476 | 904 | 566 |
| 08 | 3,138 | 2,619 | 516 |
| **09** | **8,904** | **8,904** | **0** |
| **10** | **5,787** | **5,787** | **0** |

* 18,214 of the 19,305 rows written on 25/09 are NULL.
* 1,795 places (09–10h) are marked "researched" but no DFS data was ever bought for them.

## Fix

1. Distinguish "DFS answered: no volume" (store 0/NULL with a status) from "call failed" (store nothing). Add `status` / `error` columns or skip the write.
2. Only write `segment_research_log` when the place's purchases succeeded.
3. Stop the run on insufficient-funds / 402 / auth errors (circuit breaker), and report it.
4. Log cache hits to `dfs_call_log` as well (today only live calls are logged).
5. **Data repair** (script, dry-run first, Nghiệp approves the commit):
   * delete the `search_demand` rows written 25/09 09:00–10:59 UTC with NULL volume;
   * delete the matching `segment_research_log` rows;
   * reset the `questions_count` / `contested` caches to NULL for the affected segments.
