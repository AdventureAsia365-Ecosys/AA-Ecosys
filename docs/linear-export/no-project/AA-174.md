# AA-174 — [INVESTIGATION] ACP E2E attempt → discovered S1→S4.2 pipeline is not orchestrated

## Outcome: investigation complete — original OPS goal NOT achievable in current state

Attempted full E2E ACP run (S0→S4.2) on 11/06/2026 to populate UI v3 pages and trigger Gate 2 UAT. The run could not complete because **ACP pipeline S1→S4.2 has never been orchestrated** — this issue instead surfaced a major architecture gap. Reframed from OPS to INVESTIGATION. Findings below feed the new orchestration EPIC + ADR-2026-013.

## What was verified (evidence)

### 1\. ACP S1 entry point calls the WRONG state machine

`api/routers/v1_s1.py:204-218` — `POST /acp/s1/run` reads `STEP_FUNCTIONS_ARN` (shared env var = CIS's `aa-cis-dev-pipeline`) and calls `start_execution` per tour with input `{tour_id, run_id, run_config}` — a single object.

The SM `aa-cis-dev-pipeline` is a **CIS content-rewrite** Map state: `ItemsPath=$.tours` (expects an array `{"tours":[...]}`), iterator = SEOIntelligence→ContentGeneration→Validation→CheckQualityScore→HITLWait→Export→gold. It has NO S2/S3/S4 stages.

Result: every ACP S1 execution fails instantly (\~0.05s) with `States.ReferencePathConflict` ("Unable to apply step 'tours'"). Confirmed on runs `e49871e7` and `023091eb`.

### 2\. ACP has NO state machine of its own

Only one SM exists (`aa-cis-dev-pipeline`, CIS). ACP has only discrete Lambdas: `aa-cis-dev-acp-s3-campaign-planner`, `-acp-s4-trigger`, `-acp-s4-evaluate` + EventBridge rule S3→S4. No `aws_sfn_state_machine` for ACP anywhere in code/Terraform. There is no S1→S2, S2→S3 chain.

### 3\. CIS itself does NOT use the SM in production

CIS rewrite runs **directly in ECS/FastAPI** via `_rewrite_tour()` (`api/routers/v1_pipeline.py`), called from `admin_pipeline.py` + `v1_tours.py`. The 32 published tours in `gold_aa_internal.published_tours` were produced this way. The SM `aa-cis-dev-pipeline` exists but all 83 historical executions FAILED — it is unused scaffold. (This explains the 32-tours-vs-all-failed paradox.)

### 4\. ACP tenant-auth contract is inconsistent across 3 layers (separate finding → AA-181)

To even reach `/acp/s1/run` required: `X-API-Key: <raw key>` (API Gateway TOKEN authorizer, identitySource `method.request.header.X-API-Key`, hashes raw token) + `Authorization: Bearer <JWT>` (FastAPI HTTPBearer) where JWT comes from `POST /auth/tenant-login`. No single documented header works; a normal client sending one header cannot trigger a run. This is why all ACP UI pages are empty — no tenant request has ever passed all 3 layers.
