# AA-646 — [P0][BUG] DFS research runs platform-wide after every tenant rewrite — scope it and make it admin-triggered

## Problem (verified S199, 28/09)

**Code path:**

* `api/routers/v1_tours.py::_run_research_only()` fires `run_segment_research()` after **every tenant T2 rewrite**.
* `services/acp_contract/segment_research.py::run_segment_research()` selects `canonical_place, canonical_action FROM acp_contract.atom_segment` with **no filter**.
* Since [AA-545](https://linear.app/aa-ecosys/issue/AA-545/archspec-redesign-segmentscoreroutehub-thanh-platform-wide-1-pr1) made Segments platform-wide, one tenant rewrite researches every stale place on the platform (2,222 places) × the tenant's buyer markets. The docstring ("this tenant's current Segments") is stale.

**Evidence** (`shared.dfs_call_log`, `acp_contract.segment_research_log`, 25/09):

* One run swept **2,215 places × AU/US/UK** between 05:00 and 10:59 UTC.
* 1,169 live DFS calls, **$49.02**.
* The DFS balance ran out mid-run → see the cache-poisoning issue.

## Fix

* Remove the research trigger from the tenant rewrite path. Tenant actions must never buy DFS.
* Research becomes an **admin-triggered job**: scope = new/stale places (optionally one country or one tour), markets chosen explicitly, pre-run estimate shown, budget enforced (see the cost-guard issue).
* Fix the docstring. Add a unit test proving a tenant rewrite does not call `run_segment_research`.

## Done when

* deploy COMPLETED;
* live proof: a tenant rewrite on Dev writes **0** `dfs_call_log` rows.
