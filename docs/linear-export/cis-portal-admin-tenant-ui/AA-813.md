## Problem

A tenant logs in with one shared API key shown once at creation; there are no tenant users, no key rotation, and every account change is a mailto modal (`PlaceholderTabs.tsx`) (S236 inventory).

## Scope

1. Table `acp_shared.tenant_users` (email, role owner/editor/viewer, status, last_login) + invites with expiry.
2. Login by email (password now; passwordless per [AA-703](https://linear.app/aa-ecosys/issue/AA-703/auth-passwordless-login-for-admin-tenant-googlefacebook-sign-in-and-8) later) issuing the same `cis_tenant_token` JWT carrying user + role.
3. Portal Settings → Team: invite, change role, remove; API tab: rotate key (old key grace period), shown once.
4. Admin Tenant 360: list a tenant's users, resend invite.
5. Audit rows for every change.
   Out of scope: SSO/Google sign-in ([AA-703](https://linear.app/aa-ecosys/issue/AA-703/auth-passwordless-login-for-admin-tenant-googlefacebook-sign-in-and-8)), billing.

## Done when

* On Dev a tenant owner invites a second user, who logs in and sees the portal with editor rights; viewer cannot publish (403).
* Key rotation: old key fails after grace period, new key works (curl evidence).

**Data-standards addendum (S238 backlog audit).** Basis: standards v1.0, ADR 0008 §5 / E4, golden rules 13–14, DM-3.5 / DM-6.1.

**(a) Membership contract view**

When `shared.tenant_members` lands, also define `catalog.v_tenant_member`.
- Prerequisite: the membership table is keyed by Cognito `(iss, sub)`, never `sub` alone. Create it only after N7 removes the 007b default ACL.
- Columns: `tenant_id`, `iss`, `sub`, `role`, `status`, timestamps. No email or display name unless a reader needs them.
- Grants: consumer roles get `USAGE` + `SELECT` on the view only, and no grants on the table.
- Changes: append-only. A breaking change ships as a new major version.
- Deferral: the view may wait until a second app needs it (AA-821 / L10). If it is deferred, record that in the PR and in `schema-ownership.md`, so that L10 does not read the table directly.

**(b) PII tags**

Tag columns with `COMMENT ON COLUMN … IS 'pii:<class>; …'`:

| Column | Tag |
|---|---|
| `email` | `pii:contact` |
| `display_name` | `pii:name` |
| `(iss, sub)` | `pii:online_id` |
| last-login IP | `pii:online_id` |
| invite tokens | `conf:credential` (stored hashed only) |
| API-key hashes | `conf:credential` (stored hashed only) |

The new tables and the view also get `COMMENT ON TABLE` / `COMMENT ON VIEW` naming their purpose and owner.

**Done when**
- The `pii:` / `conf:` comments are visible on Dev, via `\d+` or the regenerated `db-schema-reference.md`.
- One of these holds:
  - the view exists, and a consumer role can SELECT the view but gets permission denied on the table; or
  - the deferral is recorded as described above.
