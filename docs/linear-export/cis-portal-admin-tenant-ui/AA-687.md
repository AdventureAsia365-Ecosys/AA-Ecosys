## Why

During S201 (29/09/2026), several job-runner states could only be checked through CloudWatch or SQL:

* an `a3_atomize` job running for more than 2 hours;
* a job being released on SIGTERM and re-claimed by the new task;
* the cost attributed to each job (PR [AdventureAsia365-Ecosys/AA-CIS-App#466](https://linear.app/aa-ecosys/review/fix-attribute-llm-spend-to-the-job-that-caused-it-aa-652-58241b812887)).

Every backend capability should be observable in the admin UI. The current Jobs page (`frontend/app/admin/jobs/page.tsx`) shows the list, status, total cost, cancel and retry only.

## Scope

**Job detail (drawer on /admin/jobs)**

* Cost split: `llm_cost_usd` vs non-LLM spend (`cost_usd - llm_cost_usd`, e.g. DataForSEO).
* LLM calls made by the job: `shared.llm_call_log WHERE job_id = …` (stage, model, account, tokens, cost, time). This needs a new endpoint, `GET /admin/job-runner/jobs/{id}/llm-calls`.
* Lifecycle: attempts, `progress.releases`, lease owner and `locked_until`, started, finished and duration.
* Links to the domain row: tour version (`tenant_tour_versions.job_id`), content piece (`content_piece.job_id`), atomized tour, research run.

**Progress and alerts**

* Real progress for long kinds, starting with a3_atomize's PAA landing step: n of total, plus an ETA derived from the pacing.
* Flag jobs running longer than a per-kind threshold, and jobs close to `MAX_RELEASES`.

**Worker health panel**

* Is the in-API worker alive (last heartbeat per `worker_id`)?
* Running jobs per worker vs the per-kind concurrency caps.
* Queue depth per kind, and the oldest queued age.
* Reaper activity: expired leases re-queued or failed.

**Links from domain pages**

* Admin atoms (re-atomize returns `job_ids`), Segment Research, the S1 page, and the tenant version / content piece views link to their job.

**Minor**

* The worker's `job_succeeded` log line prints only the handler-reported cost. Log the full total, or add `llm_cost_usd`.
