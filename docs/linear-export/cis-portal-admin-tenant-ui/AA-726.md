# AA-726 — [T11] Idempotent publish — unique key per (piece, channel, revision), store remote_post_id, read-before-retry; WordPress app password in Secrets Manager

## Problem

Publish is the most obvious non-idempotent side effect in the system. If the network drops after WordPress returns 201, a retry posts a second article on the customer's site. Since the 10/09 weekly report, [AA-462](https://linear.app/aa-ecosys/issue/AA-462/t11-mo-rong-publish-sang-6-kenh-con-lai) (6 channels) and [AA-669](https://linear.app/aa-ecosys/issue/AA-669/portal-my-content-as-a-datatable-columns-filters-sort-bulk) (bulk publish) have landed, but no doc confirms publish has dedup. Must be settled **before the first real tenant publishes**.

## Step 0 — verify current state

* Does `publish_log` have a unique key / dedup today?
* Where is the WordPress application password stored (plain column, encrypted column, Secrets Manager)? Is it ever returned to the FE or written to LLM logs?

If dedup already exists, shrink this issue to the credential part.

## Scope

1. Unique key `(content_piece_id, channel, revision)` in `publish_log`; write `requested` before calling the remote API.
2. Store `remote_post_id` as soon as the API returns.
3. Retry checks the remote first (WordPress: find by slug or a meta field carrying the key).
4. Bulk publish runs through `shared.job`, one child job per piece — not a loop inside the request.
5. WordPress app password in Secrets Manager (or a KMS-encrypted column); never returned to the FE, never in prompts or `llm_call_log`.

## Done when

Simulated timeout after a 201 → retry → the site still has exactly 1 post. Credential never appears in an API response or log.
