## Decisions

- **release-please is kept (tech lead, S282).** The orchestrating agent checks the four release PRs (CIS, Booking,
  Partner, TripPlanner) and merges them weekly, when CI is green and no wave runs. Recorded in the engineering
  handbook section 5.2 (EN + VI). No code change.
- **Rollback, not only an issue, for all four web apps.** Each already has the rollback runbook pattern
  (`docs/ops/runbooks/rollback-ecs.md` lists all four services), so the "else open an issue" branch of the brief does
  not apply; the workflows do both: roll back when it is safe, and always open (or comment on) one
  `deploy-smoke-red` issue per workflow, closed by the next verified deploy (the CIS nightly-red pattern).
- **The rollback target is recorded before update-service**, from the service itself (its current task definition),
  not computed later from the family's revision list: a later revision may be a Terraform template or another run's.
  Recorded only when the service is settled (one deployment, rollout COMPLETED) and runs a real build tag
  (`<sha>` / `dev-<sha>`); otherwise empty, and an empty target means never roll back.
- **Refusals are safe outcomes.** The rollback refuses (exit 3, nothing written) when: no target; desired count 0;
  a deployment in progress (the circuit breaker acts first); the service no longer runs the deployed image (someone
  moved it); the target is not ACTIVE, not a build, the same build, or its image left ECR. Already on the target: no-op
  (re-runs are idempotent). The rollback job is green on success or refusal, red only when a rollback was attempted
  and failed; the deploy run stays red either way through its existing `result` job (unchanged).
- **Triggers**: the hard post-deploy checks of each workflow (CIS: `verify`, `smoke-production`; Booking: `verify`,
  `smoke`; CRM web: `verify`, `smoke`; TripPlanner: `verify`, `release`). Visual runs are report-only and never trigger
  it. Main only (never a PR, never another ref).
- **One script, four byte copies** (`.github/scripts/ecs_smoke_rollback.py` + its test), stdlib only, AWS CLI with the
  deploy job's OIDC role (every call it makes is one the deploy job already makes: describe-services,
  describe-task-definition, ecr describe-images, update-service, wait, list/describe-tasks). The test file also checks
  the shape of every workflow that calls it. Logs name `family:revision` and tags only (public repos).
- **AA-Partner `--container` is optional**: its web workflow names no container (one per family); the script then
  requires exactly one container definition.
- **CRM Sentry was already wired** (AA-1111, S282: `crm_sentry_enabled = true`, secret `crm/dev/sentry-dsn`). No new
  secret. What was missing is a way to prove it: `python -m app.observability.sentry_test_event` in the `api` container
  sends one tagged warning (`test_event=aa-1119`) with the API's own options and scrubbers and prints the event id.
- **DB Migrate already validated most inputs inside `migrate`**, after the environment and before OIDC. The new
  `inputs` job is additive and runs first with no environment, no AWS and no secret, prints every reason at once, and
  reads its lists from `db/owners.yaml` (owners, password roles, environments) instead of literals. New refusals: a
  run from a ref other than `main` (before: every job skipped and the run looked green), a symbolic link or a path
  outside `db/scripts/` / `db/migrations/`, an empty input for its mode. The existing "Unused inputs" and "Validate
  input" steps are unchanged.
- **TripPlanner in `QUEUE_REPOS` is safe in either order**: before the ruleset exists, the queue path's squash merge
  lands at once (its wait loop reads MERGED); after it, the queue takes the PR. So the root PR need not wait for the
  hand step.

## Changed (vs the brief)

- The coverage floor is 90.0, not the measured 90.31: one decimal under the measurement so a runner difference in a
  rounding does not turn main red; the ratchet keeps it from going down.
- The ruleset change is two commands (ruleset POST + strict PATCH), because strictness lives in the classic branch
  protection (as on AA-Booking), not in the ruleset.
- TripPlanner needs two PRs for the `gitleaks` merge-group trigger (the guard runs the base copy), as AA-Booking did.

## Tradeoffs

- A flaky smoke now rolls back a good build. Accepted (audit R32: "smoke red, roll back"); the next deploy of main
  brings it back, and the issue records each case so a flaky spec is visible.
- The automatic path skips the runbook's configuration diff (step 4): the target ran minutes earlier, so its
  configuration is the one the service had before this deploy.
- Thresholds: the CI coverage floor lives in `backend/.coveragerc` (a reviewed config file with a ratchet), not an
  admin setting: it is CI policy, not an app threshold. The override-reason length (200) mirrors the existing step.
