## Decisions

- **Hook = static reading of the SQL an agent is about to send** (`.claude/hooks/pilot_pii_guard.py`, Bash
  PreToolUse, orchestrator and subagents). It triggers only on commands that reach the database: an `aws s3 cp <file>
  s3://` upload (the S3-mediated ECS exec pattern), the ECS exec wrapper with a script file, an inline `--command` /
  `psql -c` / `psql -f`, and a DB Migrate run-script dispatch (it reads the Infra file DB Migrate would run, from
  `origin/main`). Every other command costs one regex check.
- **Same rule in both guards:** the protected columns are the DM-6.1 `pii:` tags (the hook reads them from
  `docs/architecture/db-schema-reference.md`, the Infra guard from the live catalogue) in crm, booking, tripplanner and
  the shared tables that have `tenant_id`, minus the AA staff directory `booking.staff_users`. A statement may count
  (`count(...)`, `count(DISTINCT ...)`, `FILTER`) and test `IS [NOT] NULL`, and may use the column in WHERE / JOIN /
  GROUP BY / ORDER BY; it may not return the value or a whole row.
- **Always on, not only while a pilot exists.** No agent or run-script needs a person's row values; a per-column rule
  cannot be fooled by a query that "should" only hit synthetic tenants, and it is tested before the pilot starts.
- **The hook is a heuristic, the Infra guard is precise.** The hook parses text (subqueries' select lists count, so
  `SELECT count(*) FROM (SELECT email …) s` is refused: write `count(DISTINCT email)`); the run-script guard plans each
  statement on the live database and follows aliases, views, CTEs and subplans.
- **Review fix pass (S269): the hook fails closed for what it cannot read.** For an ECS exec script the hook is the
  only gate, so: an upload whose source cannot be read (stdin `-`, a file written in the same Bash call, a binary or
  missing script, too many scripts in one directory) is refused when it looks like a script (a .py / .sql / .sh name or
  a `scripts/` key; a missing screenshot upload still passes); uploads are parsed per simple command (`aws s3
  cp|mv|sync`, directories walked for .py / .sql, `aws s3api put-object --body`); DB Migrate dispatches include the
  REST dispatch of `db-migrate.yml` through `gh api` (`inputs[script]=`, a JSON body) and a run-script path the hook
  cannot read (or hidden in a variable) is refused; a psql heredoc, `<` redirect or SQL file argument is read too; a
  missing schema reference refuses instead of passing. SQL forms that returned [] before are now reads: a bare alias
  (`SELECT t`, `t::text`, `f(t)`), `(t).col`, `schema.table.col`, quoted or spaced schema names
  (`"crm"."traveler"`, `crm . traveler`), unqualified tables (matched by name in any protected schema, so
  `SET search_path` cannot hide them), SQL text run by `*_to_xml` / `ts_stat` / `dblink`, and a dollar-quoted body
  (DO block, function) that names a tenant table with personal data or runs `EXECUTE`. A comparison over today's
  Infra `db/scripts/` and the apps' SQL-bearing Python (177 files) gives the same verdicts as before: the new rules
  add no false refusals there.
- **Re-review fix pass (S269): one tokenizer, same-call writes, more SQL forms, fail closed on errors.** Comments and
  literals (quoted, `E'…'`, `U&'…'`, dollar quotes) are handled in one left-to-right pass (the Infra
  `sql_statements()` approach), so `coalesce(email,'--')` and `'/*' … '*/'` no longer hide a select list; `U&"…"`
  names are decoded (`UESCAPE` refused). A script written and uploaded / run in the same Bash call is read as the call
  writes it (`cat`/`tee` heredoc, `echo`/`printf`, `cp`/`mv` of a readable file); any other writer, or any command
  outside a small plain list (aws, echo, cat, grep, jq, sleep, …), refuses the call ("two calls"). `bash -c` / `eval`
  strings are read as commands (an upload wrapped in `bash -c` was invisible before; the steering file's MFA wrapper
  still passes). Newly refused: `TABLE t`, `RETURNING *` inside a CTE, functions in FROM over a personal-data column
  or row (`unnest(ARRAY[c.email])`, `jsonb_each_text(to_jsonb(c))`), a FROM-less `SELECT c.email` inside a statement
  (LATERAL), whole-row functions and `t::` casts anywhere (a cast error can echo a value), a select list filled at run
  time over a tenant table, `*` / whole row of a table filled at run time, decoded / evaluated text into an ECS exec or
  psql command, and a path in a variable. Directory uploads read every text file. An exception inside the hook refuses
  a command with a database trigger (exit 2). A module-level string constant in an f-string is read as its text.
- **Re-review comparison (S269):** old vs new verdicts over 1345 SQL-bearing Python files (Infra `db/scripts/`,
  `tools/`, CIS scripts + services, Booking and Partner app code): no new refusal of a re-runnable script except
  `s248_tour_deletion_probe.py` (it returns elements of `tripplanner.trip_drafts.itinerary`, a `pii:` column, through
  `jsonb_array_elements`: a real read, past one-off). The other changes are app code that is never uploaded (CIS
  `tenant_membership/reader.py`, `writing_memory/*`, `erasure/*`, Partner `portability/builder.py`,
  `portal/progress.py`), refused now because their f-string constants are resolved.
- **Review fix pass (S269): the restore drill says whether the backup is complete** (exit 3 = restored but documents
  lost); the runbook lists what the nightly backup never holds and how a real restore gets each back.
- **Restore drill into a throwaway schema = temporary tables** of the drill's own transaction (`pg_temp`, dropped at
  commit), as `crm_app` inside the CRM API container (it holds the KMS key and the bucket). Runbook
  `docs/ops/runbooks/pilot-tenant-restore-drill.md`.
- **Retention of the nightly export:** the `crm.export_job` row of DM-7.1 already covers the files (`exports/` prefix,
  7 days by the bucket rule); its text now names the nightly pilot backup. No new table, so no new row.

## Tradeoffs

- A script written and uploaded in one Bash call passes only when the call writes it in a form the hook reads (a
  heredoc, echo / printf, a copy) and runs nothing but plain commands; otherwise: write the file first, then upload
  (two calls). Non-script uploads (images, reports) are not affected.
- A FROM filled at run time (`f"SELECT … FROM {t}"`) is judged only for `*` / whole rows: single column names
  (`label`, `error`) are personal data in one tenant table and plain elsewhere, so matching them refused re-runnable
  Infra scripts (`aa993_g4_bk_noop_report.py`, `s249_drill_schema_restore.py`).
- Known limits of the static hook (listed in the hook docstring): a script uploaded by another program (boto3, curl),
  SQL built at run time from pieces the hook cannot join or read from a file / S3 / env at run time, single columns of
  a table named at run time, a database error text a script prints, and a function created earlier and only called
  now.
- The hook refuses some harmless forms (an inner select list that only feeds a count, `email IN (SELECT email …)`).
  Rewriting them as counts is cheap; a false pass would put a traveller's data in an agent transcript.
- Static scan of today's scripts: none of `tools/**/*.py` is refused; in AA-CIS-Infra `db/scripts/`, the past one-off
  AA-682 live checks, the `aa990_*` TripPlanner backfill / checks and `dm65_consent_capture` read tagged columns and
  would now be refused if re-run (history; the re-runnable seeds pass because the staff directory is out of scope).
- Columns without a `pii:` tag are not protected (the DM-6.1 census lists 52 untagged candidates).
