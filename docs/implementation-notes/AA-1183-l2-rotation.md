# AA-1183 part 2 — weekly rotation check, metadata permission, CI bot key consolidation (S297, lane l2-rotation)

Part 1 (S296, `AA-1183.md`): register v2 and the ACM expiry rules. This lane: `tools/security/rotation_check.py`
and its weekly workflow (root), the read-only metadata permission of the compliance evidence role (AA-CIS-Infra), and
the move of the aa-ecosys-ci-bot private key into one `ci-bot` environment per repo (script + one workflow PR per repo).

## Decisions

- **The AWS CLI, not boto3.** Every AWS call goes through `AwsCli`, which refuses any (service, operation) outside
  `AWS_CALLS` (13 list/describe/get-rotation-status calls). The runner has the CLI; boto3 would be a new dependency of
  the root tools. `iam-actions` prints the IAM actions of the allowlist; the Infra policy statement lists exactly them
  and both repos pin the list in a test.
- **Cognito: `ListUserPoolClientSecrets`, never the client describe call** (that one returns the secret). The AWS API
  reference says the list call "never reveals the actual secret value"; the tool also drops any `*SecretValue` /
  `SecretString` / `PrivateKey` member from every answer (`scrub`) as a second layer.
- **Which store dates are trusted.** GitHub `updated_at` (moves only on a value set), the Cognito client secret
  creation date and the IAM key creation date are rotation dates. The Secrets Manager AWSCURRENT creation date is an
  upper bound only (a host-only edit makes a version): it can prove that a recorded rotation never reached the store
  (RED), never that one happened. Secrets Manager managed rotation (`LastRotatedDate`) is trusted when enabled (none
  today).
- **Copies raise no due finding of their own**: the primary row's issue says "update every copy". A copy is RED only
  when its store shows it set before the primary's recorded rotation (stale), or when it is missing. This keeps the six
  CI bot copies from opening six issues each time the App key falls due.
- **A source that cannot be read is one RED issue** ("check could not read <source>"), and its rows fall back to the
  register dates; it never turns every row of that store into "missing".
- **Unregistered names** (live, no register row) in Secrets Manager and GitHub: one AMBER issue per store, listing them.
- **Issue titles are stable** (`Secret rotation: <store> <name>`), so the next run finds the issue by title; the body
  is compared without its "Updated by ... on <date>" line, so an unchanged finding is not edited every week. Only
  labelled issues whose title starts with the prefix are ever closed.
- **Windows and caps are settings in `tools/security/rotation_check.toml`** (amber 30 / 14 days, short interval 90 days,
  expiry amber 30 / red 14 days, date tolerance 1 day, 60 issue writes per run), same pattern as `vuln_triage.toml`.
  The root repo has no admin-editable settings mechanism: follow-up for when the compliance settings page exists.
- **Two-job workflow**: the GitHub inventory job runs in `environment: ci-bot` (it needs the key); the check job has no
  environment so its OIDC subject stays `ref:refs/heads/master`, which the compliance role trust already uses. The
  inventory crosses jobs as a gzip+base64 job output (names and dates only).
- **The ci-bot App needs Secrets: Read-only and Environments: Read-only** (GitHub: `GET .../actions/secrets` needs
  Secrets read; `GET .../environments/{env}/secrets` needs Environments read). A browser step for the tech lead.
- **RDAP override for `lumiguides.it.com`**: it.com second-level names are not in the IANA bootstrap (rdap.org answers
  404); `https://rdap.it.com/domain/` returns the expiration event (checked live 28/11/2026: 2027-04-04, matching the
  register).
- **CI bot key: one environment named `ci-bot` in all six repos** (not the existing `release`): one name everywhere,
  and the root and Infra copies need a new home anyway. A GitHub secret cannot be read back, so the move needs a new
  key file: the consolidation is also a rotation (new key generated by the tech lead, old one deleted after cleanup).
- **AA-CIS-Infra workflows**: the root repo is public, so the "root read" ci-bot tokens (docs-gen, image-scan,
  migration-copy-guard retention-rows) are replaced by the job's own `github.token`; only jobs that WRITE to another
  repo keep the App key, in `environment: ci-bot`. Docs Gen is split into render (OIDC, no environment) and publish
  (ci-bot) jobs, because an environment changes the OIDC subject the plan role trusts.

- **Close only what was checked** (review fix, S297): a store-backed finding ("missing from", "unregistered names",
  KMS rotation off, ACM renewal FAILED, a stale copy proven by GitHub `updated_at`) simply drops out when its source
  cannot be read. `sync_issues` therefore reads each open issue's key marker, maps its store to the source that feeds
  it (`_store_source`, the same stores `_live_names` reads) and closes it only when that source is `ok` in the run's
  coverage; otherwise it logs "kept #n open, not checked this run" and writes nothing (no false "Green" comment, no
  split history). A "source X" issue closes only when X (or, for the umbrella `aws` / `github`, any `aws:*` /
  `github:*` source) was attempted. Register-only stores (vercel, vendor, local, lambda-env, other accounts) close as
  before. An issue with no key marker is never closed (fails closed).

- **The cleanup guard fails closed** (review fix, S297): the first `workflows_ready` was bash inside `if !`, where
  errexit is off, and listed files with `for f in $(gh api ...)`, where a failed substitution never trips errexit;
  so a rate limit or a 404 gave zero files and the guard passed, letting `cleanup --apply` delete the old key copies.
  It is now `tools/security/ci_bot_workflows_ready.py`: an unreadable listing or file, an empty list, a file without
  inline content or not valid YAML, a key reference outside a job, a reusable-workflow call passing the key, or a
  job in another environment all mean "not ready" (exit 1). It is job-level like `test_ci_bot_environment.py`, so
  one `environment: ci-bot` job no longer clears another job of the same file. A test runs the shell `cleanup
  --apply` with a failing `gh` stub and asserts the guard itself refuses and nothing is deleted.

## Tradeoffs

- The tool keeps no history: each run judges the register and the stores as they are. The weekly JSON artifact
  (14 days) is the ops calendar's input; a longer record would be the sealed evidence bucket (not done: it would add a
  source to the CIS compliance reader).
- RDAP failures do not open issues (the register `expires` stands in and the row notes it), to avoid a weekly issue
  for a registry outage.
- IAM: the tool reports the account's oldest active key, not a named user (no user names in a public issue).
