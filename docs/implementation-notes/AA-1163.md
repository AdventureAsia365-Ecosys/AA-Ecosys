# AA-1163 — Vulnerability management v2 (KEV, EPSS, CVSS v4.0, SLA, monthly triage record)

Lane l5-aa1163-vuln-v2, S287 (root repo).

## Decisions

- **Rule as approved (D12, S286), first match wins:** KEV → P0; EPSS ≥ 0.10 → P0; CVSS ≥ 9.0 on internet-facing code →
  P0; CVSS 7.0–8.9 (or ≥ 9.0 not internet-facing) or EPSS percentile ≥ 0.90 → P1; CVSS 4.0–6.9 → P2; else P3. The
  "≥ 9.0 but not internet-facing" case is not in D12; it lands in P1 (it still meets the P1 score band).
- **Exposure rule kept from SEC-03 v1** (build-only moves one class down), with three exposures (internet, internal,
  build) set by glob rules in the config and by Dependabot's `scope: development`. A KEV listing never moves down.
- **Prod SLA:** P0 3 days (the issue's 72 h), P1 15, P2 45 (S286 section 5.3 "prod halves the clock").
- **P3:** no clock; the due column reads "next triage <first of next month>" and it is never past due.
- **No score:** the vendor severity stands in for the lowest score of its band (critical 9.0, high 7.0, medium 4.0,
  low 0.1) and the row says "band". Code scanning alerts use their security severity this way; they have no CVE, so
  no EPSS or KEV.
- **EPSS source:** FIRST API value when reachable, else the EPSS GitHub attaches to the Dependabot alert (the record
  says which). KEV unreachable → "not checked", the run still completes.
- **One exception register** `docs/security/vuln-exceptions.toml` (TOML: stdlib `tomllib`, comments allowed). The gates
  keep their own files (pip-audit list, `.trivyignore`, GitHub dismissals); the tool cross-checks them: entry without a
  row, expiry mismatch, expired row, row older than `max_days` (90), stale row.
- **Config file, not constants:** `tools/security/vuln_triage.toml` holds every threshold, SLA, band score, exception
  cap, dismissal reasons, feed URL, cache window and exposure rule. A unit test compares the SLA days and thresholds
  with the SEC-03 table, so the page and the config cannot drift.
- **Public record:** the root repo is public and code scanning alerts are not (unauthenticated API: 401), so
  `--public` keeps code scanning as counts + alert numbers per repo/class/exposure, no rule, no file. Dependabot rows
  keep package, manifest, GHSA/CVE and score (public advisories against public lockfiles, as SEC-03 v1 did).
- **GitHub reads** go through an injected client (`gh api` GET with `--paginate --jq '.[]'` by default); a refused call
  is written as "not readable: <first line>", never guessed.

## Changed

- SEC-03 rewritten: approval section, sources (Trivy is a gate in CIS/Booking/Partner, CodeQL default setup on all six,
  pip-audit failing in four repos), triage rule table (Dev + prod), the three inputs, exposure rule, one register,
  monthly triage with the tool, where the record lives. The stale 2026-10-19 snapshot and the v1 exception table
  (all three CIS rows were gone from `pip-audit-ignore.txt`) are replaced by the monthly records.
- First record `docs/security/triage/2026-11.md` (live read 2026-11-21: 9 Dependabot alerts in CIS, all P2;
  44 code scanning alerts; 6 P1, all code scanning; 0 P0; KEV catalog 2026.11.20; EPSS scores of 2026-11-20).

## Tradeoffs

- Register in TOML in the repo, not a DB table: the compliance `exception` table comes with AA-1166/AA-1170 (S287
  advisory); until then a reviewed file is the simplest auditable list.
- The tool does not write the gates' files or dismiss alerts (GitHub writes are the tech lead's); it only reports.
- Trivy findings have no "opened" date; the clock starts at the scan's `CreatedAt` (or the record date).
