# AA-1009 — UAT dry-run harness (fast mode, sign-in per identity, ~20 read-only scenarios)

Lane w5u-uat-harness-1009 (S262, Claude Code). Root repo, branch `feat/aa-1009-uat-dry-run`.

## Decisions

- **One runner, existing recorder.** `tools/uat/dryrun.cjs` drives `record.cjs --fast` once per scenario in a child
  process (one Chromium at a time, a crash in one scenario cannot take the run down). It does not re-implement the
  step loop; it reads `work/<id>/result.json` + `timeline.json` that `record.cjs` already writes.
- **Pure logic apart.** Argument parsing, scenario selection, the identity plan, per-step rows, the SHA comparison and
  the Markdown/TSV rendering live in `tools/uat/lib/dryrun-core.cjs` (no Playwright, no AWS) so `node --test` covers
  them without a browser or a network.
- **Sign-in per identity, outside the recorded context** (`tools/uat/lib/signin.cjs`): `public`, `cis-admin`
  (Dev-only E2E CIS admin, e-mail code from `inbound-admin/`, MFA admin profile), `booking` (WORKFORCE E2E staff
  `e2e-booking@`, read-only by the backend, code from `inbound/`), `studio` (partner pool studio **viewer**, secret
  `crm/dev/e2e-test-studio/viewer`, password + TOTP), `crm` (reuses `lib/crm-signin.cjs` identity A, the owner of the
  invented agency). Each saved `storageState` is reused while the app still accepts it, so one run asks for at most one
  code per identity. A sign-in that fails marks that identity's scenarios **BLOCKED** with the reason; the others run.
- **Read-only at the network level.** Every dry-run scenario sets `readOnly: true`: `record.cjs` aborts any request
  that is not GET / HEAD / OPTIONS (unless `allowWrites` matches) and lists them in `result.json` `blocked_writes`.
  The backends also refuse writes for three of the four signed-in identities: 403 `e2e_read_only` for the E2E CIS admin
  and the Booking E2E staff, 403 `studio_role_forbidden` for the Content studio viewer (AA-CIS-App
  `api/middleware/tenant_role.py`: a viewer token may only GET / HEAD / OPTIONS plus a fixed list of read-only POSTs).
  The CRM owner can write (see the fix pass below). TripPlanner scenarios also set `blockUrls` for the two model paths
  (`/api/browse/search`, `/api/trip/narrate`): no embedding or chat call can start, even by accident.
- **TripPlanner AI paths are skipped, not run headed.** Search calls an embedding model and narrate a chat model (paid,
  and behind Vercel BotID Basic, which refuses headless Chromium with 403). The dry run covers the public browse pages
  only. `record.cjs` gained `UAT_HEADED=1` / `scenario.headed` (WSLg `DISPLAY`) for a later scenario that needs a real
  browser, but no dry-run scenario uses it.
- **Git SHA per app.** Before and after the run the runner reads every app's own health body (`git_sha` / `sha`):
  CIS API, Booking API, CRM API, CRM web, Content studio, TripPlanner. The two Vercel staff frontends (CIS admin,
  Booking admin) expose no version, so the table shows the head of the repo's `main` (`git ls-remote`, public repos)
  marked as such. A SHA that changes during the run is flagged in the report (a deploy happened mid-run).
- **Record mode from the harness:** `node tools/uat/dryrun.cjs --record <ID>` signs the scenario's identity in, then
  runs `run.sh` (captions -> local TTS -> take -> build -> sync check) with `UAT_STORAGE_STATE`. $0.
- **Ids.** Catalogue ids (plan §4) where the scenario covers the read part of that story (`TP-02`, `CIS-05`, `BK-05`,
  `CRM-02`…). The read-only set is listed in the plan's §4 "Dry-run set". One new id, `TP-PUB-02` (TripPlanner
  privacy notice + terms), follows the `-PUB-` pattern of the pilots.
- **27 scenarios, not exactly 20:** 4 TripPlanner + 1 agency public + 4 Content studio + 4 CRM + 8 CIS admin + 6
  Booking. Every identity of the issue is covered; each scenario is short (2-4 steps, one story), so a red one points
  at one page.
- **Folders per app** (`scenarios/cis-admin/`, `booking/`, `content-studio/`, `crm-web/`, plus the existing
  `tripplanner/`, `partner-portal/`). The dry-run CRM scenarios sit in `crm-web/`, apart from the CRM review set in
  `crm/` (which writes invented data and is driven by `crm/run-all.sh`).
- **Page check = title + data + no broken API** (`check()` in `lib/dryrun-page.cjs`): the h1 (text from the app's
  English messages), an optional ready marker, the kit DataTable row or kit EmptyState (`kit-datatable-row` /
  `kit-empty-state`, the same signals as the CIS UI smoke; no broad "empty" regex), and no same-origin `/api|/bff|/crm|
  /booking` answer 5xx / 401 / 403. Headings and testids were read from each app's `origin/main` (S262), not guessed.
- **Data-dependent steps degrade to the empty state, not to a skip:** BK-05 (no supplier) and PRT-03 (no tour card)
  assert the kit empty state and stop; the step still asserts something.
- **Unit tests run with `node --test`** (`tools/uat/tests/dryrun.test.cjs`, `npm test` in `tools/uat/`): the core logic
  and the manifest (every scenario loads, is built with `ro()`, has en + vi captions, unique ids, covers every
  identity, >= 20 scenarios; the paid-path regexes match both spellings and not the free browse path).

## Changed

- `record.cjs`: `readOnly` / `allowWrites`, `blockUrls`, `UAT_HEADED` / `scenario.headed`; `result.json` gains
  `identity`, `blocked_writes`, `blocked_urls`. Existing scenarios are unaffected (all three options default off).
- `lib/crm-signin.cjs`: exports `secretCreds(secretId)` and `freshTotp` so the studio sign-in reuses them (no copy).
- The outcome of a PASS scenario carries a note when a paid-path request was aborted (verdict stays PASS: the asserts
  decide; the note says a page tried to call a model).
- Plan §4 gains the "Dry-run set" table (EN + `.vi.md`); skill `aa-uat-video` gains §5a (how to run the dry run).

## Tradeoffs

- Node's built-in `node:test` instead of a test framework: no new dependency in `tools/uat/package.json`.
- The mailbox reader is a CommonJS copy of AA-CIS-App `tests/e2e/helpers/mailbox.ts` (baseline + recipient check +
  code extraction), as the Booking signed-in note asks (copy, do not import across repos).
- The read-only guard turns route interception on, which disables the HTTP cache of that context: fast mode is a bit
  slower, recorded takes are unaffected in practice (pages are server rendered).

## Fix pass (S262, review findings)

### Decisions

- **Staff session keep-alive is not a data write.** AA-CIS-App `AdminShell` mounts `SessionKeepAlive`, which POSTs
  `/api/auth/refresh` on every admin page load; the guard put it in `blocked_writes` and would have failed all 8 CIS
  admin scenarios. The classification moved to `tools/uat/lib/net-guard.cjs` (`classify()`): `SESSION` regexes
  (`/api/auth/refresh` exact, query allowed) join `TELEMETRY` as "other". The request is still **aborted**, not let
  through: a refresh could rotate the saved session's refresh token, and the page keeps working (the keep-alive retries
  in 60 s; navigations refresh through GET in `proxy.ts`). Checked with a local smoke (page POSTs the keep-alive and
  opens a WebSocket; `page.request.post` from a step): keep-alive and WS in `blocked_other`, the Node-side POST refused
  and in `blocked_writes`, the local server saw only GETs.
- **AWS CLI errors carry the error code only** (`mailbox.cjs awsErrorCode()`: `AccessDenied`, `ExpiredToken`,
  `timeout`, "credentials expired", `exit <n>`). The CLI text names the role ARN, the account and the bucket (built from
  the account), and sign-in errors reach `results.md`, which is copied to the public root repo.
- **`redact()` masks ARNs and 12-digit account numbers** (`<arn>`, `<account>`), uuids kept whole (a uuid's last
  group can be 12 digits). `record.cjs` now uses the same `redact()` as the report (one rule). `shaTable` errors are
  redacted too.
- **The CRM owner is out of the default dry run.** The CRM has no read-only member role (owner / agent / assistant,
  AA-Partner `api/app/permissions.py`) and no E2E read-only member, so `crm` is a `WRITABLE_IDENTITIES` entry: a
  default run leaves its scenarios out and names them in the report ("Not run: ..."); they run with
  `--include-writable`. Naming one (`--only CRM-01`, `--identity crm`, `--record CRM-01`) without the flag throws
  rather than skipping silently. The dry run keeps its own CRM session file (`work/dryrun/.state-crm.json`,
  `crm-signin.ensureState(who, file)`), apart from the review set's.
- **Read-only by construction:** `describe()` refuses a signed-in scenario that is not `readOnly`, any `allowWrites`
  and any `prepare()`. A manifest test scans the dry-run scenario files for Node-side requests (`.request.post|put|
  patch|delete|fetch`), new contexts, `child_process`, the CRM sign-in module and `bffCall`.
- **Gaps of `context.route()` closed in `record.cjs`:** in a read-only run `context.request` (the object `page.request`
  returns) is wrapped so a non-read call throws and counts as a write; `context.routeWebSocket(/.*/)` closes every
  WebSocket (no app opens one today: grep of the four app repos, S262) and lists it.

### Should know

- Residual risk for `--include-writable` CRM runs: the guard covers the browser network, Node-side request contexts and
  WebSockets, but a scenario could still write through a module the static scan does not know (for example its own
  `require('http')`). The real fix is a read-only CRM identity: a `viewer` member role, or an E2E member refused writes
  by the CRM API (403 `e2e_read_only` like the CIS / Booking E2E staff), with its own secret
  (`crm/dev/e2e-test-crm/sen-vang-viewer`). That needs an AA-Partner backend change plus a Cognito user and a secret
  (AWS writes), so it is a follow-up, not part of this lane.
- The CIS admin and Booking scenarios still have not run in the lane (e-mail code sign-in): the orchestrator's live run
  is their first. The keep-alive fix removes the one systematic FAIL known in advance.
