# AA-981 — Secret scanning guard for public repos (AA-Ecosys root part)

Linear: AA-981 (S248). Infra part: AA-CIS-Infra `docs/implementation-notes/AA-981.md` (rule design, Infra
baseline).

## Decisions

- **Own workflow, no path filter.** `.github/workflows/secret-scan.yml` with job `gitleaks` (every PR to
  `master`, lines the PR adds) and job `history` ("gitleaks full history": nightly 19:41 UTC, push to
  `master`, dispatch). The old gitleaks step inside `docs-lint.yml` ran only when docs paths changed and used
  the default rules only; it is removed there (a `.gitleaks.toml` change, a tool or a workflow PR now gets
  scanned too). `docs-lint.yml` checkout no longer needs `fetch-depth: 0`.
- **`.gitleaks.toml` is a copy of Infra's rules** (header says to keep them in step). Root-only differences:
  no Infra test-fixture path, lock-file allowlist covers npm/pnpm/yarn lock files instead of Lambda zips.
- **Baseline in `.gitleaksignore` without commit** (`file:rule:line`), the format the file already used for
  the S247 entries: every root finding sits in a frozen audit file and appears on two commits (lane branch +
  squash merge). 23 lines added; all are identifiers (Jev `question_key`, TripPlanner `tp_key` UUIDs, backlog
  slugs, an S3 object key, a Cognito app client ID, one prose cell). Security group IDs in
  `docs/generated/inventory.md` are covered by the resource-ID allowlist instead (line numbers there move).
- **The lesson "gitleaks with default rules missed the tfvars password" stays** in
  `skill/aa-lessons/lessons.md`, reworded: CI enforces it only in root and Infra; the three app repos and
  AA-Partner have no full-history job, so it is still a manual check there (review round: the first draft
  deleted the line as "now a CI guard", which dropped the only reminder for the other repos).
- **PR scan reads rules and baseline from the base commit** (`git show $BASE_SHA:<file>` into
  `$RUNNER_TEMP`, mounted read-only): a PR cannot add a secret plus an ignore line and pass. A PR that changes
  `.gitleaks.toml` / `.gitleaksignore` fails until it carries the label `secret-scan-baseline-reviewed`; then
  the PR's copies are used. A file missing at the base (this PR, which adds `.gitleaks.toml`) falls back to
  the PR's copy with a warning. Both files are in CODEOWNERS.
- **History job also fetches `refs/pull/*/head`**: GitHub keeps every PR head, closed PRs included, after the
  branch is deleted, and anyone can fetch it.
- **Public wording**: this repo is public, so the ADR amendment, the baseline row and the register say only
  that historical findings exist and are pinned; which credential sits where and its status stay in the
  private record (Linear AA-981, session log).

## Tradeoffs

- Global fingerprints (no commit) ignore that file:line in any commit. Acceptable for frozen audit evidence;
  new findings in other files or lines still fail.
- The baseline-change label can be added by any writer: it makes the change explicit and reviewable, it does
  not stop a determined writer (same trust as merge in the dev phase).
- The nightly history job also scans unmerged branches: a lane branch with a finding turns `master`'s nightly
  red until it is fixed or the branch is deleted. Intended: a public branch is a public leak.

## Review round (S248, independent review of the app-repo port)

Four should-fix findings, applied to the app repos and, as a follow-up PR, to the root repo and AA-CIS-Infra:

- **Inline allow comments need the label.** An added line with an inline `gitleaks:allow` comment was hidden from
  both jobs with no label. The PR job now lists the files where the PR's commits add such a line (each commit's
  patch, merge commits as a dense combined diff; file names only) and treats it like a baseline change. Existing
  inline allows on the base branch are not affected. Chosen over `--ignore-gitleaks-allow` on the PR job: an
  approved inline allow survives the squash merge, a commit fingerprint does not.
- **The label goes stale.** The label was read from the PR on every event, so a push after the review could add
  a new ignore line and still pass. Now, when the PR has a baseline change and the label: on `synchronize` the job
  compares the previous head with the new one (blob of each file + new inline allows outside the base); on a
  change, an unknown previous head (force push), or `opened` / `reopened` with the label already on, it removes
  the label (job permission `pull-requests: write`, used only for that call) and fails. The reviewer reads the
  new change and adds the label again. Removing it (rather than only failing) keeps later runs honest: a run
  started by another label event would otherwise trust the old label.
- **Fingerprint formats documented.** gitleaks 8.28 git mode honours the global `<file>:<rule>:<line>` format
  for every commit (verified locally: a global entry suppressed a base..head finding). The `.gitleaksignore`
  header now says so, recommends commit pins, and explains that a commit pin does not survive the squash merge:
  prefer a narrow `.gitleaks.toml` allowlist, otherwise pin the PR commit in the PR and the squash commit in a
  follow-up PR.
- **Required check pinned to GitHub Actions.** The post-merge step uses `PATCH .../required_status_checks` with
  the full `checks` array plus `{"context": "gitleaks", "app_id": 15368}` (not the legacy `contexts` POST, which
  any status source could satisfy), run after the PR's own `gitleaks` check is green and before the merge, so
  there is no window without a required secret gate.

Tradeoffs: an update-branch merge that brings a baseline change from the base branch also drops the label (the
blob differs); rare, and the cost is one more review. A fork PR cannot remove the label (read-only token): the
run fails with an error asking a maintainer to remove it.

Known gap, not changed here (also in the root repo and Infra): gitleaks does not scan the content of merge
commits in `base..head` (verified: an evil merge adding a secret passes the PR job). The squash commit on the
default branch is scanned by the full-history job. Closing it in the PR job (`--diff-merges=first-parent`)
would also rescan the base-branch lines an update-branch merge brings in, and those are pinned by other commits.
