# AA-1125 — Platform › Delivery: Merge queue and Git map tabs (root repo part)

Lane l11-delivery-tabs, S283. Extends the AA-1108 collector (`tools/delivery/delivery_metrics.py`, hourly workflow
`.github/workflows/delivery-metrics.yml`). The CIS part (API `section=queue|git`, settings CIS 445, the two tabs) has its
own notes in AA-CIS-App `docs/implementation-notes/AA-1125.md`.

## Decisions

- **Same pipeline, same bundle, format 1.** Two new keys per app in `summary.json`: `queue` (null for an app without a
  merge queue) and `git`; `definitions` gains `git_days`, `git_windows`, `commit_kinds`, `queue_outcomes`. Nothing
  existing changed shape, so the CIS code of AA-1108 keeps reading the file. Two new raw event kinds in the store and
  the daily NDJSON files: `aa.merge_queue.timeline` (one per pull request that went through the queue) and
  `aa.vcs.commit` (one per default-branch commit). Consumers dedupe by `id` as before.
- **Merge-queue history from the REST timeline, not GraphQL `mergeQueue`.** GraphQL lists only the entries in the
  queue now; the history is in each pull request's timeline (`added_to_merge_queue`, `removed_from_merge_queue`,
  `merged`, `closed`, `committed`, `head_ref_force_pushed`). A timeline is read for each pull request seen in a stored
  merge_group run (branch `gh-readonly-queue/<base>/pr-<n>-<sha>`), once, and again only while it is not settled
  (pull request still open) and something moved: a new merge_group run, its merge, or an entry still open. Checked on
  live CIS data (two pull requests with ejections then a merge): same entries as the GitHub page.
- **Outcome rules.** The queue's own removal (actor `github-merge-queue[bot]`) followed by the merge in the same second
  = merged (either order); the queue's removal without a merge = ejected; a removal by a person or the agent, or a close
  within a minute of the queue's removal = removed; an entry with no exit = in queue. Ejection reason from the
  merge_group runs assigned to that entry: checks failed, timed out, cancelled, no check ran.
- **Each merge_group run counts for one entry**: the newest entry that started before it (one minute of clock slack),
  and only while that entry had not left the queue.
- **Flaky signals**: a merge_group run whose newest attempt passed after a job of an earlier attempt failed
  (`rerun_green`), or an ejection on red / timed-out checks followed by a merged entry with no commit or force push in
  between (`reentry_green`).
- **Git activity from the commits list + one read per commit for its files** (`GET /commits?sha=<default>&since=`,
  then `GET /commits/<sha>`): commits never change, so each is read once and kept (`Store.KEEP`). The list is re-read
  from the cursor minus the overlap days, so a late push is not missed. A cold store reads 90 days of commits (one page
  per 100) and then fills their files newest first within the budget share.
- **Author kind**: agent App (`aa-agent[bot]`), CI bot (`aa-ecosys-ci-bot[bot]`), release-please (a `chore(...): release`
  title, which the CI bot App commits), Dependabot, any other bot, a person. As in AA-1108 a person's login is never
  stored (only kinds). Per top-level directory the summary also counts commits by kind ("who changes what").
- **Churn = additions + deletions** per top-level directory, its sub-directories or files (drill-down, 10 each), and the
  top 30 files, over 30 and 90 days; lock files left out (`churn_exclude`). Merges by branch prefix come from the
  merged pull requests already stored (head ref before the first `/`; `release-please--...` kept whole).
- **Phase order and budget.** Queue timelines run after the backfill (it finds older merge_group runs) with a soft share
  of 70 % of the run's budget; commit files run before the CI jobs with 85 %. The new reads are a few per hour in steady
  state (a dozen merged pull requests and their commits a day across the repos).

## Changed (against the issue)

- GraphQL `mergeQueue` named in the issue is not used (no history there); see above.
- "Commits per day/week": the summary carries the daily series; the CIS page sums weeks in the browser.
- Catalogue: CIS-F049 names the three green-band merge-queue settings and its summary mentions the two tabs; the six
  new `cis.delivery.queue_*` keys are added to `docs/catalogue/surface.snapshot.json` (only these lines).
- Guide `docs/guides/delivery-metrics.md` (+ `.vi.md`): sections 7 (Merge queue tab) and 8 (Git map tab).

## Tradeoffs

- Commit dates in a timeline are the commit's own date, not the push time: a commit made before an ejection but pushed
  after it counts as "no new commit" and could mark a `reentry_green` that was really a fix. Rare with squash-and-push
  agent branches; a force push carries its own time and is exact.
- One request per commit for its files is the only REST way to get per-file additions and deletions; the cold fill
  takes a few hourly runs, shown on the page as "Files read".
- The store grows by about the commit file lists of 90 days (a few MB in the Actions cache entry); events older than
  `store_days` (98) are pruned as before.
