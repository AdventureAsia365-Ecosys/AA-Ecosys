# AA-859 implementation notes (root repo: PR-0 pre-flight)

Scope of this file: the root-repo pieces of AA-859 (PR-0 pre-flight probe, `/admin/atoms` tenant-caller
log runbook). CIS code PRs keep their own notes in AA-CIS-App `docs/implementation-notes/AA-859.md`.
Plan: `docs/audits/2026-10-16-S240-aa859/aa859_plan.md`.

## Decisions
- **P0 probe = one script, one READ ONLY transaction, rolled back** (`docs/audits/2026-10-16-S240-aa859/p0_preflight.py`).
  Same shape as the S239 probe v2 (`.tmp-session/s239/aa817_probe_v2.py`): main secret `aa-cis/dev/rds`,
  savepoints that always roll back, `SET LOCAL ROLE aa_app_user` for reads that must go through the tenant
  role, and the `aa-cis/dev/rds-app-user` login only as a fallback when SET ROLE is refused.
- **Output**: the full JSON goes to `s3://aa-cis-bronze-005097885195/scripts/out/s240_aa859_p0.json`; stdout
  is only `OK <bytes>` (lesson S237: ECS exec output is cut silently). The reader checks `wc -c` against
  `<bytes>` and `json.loads` before reading; a DB failure is in the JSON as `fatal`, never on stdout.
- **Item 1 reads `aclexplode(relacl)` and `aclexplode(attacl)` separately (UNION ALL)**, so a column grant
  never hides a table grant (the plan's D1 text uses `COALESCE(att.attacl, c.relacl)`, which does hide
  it; the probe also runs that D1 text verbatim and records its rows, for comparison).
- **Classification is done in Python from raw rows**, with the rule written once (`_classify`):
  (b) catalog contract = schema `catalog`, owner `catalog_owner`, table level, SELECT;
  (a) 241 revokes = aa_app_user item, runner can act for the owner, owner not in
  {catalog_owner, tripplanner, booking}; (c) every other aa_app_user item on a non-RLS relation.
  Sequences are listed as `seq` (out of the 241 rule, plan D1). PUBLIC items are listed separately with
  "aa_app_user has USAGE on the schema" (guard 0 input).
- **Roles aa_app_user inherits** (`pg_has_role('aa_app_user', r, 'MEMBER')`) are probed too: an ACL item
  granted to such a role reaches the tenant role without naming it, and 241's loop would not see it.
  They count as class (c). Predefined roles (`pg_read_all_data`, `pg_write_all_data`) are flagged because
  they grant without any ACL item.
- **Live master tours for D9 use the base-table rule of `catalog.v_tour`** (225: master tenant,
  `master_status = 'active'`, `deleted_at IS NULL` on published_tours; `source_status = 'active'`,
  `deleted_at IS NULL` on raw_tours), read as the runner with `app.tenant_id` pinned to the master tenant
  inside a savepoint, so the counts are right whether or not the runner is filtered by FORCE RLS.
- **"Appears in the catalog views" is read through the views themselves as aa_app_user** (the role that
  holds the catalog SELECT), keyed by values the runner computed (no tenant data leaves the transaction).
- **`schema_versions` latest uses `max(version::int)`**, not `max(version)` (text max puts '99' after '240').
- **A failed fallback login is not fatal** (review fix): if SET ROLE is refused and reading
  `aa-cis/dev/rds-app-user`, connecting (e.g. `TooManyConnectionsError` at aa_app_user's CONNECTION LIMIT 15)
  or starting its transaction fails, `catalog_reads_as` records `{"error": ...}`, the reader is closed and
  set to None, and only item 2's two catalog-view reads come back as errors (`_as_reader` retries SET LOCAL
  ROLE and records the refusal). Items 1, 3-6 still run; the final reader rollback is guarded by
  `atr is not None`.
- **Item 6 = runbook Q7** (review fix): `shared.tenant_api_usage` admin rows on `/admin/atoms*` per UTC day,
  method and status over 30 days, in the same READ ONLY transaction, so the P0 run completes the
  14-day ECS cross-check without a second ECS exec. Columns from `db-schema-reference.md`
  (`endpoint`, `method`, `status_code`, `called_at`, `actor_type`). Not a plan item, so an item 6 error
  does not make `gate_241_ready` false.

## Changed
- **D9 / `v_tour_component`: the plan says it "joins tour_atoms"; it does not.** 228:249-273 builds it from
  `geo.tour_place` joined to `catalog.v_tour` on `source_id`. Its link to atoms is provenance:
  `geo.tour_place.atom_ids text[]` (the place pipeline reads atoms through `v_active_tour_atoms`,
  `services/places/store.py`), and `text_extract` is derived from those atoms' text. So P0 measures
  `v_tour_component` exposure as "components whose `atom_ids` contain a non-platform atom (any state)",
  plus the subset made only of non-platform atoms. Only `v_tour_place` (225:257-258, 228:143-144,
  235:54-55) joins `tour_atoms` directly; it exposes no atom id, only `atom_count` / `activity_types` per
  (tour, day, place), so P0 matches its rows on (tour_id, day_number, lower(place_name)).
- **ECS log retention is 14 days, not 30** (AA-CIS-Infra `modules/ecs/main.tf:250-252`). The 30-day
  look-back for `/admin/atoms` tenant callers comes from the WAF log group (30 days) instead; see
  `admin_atoms_tenant_callers.md`.

## Tradeoffs
- The fallback reader login takes one of aa_app_user's 15 connections for a few seconds; accepted (the
  tenant pool uses at most 1 per api task today), same as probe v2.
- `v_tour_place` is a heavy security-barrier view; the reader query pre-filters on `tour_id = ANY(...)`
  and runs with a 30 s statement timeout inside its own savepoint, so a timeout is recorded, not fatal.
- Item 3 / item 4 are plain counts (no verdict): they are baselines for wave 4 and D5.

- **Item 4 does not filter on `backend_type = 'client backend'` alone**: for other roles' sessions,
  `backend_type` and `state` read NULL without `pg_read_all_stats` (seen on a local PG16 dry run as a
  non-superuser runner), so that filter returned nothing. It keeps rows with a `usename` and a NULL or
  `client backend` type, and excludes the probe's own sessions (`application_name = 's240-aa859-p0'`).
- **The `/admin/atoms` evidence uses WAF header names + a positive control**: WAF logs keep the header
  names after AA-806 redaction, so "Bearer present, X-Admin-Secret absent" identifies the tenant branch
  (which wins in `_resolve_atom_owner_scope` when both are present). A zero only counts if the same
  query finds the portal's legitimate tenant-JWT calls to `/admin/brand-identity`. The second proxy is
  `shared.tenant_api_usage`, which records `/admin/*` calls only when `X-Admin-Secret` matches: the ECS
  200 count minus the DB admin count is the non-admin successes.

## Validation done (S240)
- `python3 -m py_compile` on the probe.
- Dry run against a throwaway local PostgreSQL 16 with stub tables whose columns and types come from
  `db-schema-reference.md` (tour_atoms, tenants, published_tours / raw_tours with FORCE RLS and the 225
  policies, geo.tour_place, angle_gate_*, tenant_tour_pages, subject, quarter_plan(_version), shared.job,
  schema_versions) and `catalog_owner` security-barrier views shaped like v_tour / v_tour_place /
  v_tour_component. The runner was a non-superuser owner, like `aa_cis_admin`. Three runs: the SET ROLE
  refused path (fallback login), the SET ROLE path, and a negative case (an inherited-role grant, a
  column grant on a catalog view, an INSERT granted to PUBLIC, a grant by `catalog_owner` as foreign
  grantor). Each class landed where the D1 rule says, `gate_241_ready` went false in the negative case,
  the D9 counts matched the seeded rows (including the np-only groups and components), and
  `schema_versions` was unchanged afterwards (READ ONLY + rollback).
- After the review fixes, rerun on a fresh local PG16 cluster with the same stub plus a
  `shared.tenant_api_usage` stub: SET ROLE refused + fallback ok; fallback refused by CONNECTION LIMIT
  (`TooManyConnectionsError`); fallback secret read failing; SET ROLE allowed; item 6 table missing;
  the negative case. No run had `fatal`; in the two fallback failures only item 2's view reads were
  errors and items 1, 3-6 were all present; item 6 counted only 30-day admin `/admin/atoms*` rows;
  an item 6 error left `gate_241_ready` true; the negative case still made it false. No probe session
  left open, `schema_versions` and `tenant_api_usage` unchanged.
- Not validated locally: the real `v_tour_place` cost on Dev, and whether RDS lets `aa_cis_admin`
  `SET ROLE aa_app_user` (both paths are handled and recorded in the JSON).

## Should know
- Nothing in the probe writes: READ ONLY transaction, rolled back; `set_config(..., true)` and
  `SET LOCAL ROLE` only inside savepoints that roll back.
- `current_user` of the probe is the api task's DSN user, which is also the DB Migrate runner (the
  workflow runs the api task definition with its `DATABASE_URL` secret), so `runner_acts_for_owner` /
  `runner_acts_for_grantor` predict what 241's `pg_has_role(current_user, ...)` will see. The JSON
  records `identity` so the reader can confirm it.
- WAF log rows recorded before the AA-806 redaction (AA-CIS-Infra #145, 16/10/2026) may hold plaintext
  `Authorization` / `X-Admin-Secret` values: the runbook's queries never output `@message` or header values.
