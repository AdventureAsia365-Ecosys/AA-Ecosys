## Decisions

- **v1.2 is a new file, additive over v1.1** (contracts rule 2). Each leg gains `source_system` (`"cis"`) and
  `source_id` (1..128 chars), **both required keys but nullable together** (`oneOf`): TripPlanner sends both null when
  the tour key cannot be resolved (tour left the catalog, catalog unreadable). Refusing a traveller's hand-off over a
  catalog lookup would lose a customer; the null pair makes the gap visible instead, and Booking retries the lookup
  and reports it. `version` enum is `[1.2]`: payloads labelled 1 / 1.1 are validated by their own files.
- **`source_tour_id` keeps its old meaning** (whatever key the TripPlanner component carries) so v1 / v1.1 readers and
  existing Booking code keep working; the description says not to key on it.
- **Both key kinds accepted when resolving** (`source_id = k OR tour_id::text = k` on `catalog.v_tour`), source_id
  first. S238 read-only check on Dev: `catalog.v_tour` has 892 tours, `source_id <> tour_id` for all of them and no
  value is both a tour_id and another tour's source_id, so the rule is unambiguous; 8 legs / 3 outbox rows today, all
  keyed by a version tour_id, all still in `catalog.v_tour`.
- **Back-fill = Booking legs only**, DRY RUN first, report unmatched. TripPlanner drafts carry no tour key (projected
  from components at read time) and outbox rows are published events already consumed, so they are reported
  (read-only) by the same Booking module, never rewritten.
- **Orphan check in the nightly schema dump** (DM-4.2 names that home): counts only, skipped as `not_applicable` until
  bk-011 exists, warning annotation when orphans > 0, new section in `db-schema-reference.md`.

## Changed vs. the issue

- The bk-011 migration itself does not back-fill (it would tie a Booking migration to the CIS catalog); the
  back-fill is the re-runnable module, run by hand after deploy.
- Glossary wording in `02-data-management.md` §3.3 changed (the `source_tour_id` trap now names the v1.2 / bk-011
  columns), plus the DM-4.2 "Enforced by" cell and the X3 roadmap row (now AA-830).

## Tradeoffs

- A superseded version `tour_id` cannot be mapped by Booking (it may not read `raw_tours`, ADR 0002; `catalog.v_tour`
  is live tours only). Such legs stay unmatched and are listed; running the back-fill soon after bk-011 keeps that
  set at 0 on Dev.
