# AA-928 / AA-930 — CRM integrations are bring-your-own; shared responsibility (S247)

S247, 22/10/2026. Agent: Claude Code (subagent of the S247 orchestrator). Root repo only. Docs only; no AWS, no DB,
no paid calls, no Linear/Jira writes. Direction from Nghiệp (S247): the agency brings its own vendor accounts and is
the data controller; AA builds the connectors, stores credentials encrypted and keeps platform security; legal wording
is a proposal for Ms. Thư.

## Decisions

- **Where the amendment lives.** ADR 0010 is still Proposed, so the BYO rule is a new decision 9 inside 0010 (status
  stays Proposed), not a separate `0010a` file. A separate letter file is for amending an *accepted* ADR (index rule).
  0008a and 0006b get one pointer line each, no decision change.
- **Design errata as a file next to the final design** (`final/errata-s247-byo.md`), linked from a one-line note at
  the top of `crm-design-final.md` and from §6 and §8. The final design is "accepted (S246)"; rewriting its tables in
  place would hide what was accepted. Same pattern as the spec errata (AA-928, #156).
- **"BYO" vs "BYOK".** The design already uses BYOK for customer-managed *encryption keys* (not in v1). The new rule is
  about *vendor accounts*. The ADR names it "BYO integrations" and says BYOK is unchanged, so the two are not confused.
- **Twilio ISV (AA-930 check 11) = resolved by BYO.** The Tech Provider rule applies to a software vendor that
  onboards WhatsApp senders for its customers (Embedded Signup, subaccounts under the vendor). Under BYO AA never
  onboards a sender, never creates a subaccount and never runs Embedded Signup: the agency registers its own sender
  in its own Twilio account through Twilio Self Sign-up, and AA only stores the agency's credentials. The subaccount
  fallback is removed from the design. Residual, written in the check: if Twilio's answer ever says the rule also
  covers software that uses customer-owned credentials, only the WhatsApp half of CRM-28 is re-opened (SMS is not
  affected); the build does not wait for the answer.
- **Stripe: agency's own restricted key first, Connect later (proposed; Nghiệp confirms).** "Connect Standard or own
  keys" were both allowed by the direction. Connect needs an AA Stripe *platform* account (a vendor account held by
  AA, platform review, the platform agreement, and an AA legal entity in a Stripe country) and the legacy Standard type
  is now "controller properties / Accounts v2" in Stripe's docs. A restricted key (`rk_`) created by the agency in its
  own Dashboard needs no AA account at all, and Stripe's own docs recommend restricted keys for third-party sharing.
  So: v1 builds the own-key path; the adapter keeps a Connect slot for later. Listed in `needs_nghiep`.
- **Maps BYO (proposed).** The direction lists maps. The agency may paste its own URL-restricted public map token;
  without one, the builder and the proposal page show the day list with place names and "open in maps" links (no
  embedded map). Mapbox then leaves AA's sub-processor list (it is the agency's processor when connected). Listed in
  `needs_nghiep` because it reverses part of readiness check 10 and touches CRM-20.
- **AA SES = system mail only.** Closed list: invitations and security mail to agency people, one-time codes to
  travellers (portal sign-in, e-sign), operational alerts to agency people. Everything else to travellers (proposal,
  pay reminders, Stage 3 nudges, portal invite, campaigns) leaves from the agency's own mailbox (Gmail, Microsoft 365
  or the agency's SMTP). `allow_platform_sender` (Fix B18) and the `crm-marketing` configuration set are removed.
  Inbound forward-in through AA's SES receipt rule stays: it is receive-only on AA's domain, sends nothing and is the
  only way to receive without a Restricted Gmail scope (CASA).
- **SMTP added** as a third mailbox kind so agencies outside Google/Microsoft are not stuck; send only, the CRM keeps
  its own copy (no IMAP append in v1).
- **AI is not BYO.** AI stays AA's feature on AA's Bedrock (acc3 InvokeModel, Guardrails in acc2 per check 2), AA
  pays inside the per-agency cap, AA is the processor and AWS the sub-processor. No agency-supplied LLM keys. Said in
  the ADR so AA-964 does not drift.
- **AA keeps the OAuth app registrations** (Google client, Microsoft app) and their verification. Those are AA's
  connector identity, not an account held on the agency's behalf; the agency grants access to its own mailbox.
- **Ms. Thư's page** is a neutral survey (5 choices, each with a proposed answer), bilingual side by side, public
  sources only (Tern Terms + Privacy, TravelJoy Terms, WeTravel help, HubSpot Terms + DPA, Stripe docs, iClosed and
  Front help on customer-owned Twilio). Whether counsel is needed is her call; the page says so once, without pressure.

## Tradeoffs

- **Own-key Stripe vs Connect.** Own key: no AA platform account, works today on Dev with the synthetic agency's
  test key, but the agency handles a key (copy/paste, rotation) and the CRM must create its webhook endpoint through
  the key. Connect: smoother OAuth, but AA becomes a Stripe platform with its own obligations. Chose own key first.
- **Campaigns through the agency mailbox** cap volume at the mailbox's daily limit (CRM-36 already spreads a list over
  days). Agencies that need volume connect their own email service by SMTP. AA's sending reputation is never used
  for agency marketing.
- **Maps BYO** makes the proposal page plainer for agencies that skip the token. Accepted: a map is optional, the day
  list is the real content.
