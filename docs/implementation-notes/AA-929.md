## Decisions

- **Version 1.3**, not 2.0: the change adds classes, rows and one rewritten rule (DM-6.8); no rule is removed.
- **DM-6.1 class meanings.** `government_id` = data taken from an identity document (passport / ID number, issuing
  country, nationality, expiry, scans). Date of birth stays `profile` (the existing class), so no Booking column
  changes class. `health` = special-category data, consent-only, closed-list codes. `emergency_contact` = a third
  person's name and phone.
- **DM-6.4 for the new classes.** `government_id` and `emergency_contact` join the "never in a prompt" list (design
  §4.3: Stage 3 data never in an AI view). `health` is out too, except unidentified closed-list dietary / mobility
  codes: that is exactly what the design lets the AI see (F2 flags), so the rule says so instead of forbidding a
  designed flow.
- **DM-6.8 rewritten, not patched.** The old text assumed "a CIS module" and a consented hand-off after which
  Booking creates its own customer (X2, X5). The new text: separate app AA-Partner (ADR 0008a, AA-928); no Booking
  customer (B2B trip case, counts only); ops data stays in `crm.ops_release`; three AA access layers; the honest
  threat model (F2 is joinable by `crm_app` and the master). The X1-era sentence "`aa_cis_admin` can still read
  `crm.*` through `pg_read_all_data`" is replaced by that threat model, because X1 is done and the master is still
  `rds_superuser`.
- **DM-6.2 note.** A CRM traveller is the agency's record (controller), so "no parallel customer profile" does not
  apply. Without the note, DM-6.2 and golden rule 13 read as forbidding `crm.traveler`.
- **DM-7 rows name every planned table** from the design (88 `crm.*` names, checked against the lane's table list
  and design §3.3: no table missing). Reason: the Infra check needs concrete names, and DM-7.1 asks for a row per
  table. Rows are grouped by window, as the existing table does.
- **Windows not in §3.6 are not invented.** `dispatch_queue` and `metric_event` are "proposed in the card that creates
  each table" (nothing is deleted from a proposed row). Audit-evidence tables (`erasure_request`, `export_job`,
  `support_*`, `owner_recovery_request`) are "kept; a window is set before Go-real", the pattern the table already
  uses for `booking.audit_logs`. Reference tables (`fx_rate_platform`, `insight_aggregate`, `release_note`) are kept.
- **DM-7.3 exception.** The archive-before-delete rule would contradict the deletion promise (≤ 30 days) for agency
  data, so the agency data in `crm` is excluded; the audit archive is its only S3 copy.
- **C2.2 row** `crm-api` / `crm_app`: pool 3 × 2 processes (1 task + deploy overlap) = 6 = the limit (C2.3c holds);
  total ~126 → ~132 of the 135 ceiling, as the design computed. Timeouts "set with the pool" (C2.3f), not invented.

## Tradeoffs

- **Planned table names in a binding registry.** Names can change while CRM-04…CRM-37 are built. Accepted: the
  check makes a rename visible (the copy fails until the row is updated), which is the point of DM-7.1.
- **Root PR before Infra copy PR.** The Infra check reads the root `master`, so every future CRM table needs its row
  merged here first. One more step per migration, in exchange for a single registry.
- **Approval wording.** D6 approved the windows; the PR still needs Nghiệp's root-PR approval per "Changing this
  standard". The README version line says both.
