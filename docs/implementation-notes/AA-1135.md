# AA-1135 — Platform › Delivery v2 (root repo part: the collector)

Lane l8-aa1135, S284. The CIS part (custom-range endpoint, settings, page) is in AA-CIS-App
`docs/implementation-notes/AA-1135.md`.

## Decisions

- **One computation, two callers.** The metrics code moved out of `tools/delivery/delivery_metrics.py` into
  `tools/delivery/delivery_engine.py` (pure, stdlib only). The collector keeps GitHub reading, the store files and the
  CLI and re-exports the engine names it used to define (tests and older callers keep `dm.<name>`). CIS computes a custom
  range with a **byte copy** of the engine, so a custom range and a preset of the same window cannot diverge.
- **Guard against drift at runtime, not by convention.** `summary.json` carries `definitions.engine_sha256` (sha256 of
  the engine file) and `config` (the apps.json the summary was computed with). CIS compares its copy's sha256 with the
  published one and refuses a custom range while they differ; presets keep working. `tools/delivery/sync_engine.py
  --cis <checkout>` writes the copy and its lock file; `--check` exits 1 when they differ.
- **`range_block`** is the single windowed function: dora, lead-time segments (now with p95), CI, merge-queue block,
  flaky jobs, verify, the deploys and failed deploys of the window, change counts, the merge-queue section and the git
  activity of the window. The presets (`ranges.d7|d28|d90` per app, `range_presets` in apps.json) and the CIS custom
  range both call it. The existing top-level (28-day headline) keys are unchanged: format 1 stays, new keys only.
- **Deterministic event order.** `Store.of` returns events in (time, id) order. Before, the order was the dict
  insertion order, which differs between the cached store and a store rebuilt from day files; a tie in
  `classify_entries` (`run_url` of the first run) then picked another run (seen on live data: one Partner queue entry).
- **Day files can hold an older copy of an event** (a run that moved to a later day when it finished keeps its first
  copy in the earlier file). `load_events` keeps the copy with the newest time per id, as the store does; the custom
  range prunes events before `store_from` like the collector.
- **The data must match too, not only the code (review fix).** `definitions.store_fingerprint` publishes, per repo,
  the event count and a sha256 of the canonical JSON lines (time, id order) of the store the presets were computed
  from, cut at `store_from`. `custom_range` rebuilds the store from the day files, prunes it the same way and raises
  `StoreMismatch` when the fingerprint differs; CIS answers 409 `out_of_step`. Full content, not only (id, time): a run
  whose result changed without a new time would otherwise pass.
- **How the day files stay in step.** (1) The workflow saves the Actions-cache store only after the S3 upload
  succeeded (and deletes the old entry only after that save): a failed upload leaves the older store, whose next run
  re-reads the same GitHub data and re-uploads those days. (2) A run without a cached store, or a manual run with the
  input `full_day_files`, passes `collect --all-days`: every day of the store window is written, an empty file for a
  day without events, so whatever an older store left on S3 is overwritten. (3) `Store.put` also rewrites the old day of
  an event whose time moved to another day, so a day file never keeps a stale copy from now on.
- Merge-queue charts: `wait_histogram` (bins `queue_wait_bins_h` in apps.json) and `weekly` (merged / ejected / removed
  and the ejection rate per ISO week of the window) in the queue section.

## Changed

- `DEFINITIONS_VERSION` 2026-11-18 (event order; new keys). No metric definition changed.
- `summary.json` grows from about 0.7 MB to about 1.9 MB on live data (three range blocks per app); the CIS reader cap
  is 5 MB.

## Tradeoffs

- The fingerprint hashes the whole store window (about 50 MB of JSON lines) once per summary and once per custom
  range; about a second each on live-sized data. Accepted for a check that turns silent drift into a visible 409.
- A cold store (cache evicted) overwrites the S3 history with the rebuilt, shorter store: S3 then mirrors exactly what
  the presets show; the older days come back as the backfill re-reads them (S3 keeps noncurrent versions 7 days).

- A collector change that touches the engine pauses CIS custom ranges until the CIS copy is synced (one CIS PR running
  `sync_engine.py`). Accepted: a short pause is better than custom numbers that silently disagree with the presets.
- Range thresholds of the root collector (presets, histogram bins) stay in apps.json: the root repo has no settings
  registry (same as AA-1108). The CIS-side cap and cache size are CIS settings.

## Should know

- Verified on a read-only copy of the live day files (scratchpad, not committed): recomputing from the day files gives

- Parity test: `TestRanges.test_custom_range_equals_each_preset` (fixture), plus any window vs the store and the

  event and missing-fingerprint cases, `test_all_days_writes_every_day_of_the_store`.
- Day files written before this change may hold a stale copy (an upload that failed earlier): CIS then says
  "out of step"; repair with a manual run of the workflow with `full_day_files` checked.

## S284 follow-up — the merge-queue recent list is bounded by the window end (lane l13)

- **Decision.** `queue_summary` built `recent` with a lower bound only (still queued, or left after the window start)
  and cut it at `list_cap` (30) before anything else. For a past custom range, the entries that left after the range
  end took every place and the CIS clip then emptied the list. `recent_in_window(e, a, b)` now keeps an entry that left
  inside [a, b), or one still queued that entered before b, and is applied before the cap.
- **Changed.** `tools/delivery/delivery_engine.py` (engine sha256 changes; `DEFINITIONS_VERSION` stays 2026-11-18: no
  count or rate changes, the presets end at the collection time so their lists are the same), tests
  `TestQueueEntries.test_recent_is_bounded_by_the_window_before_the_list_cap` (fails on the old filter) and
  `test_recent_in_window_helper`, the Merge queue table of `docs/guides/delivery-metrics.md` (+ `.vi.md`).
- **Tradeoff.** `in_queue` ("in the queue now") still counts the entries queued at collection time, also for a past
  range: unchanged here.
- **Should know.** Ships with the CIS PR that runs `sync_engine.py --cis` (copy + lock + parity fixture). Between the
  two deploys CIS custom ranges say "paused" (engine sha256 differs): merge both in one wave.
