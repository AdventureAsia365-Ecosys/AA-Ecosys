# AA-1162 — repo change control: agent reviews on the PR, human approval switch, baseline

Root repo part of the remaining scope (the rulesets were set by the orchestrator in S287: root and Partner got
"default branch: no force-push, no deletion (AA-1162)"; all six default branches now block deletion and force-push).
Context: S286 decision D4 (risky PRs need the tech lead's approval from the first pilot with real data), S287
compliance advisory §2.2 item 8 and §5 (agent review is not a human review; Trivy/CodeQL lines of the baseline stale).

## Decisions

- **Agent review as a COMMENT review.** The aa-agent App authors the lane PRs, and GitHub refuses `APPROVE` and
  `REQUEST_CHANGES` from a PR's author. The verdict is the first line of the body (`Agent review: approve | request
  changes | blocking`), so it is still machine-readable for a later compliance collector.
- **Verdict mapping:** blocking = any blocking finding; request changes = a major finding or any reviewer verdict
  `changes`; approve otherwise. Minor findings never change the verdict (as in `tools/workflows/lane.js`, which only
  sends blocking/major findings to the fix pass).
- **Idempotency per head SHA** with a hidden marker `<!-- aa-agent-review head=<sha> -->`; only a review by a `Bot`
  user with that marker is updated (`PUT .../reviews/<id>`), so a human quoting the marker is never edited and a new
  head keeps the older review as history. Marker text inside a finding is escaped (`&lt;!--`).
- **Input = what the lane workflow already returns**: a `wf_` run id or its `journal.jsonl` (review agents are
  labelled `review:<lane>:<i>`, so lens order is recovered; a `fix:` agent marks that a fix pass ran), or a JSON file
  with the lane result `{lane, impl, reviews, fix}`, `reviews[]`, a list or one review. Lens names: per-review `lens`,
  else `--lenses`, else `lens <i>` (the journal does not hold the lens text).
- **No GH_TOKEN, no post.** A run outside `as-app.sh` would post under the logged-in person's account and look like a
  human review; the tool refuses (exit 4). `--dry-run` needs no token.
- **lane.js unchanged.** A `post_review` hint in its live_steps would change the script's output (not doc-only), so
  the orchestrator step is documented in `skill/aa-ship/SKILL.md` §1 instead.
- **Human-approval switch is a committed config file** (`tools/github/change_control.json`), not an env var: a
  switch change is a reviewed root PR with history, and an agent cannot turn it off in its own shell. While ON, a PR
  that changes this file is itself risky. No command-line override.
- **The rule lives in `ship_merge.merge_one`** (new module `change_control.py`), after the check gate and before the
  ECS exec guard and the merge call, so `ship_merge.py`, `ship_wave.py`, `ship_train.py` and `ship_copy_apply.py` all
  apply it, and `--check-only` reports it.
- **Risky =** label `risky` / `change-control: risky`, or a changed file matching `risky_paths` (migrations,
  Terraform/IAM/policies, workflows/actions/CI scripts, `.gitleaks.toml`, git and Claude hooks, `.claude/settings.json`,
  names with secret/auth/permission/rbac/middleware/cognito/erasure/retention/grants). `*.md` never counts. The CI
  bot (`app/aa-ecosys-ci-bot`) is exempt: its PRs copy migrations already approved in their app PR.
- **Review fix pass (six reviewer findings, two of them duplicates, all confirmed):**
  - the merge tools that enforce the rule (`tools/github/*`, `tools/workflows/*`) are now risky paths, so a PR that
    drops the check call or empties `check()` needs the human approval while ON (before, only the JSON file was);
  - a renamed file is classified by its old path too (`previous_filename` in the files read), so renaming a workflow
    to a `.md` file or out of a risky folder is risky;
  - only reviewers with repo access count (`author_association` OWNER / MEMBER / COLLABORATOR; the repos are public
    and any signed-in GitHub user can submit Approve or Request changes), and ON with an empty `approvers` list
    refuses (exit 2). `approvers` stays empty while OFF: the switch-on PR names the tech lead's login, so no personal
    login is committed before it is needed. The tech lead's comments on root read `author_association` MEMBER
    (2026-11-21); if a token ever reads a private membership differently, the tool refuses (fails closed);
  - `post_agent_review.py` redacts every reviewer-written cell (account IDs, ARNs, network resource IDs, e-mails,
    AWS access keys, GitHub/OpenAI-style/Slack tokens) before the body goes onto a public PR;
  - the baseline CodeQL row: root and Infra have completed analyses (Python, JS/TS, Actions) since 2026-11-21
    03:56Z, so the row is "in place" and the gap is gone.
- **Approval =** the latest decisive review (APPROVED / CHANGES_REQUESTED / DISMISSED) of a GitHub user of type
  `User` with repo access, not the PR author, in `approvers` (required while ON), is APPROVED on the gated head commit. Any human's
  latest CHANGES_REQUESTED refuses. A push after the approval needs a new one (the merge is `--match-head-commit` on
  non-queue repos, the queue merges the gated head on the others).

## Changed (vs. the issue)

- The issue asked for "approve / request changes" reviews from the App; GitHub does not allow that on the App's own
  PRs, so it is a comment review with the verdict as its first line (as the lane brief foresaw).
- The trigger is written in aa-ship §1 and implemented now behind the OFF switch, instead of only written.
- `docs/security/baseline.md`: CI security gates (Trivy failing gate + SBOM in CIS, Booking, Partner), a new Code
  scanning (CodeQL) row, branch rules rows (all six rulesets, required check counts from branch protection), merge
  rights (D4 + the switch), and the stale "app repos: no full-history secret scan" sentence.

## Tradeoffs

- Path globs over-classify (for example any file with "auth" in its name). In the strict mode that only costs one
  human approval; under-classifying would defeat the control. Labels cover what paths miss.
- The rule is enforced by our merge tool, not by GitHub (a ruleset with a required approving review would also block
  the CI bot and every agent PR today). A person with admin rights can still merge by hand on GitHub; the access
  review and the human-review collector of the compliance plan watch that.
- Paginated `gh api --jq` output is one JSON array per page, parsed with the shared `_parse_paged_arrays`.
