# AA-1106 — Feature and integration catalogue (root repo part)

Companion of the AA-CIS-App branch `feat/aa1106-product-map` (the admin page Platform › Product map).

## Decisions

- **Location: the root repo, `docs/catalogue/`** (the issue: "two machine-readable catalogues in the root repo, the
  single source"). `features.yaml` holds the apps, the features and the journeys (a third file for journeys was not
  worth it: they reference features and integrations only); `integrations.yaml` holds the links.
- **Feature ids by app prefix**: `CIS-F`, `BK-F`, `CRM-F` (AA-Partner: CRM and the Content studio, one deployable app),
  `TP-F`, `INF-F`. The Content studio *API* lives in CIS (`CIS-F040..047`) and its *pages* in AA-Partner
  (`CRM-F040..046`), joined by `depends_on`.
- **Granularity**: one feature per module or page group (116 features), not per page; every page and API route group
  is still mapped through the `surface` patterns, so the guard sees each one.
- **The code surface comes from a committed snapshot** (`surface.snapshot.json`, `tools/catalogue/surface.py`), the
  pattern of `docs/generated/llm-routes.snapshot.json`: the app code is in four other repos, so a pull request check of
  the root repo cannot read it. A nightly job of the `Catalogue` workflow checks the four public app repos out (sparse:
  pages, routers, settings registries, CIS migrations) and fails when the snapshot is stale, so a new page or router
  without a feature shows up within a day.
- **What counts as an API route group**: a router module with at least one route decorator (CIS `api/routers`, Booking
  `backend/app/routers`, AA-Partner `api/app/routers`, `_`-prefixed helper modules skipped); for TripPlanner the first
  segment under `frontend/app/api` (`bff/<x>`) and each Lambda folder with a `handler.py` (`lambda/<x>`).
- **Settings named in conditions must exist in a registry**: CIS + TripPlanner (`shared/settings/compiled_defaults.json`),
  CRM (`api/app/platform_settings/compiled_defaults.json`) and Booking's pricing policy params, named
  `booking.policy.<key>` (Booking keeps its own maker-checker page, no registry key format of its own).
- **Plan or add-on conditions are the entitlement feature keys** of `shared.entitlement_feature` (CIS 355), read from
  the CIS migrations; apps check feature keys, never plan names (`tenant.entitlements.v1`).
- **Secrets by name only**, each must appear in `docs/security/secrets-register.md`; connections must exist in the
  llm-routes snapshot.
- **UAT rows carry `features`**: an optional field in `tools/uat/lib/catalogue.cjs` (so the UAT tools stay
  independent); the catalogue guard requires it on every row that is not retired. All 146 rows tagged
  (script kept at `.tmp-session/S280/aa1106/uat_features.py`, not committed).
- **Publishing**: the `Docs sync` workflow builds `catalogue.json` next to the docs manifest and uploads it under the
  same `docs-reader/` prefix, so no new IAM, bucket or table. A failing catalogue never blocks the docs pages: the step
  is `continue-on-error` and the upload is skipped with a warning.
- **Integration status** is what the code does on Dev today (e.g. `catalog.tour.v1.3`, `lead.submitted.v1`,
  `tenant.entitlements.v1` are served), not the older "planned until applied" text of the contracts registry table.

### Fix round (independent review)

- **No `paths:` filter on the guard's `pull_request` trigger.** A required check whose workflow a path filter skipped
  stays "Expected" on GitHub, which would block every other root PR, including the auto-merging
  `bot/db-schema-reference` PRs and the root merge tool (it wants every check green). The job takes about a minute, so
  running it on every PR is cheaper than an always-green shim job. It also closes a gap: rule C6 reads guide pages
  anywhere under `docs/` and `tools/docs/build_docs_reader.py`, so a docs-only PR that renames, demotes or moves a
  guide page now fails here instead of silently stopping the catalogue upload in Docs sync (that step only warns).
- **INT-013 `trip_case.status_changed.v1` is `retired`, not `planned`.** It was the answer to `inquiry.submitted`,
  which has had no consumer since the move to agencies only (root ADR 0019 d8, AA-1046); agencies follow trips in the
  CRM through `lead.submitted.v1`. No contract file was ever published, so none is added. The tech lead should confirm
  in the YAML review; reviving it would mean a new design anyway.
- **`docs/contracts/README.md` status column brought in line with `integrations.yaml`.** 21 stale cells ("planned until
  CIS nnn is applied", "proposed") now start with the current status and keep the old text after "Was:", the format the
  retired rows already use. Evidence for each: the view or column in the live schema dump of 14/11/2026 (CIS 417,
  tp-031, bk-057), or the serving router on main.

## Changed

- New: `docs/catalogue/{README.md,features.yaml,integrations.yaml,surface.snapshot.json}`,
  `tools/catalogue/{catalogue.py,surface.py,test_catalogue.py}`, `.github/workflows/catalogue.yml`.
- `tools/uat/catalogue.json`: `features` on every row; `tools/uat/lib/catalogue.cjs`: `features` optional field.
- `.github/workflows/docs-sync.yml`: builds and uploads `catalogue.json`; also runs on `tools/catalogue/catalogue.py`
  and `tools/uat/catalogue.json` changes.
- `docs/README.md`: catalog row ARCH-07 (contracts catalog) links the catalogue page (`ARCH-07-catalogue`). Not
  ARCH-03 (service catalog): that id prefix is owner-only in the docs reader, and every admin should open this page.
- A feature `guide` must be a published staff-tier docs reader page (the guard imports the docs reader's own
  publication rules), so the Product map never links a page an admin cannot open.

## Tradeoffs

- A snapshot can lag the code by up to a day (nightly job) instead of failing the app PR itself. Making each app repo
  check out the root catalogue would put a cross-repo dependency in four CI pipelines; the nightly job keeps the
  dependency one-way.
- Every feature now has `summary_vi` too (fix round), required by the guard like `name_vi`, so the business-owner view
  reads fully in Vietnamese. It sits before `summary` in the YAML so the few multi-line English summaries stay untouched.
- No Backstage server; only its entity vocabulary (System / Component / API, provides / consumes).
