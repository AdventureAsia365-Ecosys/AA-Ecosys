# AA-1193 — Auto-rollback of the API deploys (whole picture + root part)

Session S297, lane l5-rollback. Source: S295 Well-Architected review, OPS06 (the smoke-red rollback of AA-1119 ran in
the four web deploys only; an API build that starts and passes its health check but breaks a real check kept
serving). Cost 0 USD.

## What ships, by repo (merge order)

1. **AA-CIS-Infra**: `accounts/aa365/cicd_deploy_alerts.tf`, `sns:Publish` on the alerts topic for the three API deploy
   roles. Booking + CRM applied by Terraform Apply (CI); the CIS role is bootstrap: local MFA admin apply with
   `-target=aws_iam_role_policy.cis_app_deploy_publish_alerts`. The app PRs work without it (the alert logs "not sent"
   as a warning), so the order is a preference, not a chain.
2. **AA-CIS-App**: `deploy-dev.yml` (record api + worker revisions, `rollback`, `report`, drill input),
   `post-deploy-verify.yml` (drill step, `failed_checks` output), `post_deploy_verify.sh` (`VERIFY_FAILED_FILE`), new
   `.github/scripts/ecs_api_rollback.py` + test.
3. **AA-Booking** and **AA-Partner**: the same for `aa-booking-dev-api` / `aa-crm-dev-api` (one service each; byte
   copies of the new script and test; `post_deploy_verify.sh` stays byte-equal between the two).
4. **Root (this PR)**: runbooks rollback-ecs / rollback-cis / rollback-booking, ops README, these notes.

## Decisions

- **Reuse, do not fork**: `ecs_smoke_rollback.py` (AA-1119, byte copy in four repos) is unchanged; the new
  `ecs_api_rollback.py` imports it for every per-service rule and adds the API parts: several targets all-or-none,
  the health `git_sha` check, the SNS alert. Changing the shared script would have pulled AA-TripPlanner-Web in.
- **All or none for CIS**: api and worker run one image; every target is dry-run first and one refusal writes nothing.
  The dry run also refuses when the targets' previous revisions are different builds (a worker left behind on an older
  build): rolling back would bring them back split while `/health`, which reads the api only, looked green (S297
  review finding).
- **Deploy gate respected the same way as the roll**: the rollback re-runs the app's own guard (CIS
  `deploy_job_guard.sh`, Booking `booking-deploy-preflight.sh`, Partner `partner-deploy-preflight.sh`) with the run's
  `override_running_jobs`. A held gate (wave open, deploy-blocking job, ECS exec heartbeat, gate unreachable) means no
  rollback; the alert and the issue say so and point at the hand runbooks.
- **Alert channel**: the alerts SNS topic (the ops topic of every alarm and in-app check), ticket severity, not the
  page topic. The ARN comes from the task definition's `ALERTS_TOPIC_ARN` (Terraform sets it on the three API tasks),
  so no GitHub variable is added; it is never printed. The `deploy-smoke-red` GitHub issue of AA-1119 is kept too.
- **CIS outputs hold revision numbers only**: the CIS family names are the `ECS_SERVICE` repo secret, and GitHub drops
  a job output that contains a secret value (the AA-725 part 5 trap); the outcome output says `api` / `worker`.
- **Drill without a broken build**: dispatch input `drill_force_smoke_fail`. The verify runs every real check, then a
  drill step turns it red, so the real rollback, alert and issue run. The deploy job refuses the drill before the roll
  when Dev already runs the dispatched commit (no older build to return to). The OIDC trust of the deploy roles pins
  `ref = refs/heads/main`, so the drill runs on `main`, not on a throwaway branch: it needs `main` one commit ahead of
  what Dev runs (a commit that does not deploy, e.g. docs only). For CIS, merging the CIS PR itself is such a commit
  (workflow files are outside the push paths).
- **Never a loop**: the rollback is an `update-service` to an existing revision; nothing is built, pushed or
  dispatched. A re-run is a no-op.

## Tradeoffs

- A flaky verify now rolls back a good build (the AA-1119 trade-off); the next deploy of main brings it back.
- The rollback's health retries (6 x 10 s) are CLI defaults in the CI script, like `VERIFY_TRIES` of the verify: the
  CI runner has no admin settings store. Follow-up only if the tech lead wants them editable.
- No schema rollback (out of scope): migrations only go forward; expand migrations keep the previous build working.

## Should know

- The drill per app is the Done evidence of the issue: run summary (rollback outcome, `/health` on the old commit),
  the alert e-mail (subject `[aa-deploy drill] ...`), `aws ecs describe-services` before/after.
- Before the Infra apply, the alert step warns "not sent"; apply first if the drill should prove the alert too.
