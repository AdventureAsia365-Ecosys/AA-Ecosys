# AA-1111 — Implementation notes (root repo, lane l14-zap: ZAP baseline)

Scope of this lane: the "one OWASP ZAP baseline run, triaged" item of AA-1111. Local Docker is not available, so the
scan runs in GitHub Actions in the root repo. The other AA-1111 items (admin MFA, access review, account guards,
agent role, fork-PR approval) are not in this lane.

## Decisions

- **Official action, passive only.** `zaproxy/action-baseline` v0.15.0, pinned to its commit
  `de8ad967…` (tag object dereferenced) with `# v0.15.0`, as WL6 requires. It runs `zap-baseline.py`: spider plus
  passive rules, no attack payload. `action-full-scan` and `action-api-scan` are named in the workflow header as
  out of bounds.
- **ZAP image pinned by tag and digest** (`ghcr.io/zaproxy/zaproxy:2.17.0@sha256:9624…`, the same digest as
  `stable` on 17/11/2026; 2.17.0 was released 15/12/2025). The action's default `:stable` would move under us.
- **Artifact retention 7 days without `actions: write`.** The action always uploads its own artifact with the
  repository default retention (its `uploadArtifacts` passes no options). The next step uploads the same three files
  under the same name with `actions/upload-artifact` `overwrite: true` and `retention-days: 7`; overwrite deletes the
  earlier artifact with the runtime token, so `permissions: contents: read` stays the only grant.
- **Nothing in the run summary.** The repo is public; ZAP's own log lines are unavoidable, but the workflow adds no
  alert table to the summary. Findings are triaged from the downloaded artifacts.
- **Job name `ZAP baseline <id>`** with a fixed prefix before the matrix value (lesson S273, root #642).
- **Concurrency group `zap-baseline`, no cancel**: a second dispatch waits instead of killing a scan halfway.
- **`tools/security/zap_summary.py`** is stdlib only and reads every `*.json` with a ZAP `site` list under a folder,
  naming the target after its artifact folder (`zap-` dropped), so the two TripPlanner targets (same host) stay apart.
  Three sections: counts per target and risk, the same alert across targets (to spot one-fix-at-the-edge header
  gaps), and per-target tables with example URIs. Pipes and line breaks in cells are escaped.
- **Docs**: a "Dynamic scan (OWASP ZAP baseline)" section in SEC-03 (`docs/security/vulnerability-management.md`)
  plus a row in "Where findings come from", not a new page: SEC-03 is where findings and fix times live, and the
  index page `docs/security/README.md` is being edited by another S283 lane.

## Changed

- `tools/github/actions-allowlist.txt`: `zaproxy/action-baseline@*`. This file is only the record; the org setting is
  the org owner's hand step (without it the run fails at "Set up job").
- `tools/github/pin_freshness.py`: an image tag with no prefix (`2.17.0`) now also matches upstream release tags with
  a `v` (`v2.17.0`), exact prefix first. Without it the weekly pin check would report the ZAP pin as "unknown" (exit 2)
  because ZAP's releases are tagged `v2.17.0` and its weekly builds `w<date>`. Two tests added.
- `.github/workflows/docs-lint.yml`: `tools/security/**` in the paths filter and a "Security tools tests" step.

## Tradeoffs

- Running the ZAP Docker image directly (no third-party action) would avoid the allow-list change and the overwrite
  trick, but the brief asked for the official action, which also handles ZAP's exit codes and report names.
- `fail_action: false`: a finding never turns the run red. A red job therefore means the scan itself failed.
- No rules file yet: false positives are decided at the first triage; a `rules_file_name` TSV can follow.

## Should know

  (ADR 0021 decision 4), not an app setting.
- The fixtures in `tools/security/testdata/` follow the ZAP 2.17 `-J` report shape with invented `example.test`
  hosts; no real report was recorded locally (no Docker). The first real run should be checked against the summary

- Locally two `tools/github` tests fail on this machine before and after this change (they expect no locally
  installed gitleaks: `test_git_env_isolation` pre-push self-test and `test_ship_open_prs` gitleaks resolution).
  They do not touch the files of this lane.

## S294 follow-ups (lane l6-sec-hygiene)

### Decisions

- **WL9 in `tools/github/ci_hygiene.py`: `curl ... | grep -q` is a finding.** `grep -q` exits at the first match and
  closes the pipe; curl, still writing, dies of SIGPIPE (exit 23) and `pipefail` fails the step although the text was
  there (S272 TP #240; the Partner CSP smoke had the same shape). The rule joins backslash continuations, skips comment
  lines, splits a line into pipelines on `||` / `&&` / `;` and flags a pipeline where a segment that runs curl is
  followed by a segment that runs grep with `-q` / `--quiet` / `--silent` (short options may be clustered; the value of
  `-e`, `-f`, `-m`, ... is skipped, so `grep -e -q` is not quiet). It flags whatever the shell: a step without
  `pipefail` today can gain it later.
- **Failing in the root Workflow Lint, RED in the daily run.** `--pipe-scan <checkout>` prints `::error` annotations
  and exits 1 (a new step in `.github/workflows/workflow-lint.yml`); `collect()` adds `wl9` to every repo's row and
  makes the repo RED, and `hygiene_issues.py` opens one `curl-pipe-grep` issue for it. All six repos are clean once the
  Partner change of this lane is merged (Partner `ci.yml` was the only hit).
- **The lesson moved to `skill/aa-lessons/guards.md`** (it was `Guard: pending AA-1024`); the guard covers the class.

### Should know

- The rule reads text, not a parsed shell: a `|` inside a quoted grep pattern splits the segment, which can only make
  the grep segment shorter (still detected) or a non-grep segment; a `curl` word inside a quoted `echo` before a quiet
  grep would be a false positive (none in the six repos).
