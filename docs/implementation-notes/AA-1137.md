# AA-1137 — Implementation notes (root repo, lane l3-root-spec, S285)

Source: the S284 hooks and spec advisory, section 5 and slice 3 (`docs/audits/2026-11-18-S284-hooks-spec-advisory/`).
Spec of this issue (the first one, also the committed sample the tests use): `.kiro/specs/AA-1137-spec-trace/`.

## Decisions

- **The spec of this issue is the sample.** `.kiro/specs/AA-1137-spec-trace/` is a real feature spec (status
  in-progress, approved with the S285 session list), so the Spec trace run of this PR checks a real spec and the
  tests use it as a passing fixture. T7 (app-repo callers) and T8 (TripPlanner orphan spec) stay open for the next wave.
- **Folder name and id.** `.kiro/specs/AA-<n>-<slug>/`, front-matter `id: spec-AA-<n>` (one issue, one spec); the
  checker refuses a folder or id that does not match `issue`.
- **Requirement line format.** `R<n>.<m>` criteria (a `### R1 <group>` heading is only a group), one Verify line with
  `;`-separated items: a path (or `test: ...`) is a test, `live: ...` is a live step; anything else is an error, so
  "ask someone" cannot pass as verification. A criterion may wrap onto indented lines before its Verify line.
- **Task refs.** `_Requirements: R1.1, R1.2_` (Kiro's third-party convention); `1.1` (Kiro style) and `R1` (every R1.x)
  resolve too. A dropped task needs no ref; a carried task names the issue (`carried -> AA-<n>`).
- **bugfix.md.** A bugfix spec may name its requirements file `bugfix.md` (Kiro's name); both files at once is an error.
- **Design approval.** Each decision carries `Hard to reverse: yes|no`; a `yes` needs an `Approved:` line once the
  spec is in-progress (the tech lead approves those on the session decision page). Draft specs may wait.
- **Frozen.** With `--base`, a spec whose base `requirements.md` was implemented or archived may only change its
  status line to archived; any other change (a new file too) is an error. A move into `_archive/` is a new path and
  is not compared (the archive move happens at the session close, together with status archived).
- **Public safety.** The checker reuses the resource-ID lint patterns (`tools/docs/check_docs_text.py`) plus the AWS
  access key pattern of the docs reader redaction; the docs lint also scans `.kiro/specs` in error mode (`--scope`).
- **PR mode.** Issue keys from the PR title and body (merge queue: the group's commit messages) plus every spec the
  PR changes; none found = pass. A caller repo's specs come from its checkout, the root's from a sparse checkout of
  AA-Ecosys at `tools-ref` (`--extra-root`).
- **Lane claims.** `lane_start_guard.py` records claimed tasks in `.tmp-session/spec-claims.json` only after every
  gate passed (a refused launch claims nothing). Claims of an earlier session are stale; the same lane key relaunching
  passes; `spec_gate: "skip: <reason>"` passes the spec gate only. A replay (`resumeFromRunId`) skips the spec gate.
- **lane.js cannot read files** (it runs in the Workflow harness), so the brief tells the agent to print its tasks
  and requirements with `trace_check.py show`; the trace is required in the implement and fix schemas only when a spec
  is given, and the spec lens is appended to custom lenses unless one already starts with "spec".

## Tradeoffs

- **Spec trace runs on every root PR (no `paths:`)**: it must see the PR body, and a path filter would also break a
  required check in a merge queue later. It costs about 20 s and passes at once without a spec.
- **Uncovered requirement is a warning**, not an error: a bugfix spec lists unchanged behaviour that no task builds.
- **Test paths are not checked for existence**: tests may live in another repo or not exist before the lane runs.
- **The docs reader bundle does not publish specs yet** (advisory 5.1, docs-sync): the same ID patterns guard them
  in the checker and the docs lint; publishing them in `/admin/docs` is a follow-up.
- **The generic kit skill (`skill/kit/project-issue`) is not changed**: the spec flow is tried on AA issues first.

  and `merge_group`; a required job there needs `merge_group` and no `paths:`.
- The orchestrator ticks root-spec tasks (T7, T8 here) in the root PR of the session that finishes them, and sets
  `status: implemented` when the last one merges.
