# AA-1084 — Implementation notes (root repo, lane l22: ship tools and lane rule)

This file covers the root-repo part of AA-1084: the stacked-branch handling in `tools/github/ship_wave.py`, the lane
rule in `tools/workflows/lane.js`, and the ship skill and lessons log. The CIS CI part (duration refresh, four unit
shards) is a separate lane in AA-CIS-App with its own notes.

## Decisions

- **Merge, not rebase.** The tool merges `origin/<default>` into the code branch and pushes without force. A rebase
  needs a force push (lease) and rewrites commits other people or bots may have built on; a merge keeps the PR's
  history and the squash merge flattens it anyway. `ship_train.py` keeps its rebase for explicit stacked trains.
- **Detection = "the head changes a migration file that the default branch already has".** The tool diffs
  `origin/<default>...head` (merge base to head, `--diff-filter=AM`, no renames), keeps paths matching
  `(^|/)migrations/[^/]+\.sql$` (CIS / Partner `api/migrations/`, Booking / TripPlanner `migrations/`; not
  `migrations/tests/`), and keeps those that exist on `origin/<default>`. A code PR's own new migration (not yet on
  main) is not a stacked one and is left alone.
- **Only for held PRs (`@after=`), only after the apply, only before the gate.** Independent PRs and `--check-only`
  are never touched. One branch update at a time per repo (shared clone; the CIS pre-push is heavy).
- **Worktree choice.** Reuse the lane worktree only when it has exactly that branch checked out at exactly the PR
  head, no modified tracked file and no merge/rebase in progress; never the main checkout. Otherwise a temporary
  detached worktree `.tmp-session/wt/ship-wave-<repo>-<n>-<pid>` at the PR head.
- **Pre-push like `ship_open_prs.py`.** Push through `as-app.sh` with `core.hooksPath=<safe-hooks>`, so the repo's
  pre-push runs (and `AA_PREPUSH_PYTHON` / `AA_PREPUSH_SKIP_INTEGRATION` keep their meaning); a refused push reports
  `push_failure_reason`. For CIS, `scripts/pre-push.sh --integration` runs first on the merged code, because the
  stamp key names the changed files and the merge drops the migration from the diff.
- **The gate checks the pushed head** (`expect_head`), so an old green run on the pre-merge head is never accepted.

## Tradeoffs

- A merge commit in the PR branch is noise in the PR view, but the squash merge removes it on main; no force push is
  worth more than a linear PR history.
- The CIS integration run adds minutes per stacked PR; skipping it would make the push fail at the hook. The lane
  rule removes the stacked case at the source, so the tool path is a safety net, not the normal path.

## Should know

- Failure paths (exit 4, that PR only): merge conflict (merge aborted, nothing pushed, conflicting files named), the
  migration still differing from main after the merge (the code PR changes an applied migration), a failed
  integration run or a refused push (the merge is kept in the worktree for a hand fix; a temporary worktree is kept
  only in these cases and must be removed by hand after).
- Unit tests mock git/gh through the scripted runner (`test_ship_wave.py`, `StackedBranchTest` and the held-PR
  tests in the wave test class). Live proof is the next chain shipped with `ship_wave.py` needing no hand merge.
