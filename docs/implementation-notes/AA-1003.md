# AA-1003 — Report core R1: registry (root part)

Slice R1 of the AA-1001 report catalog (`docs/audits/2026-10-29-S258-report-catalog/`, README §6-7,
`automation-plan.md`). This file covers the root repo part; the CIS engine (migration, job kinds, admin API and page)
has its own notes in AA-CIS-App `docs/implementation-notes/AA-1003.md`.

## Decisions

- **The YAML is the source of truth from now on.** `docs/reports/catalog.yaml` and `docs/reports/kpis.yaml` were
  imported once from the advisory `catalog.json` by `tools/docs/report_registry.py import`; the importer refuses to
  overwrite the files without `--force`, so hand edits are not lost by accident. The advisory JSON stays as history.
- **One tool, two subcommands** (`check`, `import`) in `tools/docs/` so the existing Docs lint job runs its tests
  (`test_*.py` discovery) and its path filter (`tools/docs/**`, `docs/**`) already covers both files. Root only, not
  vendored.
- **Machine fields added to the catalog**: `schedule` (normalised from the free-text `cadence`: hourly, daily, weekly,
  monthly, quarterly, live, event, on_demand), `generator` (`cis` = the CIS engine renders it; R1: EX-04, EX-06),
  `decision` and `sections` (kept from the advisory: the CIS page shows them, the generator prints the sections).
  `status_today` became `status`.
- **Templates** point at `docs/audits/2026-10-29-S258-report-catalog/templates/` until roadmap R0 moves them to
  `docs/templates/`. The mapping is the `automation-plan.md` §6 table; a report listed by two templates gets its
  family's template (OPS-14 → app-ops, DATA-02 → data-quality). 43 of 63 reports have one; agency/tenant reports and
  the scorecard pages have none.
- **KPI IDs**: the catalog's `K-…` IDs are kept. KPIs listed as a pair (`K-TP-TRIPS / K-TP-INQ`, `K-BK-INQ /
  K-BK-CONF`) are split into two entries with readable names. The agency reports (CIS-04, CRM-01..06) name KPIs without
  an ID: they get `K-<REPORT>-<SLUG>` (for example `K-CRM01-WIN-RATE`); a "Defined in CRM-01" reuse points at the same ID.
- **Canonical definition**: an entry marked "(canonical definition)" wins, else the first definition that is not a
  "Defined in …" reference. Per-report thresholds that differ from the canonical one are kept in `report_thresholds`.
- **Units** were inferred from the KPI name at import (count, ratio, usd, seconds, hours, days, score, status) and are
  provisional for every KPI nothing computes yet; the six KPIs the CIS snapshot computes in R1 have exact units,
  a `snapshot` block (job, scopes, what is computed) and, where the catalog gives numeric bounds, an `alert` block.
- **Sources**: every `schema.relation` a definition names is extracted into `sources` and checked against the live
  schema reference. Only `shared.report_run` (created by CIS 305) is not there yet, so it is in `planned_sources`. A
  planned source that later appears in the reference is a warning, never an error, so the DB Schema Dump bot PR (which
  must be green to auto-merge, ADR 0017 d9) never fails on it.
- **Retention row** for `shared.kpi_daily` and `shared.report_run` added to data standards Part B §7 (DM-7.1: same
  change as the table; root PR before the Infra copy).
- **No new doc IDs registered.** README §9 item 4 (PLAT-03, APP-11.., OPS-12.., SEC-08..) belongs to the template move
  of R0; the registry files are YAML, not catalog pages, and need no front-matter ID.

## Changed (vs the issue text)

- The lint lives in `tools/docs/report_registry.py`, not `tools/reports/` (the Docs lint job and its test discovery
  already run there).
- KPI entries carry more than "id, definition, unit, source, threshold": also `version`, `name`, `defined_in`,
  `used_by`, optional `report_thresholds`, `snapshot`, `alert`.

## Tradeoffs

- Inferred units are wrong for some KPIs (the name is the only signal). Correcting all 229 by hand now buys nothing:
  the unit matters only once a job computes the KPI, and each slice that builds one sets it.
- The CIS app reads a vendored byte copy, not the root file (the root repo is a separate repo; the docs bundle sync to
  S3 would need a root workflow change and an Infra permission). `report_registry.py check --copy <CIS dir>` compares
  them; keeping them equal is a session rule until the registry moves into the docs bundle.

## Should know

- `python3 tools/docs/report_registry.py check` runs in the Docs lint job (step "Report registry").
- Re-running `import --force` throws away hand edits; only do it to re-import a new advisory version.
