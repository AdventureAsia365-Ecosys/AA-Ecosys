# AA-1003 — Report core R1: registry (root part)

Slice R1 of the AA-1001 report catalog (`docs/audits/2026-10-29-S258-report-catalog/`, README §6-7,
`automation-plan.md`). This file covers the root repo part; the CIS engine (migration, job kinds, admin API and page)
has its own notes in AA-CIS-App `docs/implementation-notes/AA-1003.md`.

## Decisions

- **The YAML is the source of truth from now on.** `docs/reports/catalog.yaml` and `docs/reports/kpis.yaml` were
  imported once from the advisory `catalog.json` by `tools/docs/report_registry.py import`; the importer refuses to
  overwrite the files without `--force`, so hand edits are not lost by accident. The advisory JSON stays as history.
- **One tool, two subcommands** (`check`, `import`) in `tools/docs/` so the existing Docs lint job runs its tests
  (`test_*.py` discovery) and its path filter (`tools/docs/**`, `docs/**`) already covers both files. Root only, not
  vendored.
- **Machine fields added to the catalog**: `schedule` (normalised from the free-text `cadence`: hourly, daily, weekly,
  monthly, quarterly, live, event, on_demand), `generator` (`cis` = the CIS engine renders it; R1: EX-04, EX-06),
  `decision` and `sections` (kept from the advisory: the CIS page shows them, the generator prints the sections).
  `status_today` became `status`.
- **Templates** point at `docs/audits/2026-10-29-S258-report-catalog/templates/` until roadmap R0 moves them to
  `docs/templates/`. The mapping is the `automation-plan.md` §6 table; a report listed by two templates gets its
  family's template (OPS-14 → app-ops, DATA-02 → data-quality). 43 of 63 reports have one; agency/tenant reports and
  the scorecard pages have none.
- **KPI IDs**: the catalog's `K-…` IDs are kept. KPIs listed as a pair (`K-TP-TRIPS / K-TP-INQ`, `K-BK-INQ /
  K-BK-CONF`) are split into two entries with readable names. The agency reports (CIS-04, CRM-01..06) name KPIs without
  an ID: they get `K-<REPORT>-<SLUG>` (for example `K-CRM01-WIN-RATE`); a "Defined in CRM-01" reuse points at the same ID.
- **Canonical definition**: an entry marked "(canonical definition)" wins, else the first definition that is not a
  "Defined in …" reference. Per-report thresholds that differ from the canonical one are kept in `report_thresholds`.
- **Units** were inferred from the KPI name at import (count, ratio, usd, seconds, hours, days, score, status) and are
  provisional for every KPI nothing computes yet; the six KPIs the CIS snapshot computes in R1 have exact units,
  a `snapshot` block (job, scopes, what is computed) and, where the catalog gives numeric bounds, an `alert` block.
- **Unit guess, whole words.** The time words (`time to`, `lead time`, `age`, `ttr`, `ttd`) match whole words only:
  as substrings, "age" typed coverage, overage, average and storage KPIs as hours. After the fix and a re-import
  (before any hand edit, so nothing was lost) 11 KPIs changed unit: K-CAT-COVER, K-GEO-TOURPLACE, K-SEO-COVER,
  K-CAT-S1, K-BILL-OVERAGE, K-PRIV-CONSENT, K-VEND-DPA, K-UAT-COVER, K-SNAP-COVERAGE → ratio, K-AIQ-SCORE → score,
  K-CAP-STORAGE → count.
- **K-CAT-LIVE counts state `served`.** `gold_aa_internal.v_tour_liveness` (CIS 272) yields served / paused / retired,
  never `live`; the advisory wording "state 'live'" is replaced through an optional `definition` in `SNAPSHOT_KPIS`
  (a snapshot KPI's definition is what the job computes), and its `computes` text says `served` too.
- **Text scrubbed for the public CIS copy** (`REPLACEMENTS`): person handles become roles, and the retired personal
  account is not named (the CIS guard test `test_aa998_no_acc1_runtime` scans the vendored copy).
- **Alert bounds**: the lint accepts only numeric `amber_gte` / `red_gte` (the only keys the CIS engine reads); a test
  pins that a `red_lte` is an error. The CIS parser refuses other keys too.
- **Sources**: every `schema.relation` a definition names is extracted into `sources` and checked against the live
  schema reference. Only `shared.report_run` (created by CIS 305) is not there yet, so it is in `planned_sources`. A
  planned source that later appears in the reference is a warning, never an error, so the DB Schema Dump bot PR (which
  must be green to auto-merge, ADR 0017 d9) never fails on it.
- **Retention row** for `shared.kpi_daily` and `shared.report_run` added to data standards Part B §7 (DM-7.1: same
  change as the table; root PR before the Infra copy).
- **No new doc IDs registered.** README §9 item 4 (PLAT-03, APP-11.., OPS-12.., SEC-08..) belongs to the template move
  of R0; the registry files are YAML, not catalog pages, and need no front-matter ID.

## Changed (vs the issue text)

- The lint lives in `tools/docs/report_registry.py`, not `tools/reports/` (the Docs lint job and its test discovery
  already run there).
- KPI entries carry more than "id, definition, unit, source, threshold": also `version`, `name`, `defined_in`,
  `used_by`, optional `report_thresholds`, `snapshot`, `alert`.

## Tradeoffs

- Inferred units are wrong for some KPIs (the name is the only signal). Correcting all 229 by hand now buys nothing:
  the unit matters only once a job computes the KPI, and each slice that builds one sets it.
- The CIS app reads a vendored byte copy, not the root file (the root repo is a separate repo; the docs bundle sync to
  S3 would need a root workflow change and an Infra permission). `report_registry.py check --copy <CIS dir>` compares
  them; keeping them equal is a session rule until the registry moves into the docs bundle.

## Should know

- `python3 tools/docs/report_registry.py check` runs in the Docs lint job (step "Report registry").
- Re-running `import --force` throws away hand edits; only do it to re-import a new advisory version. Until the first
  hand edit it is reproducible: `import --force` on this branch leaves both files byte-identical.
- After any change here, copy both files to AA-CIS-App `services/reports/registry/` in the same session and run
  `check --copy` (the CIS copy of this branch is in sync).

# R7 (S283) — growth, customers, forecasts: catalog status (root part)

Slice R7 of the S258 roadmap (MKT-01, MKT-02, CX-01, BK-02, BK-04, BK-05, BK-06, CIS-02, TP-02, OPS-16, EX-05),
re-scoped under root ADR 0019 (B2B only). This slice decides each report's catalog status; it builds no generator.
The CIS part (registry parse of `trigger`, EX-06 "Catalogue status" section, byte copy) is in AA-CIS-App
`docs/implementation-notes/AA-1003.md`.

## Decisions

- **New optional field `trigger`** on a report: the business milestone or event that starts building it, in words.
  Lint (`report_registry.py check`): required for status `planned`; allowed on any other report with
  `generator: null`; refused on a retired report and on a report the CIS engine renders. EX-06 prints it.
- **Re-pointed to B2B, status planned with a trigger:**
  - MKT-01 → "Agency growth and acquisition": new agencies (K-MKT-SOURCE v2, `shared.tenants`), trial to paid
    (K-MKT-CONV v2, `shared.tenant_subscription`), sign-up source (K-MKT-CUSTSRC v3, "source not recorded" until the
    agency record has one), CRM agencies by state through `crm.ops.v1` (`/tenants`, `/data-coverage`).
  - EX-05 → quarterly review on the agency base, **contracted MRR trend** (new K-MRR-TREND) and **entitlement trend**
    (new K-ENT-TREND). K-MRR-TREND reads only named v1 columns of `catalog.v_tenant_billing_v1` (contract 1.9 columns:
    subscription_status, trial_ends_at, bill_free, agreed_price_monthly, agreed_currency, agreed_until, price_usd_monthly,
    price_vnd_monthly, billing_currency, price_unit, seats, seats_min, seats_included, price_extra_seat_usd,
    price_extra_seat_vnd, billing_interval). It is before discount: "discount pending 1.10" (the contract minor that
    appends a discount column).
  - OPS-16 → adds the **tenant pipeline forecast** (new K-FC-TENANTS: paying now + trials x trailing trial-to-paid rate
    + the pre-trial pipeline from `shared.tenants` and `crm.ops.v1`).
  - MKT-02 → "Platform keyword research coverage": the tech lead's 2026-11-16 decision keeps keyword research
    platform-wide and rejects Search Console, rank tracking and per-agency SEO reports, so K-SEO-CTR v2 is retired in
    its definition (the R0 precedent of K-MKT-CUSTSRC) and the sections drop the tenant view.
  - CX-01 and BK-06 → planned with a trigger (first quarterly agency survey; first fixed departure offered to agencies).
- **Kept partial with a trigger for the CIS part:** BK-02, BK-04, BK-05 (Booking pages; CIS needs a Booking contract
  view of counts), CIS-02 (admin card + audit; next geocode chain batch), TP-02 (re-worded to the agencies' TripPlanner
  sites; first paying agency site served).
- **Triggers for the three reports already planned:** CIS-05 (writing-memory KPI work), CRM-01 (inside the CRM, never
  the CIS engine), DEV-04 (UAT round).
- **No R7 report is retired.** After the R0 re-scopes (BK-02, CX-01) no R7 report was B2C only; the B2C parts of
  MKT-01 (traveller sessions, inquiry funnel) were removed from its definition instead, which keeps the IDs stable.
  TP-03 stays the one retired report.
- No threshold is added: every new KPI threshold is a trend read by the business owner; the trial-to-paid window of
  K-FC-TENANTS is named as an admin setting the generator slice registers.

## Changed (vs the issue text)

- The S258 table planned tp-NNN visitor-source columns and a bk-NNN survey table for R7. Both are dropped or deferred:
  tenant site traffic belongs to the agency (ADR 0019 invariant 2), and the survey store is the CX-01 trigger's slice.

## Tradeoffs

- Re-pointing in place (same IDs) instead of retiring MKT-01 and adding a new report: no report_run rows exist for
  MKT-01, so nothing historical is mislabelled, and the catalogue keeps its 65 reports.
- K-MRR-TREND sits next to K-PART-MRR (EX-03, list prices from `shared.plan`). The trend needs the agreed price and
  currency, which only the 1.9 billing view carries; EX-03 is left unchanged in this docs slice.
