# AA-1136: agent change hooks, root repo part (lane l4-root-hooks, S285)

Source: the S284 hooks advisory `docs/audits/2026-11-18-S284-hooks-spec-advisory/README.md` (sections 4 and 6, slice 1).
This lane builds the root-repo pieces: the shared library `tools/sync/`, the Claude Code hooks that call it, their
settings entries and self-tests, and the measuring plan (thresholds below). The app-repo pieces (`--select-only` for the
pre-push test selector, CI jobs `notes-present` / `test-cochange`) are a separate lane.

## Measuring plan (S5): written before any log week starts

The hooks ship in `log` mode (`AA_SYNC_HOOKS` unset = `log`): they compute everything, append one JSON line per event
to `.tmp-session/hooklog.jsonl` and never say anything to the agent. The log week starts with the first session after
this PR merges and runs 7 calendar days (or 3 working sessions, whichever is longer). `python3 tools/sync/change_guard.py
report --since <start>` prints every number below from the log; `change_guard.py commits --repo-dir <repo> --since
<start>` prints the uncovered-commit rate from git.

| # | Measure | How it is counted | Pass | Fail |
|---|---|---|---|---|
| M1 | Hooks run where they should | events in the log by `event` and `agent` | at least one `PostToolUse` and one `SubagentStop` event from 3 or more distinct lane agents (`agent` != `main`) whose `repo_kind` is `worktree` | no `SubagentStop` event from any lane agent: SubagentStop does not reach workflow lanes, redesign before `warn` |
| M2 | Latency, PostToolUse | `latency_ms` (measured inside the script, interpreter start excluded) | p50 <= 120 ms and p95 <= 300 ms | p95 > 300 ms |
| M3 | Latency, Stop / SubagentStop | same | p50 <= 150 ms and p95 <= 300 ms | p95 > 300 ms |
| M4 | Hook health | events with an `error` field | <= 1 % of events, and 0 tool calls or stops refused because of a hook error | > 1 %, or any refusal caused by an error |
| M5 | False-reminder rate | every `would: remind` finding of the week (all of them if <= 50, else a random 50), each labelled true or false by reading the final PR diff: false when the change truly needed no test (pure refactor, config, style, generated file, kit sync, migration copy) or no note | <= 20 % false | > 20 % false: tune the file classes in `change_guard.py` and log one more week |
| M6 | Uncovered-commit rate (baseline) | `commits`: code commits on the default branch in the week with no `docs/implementation-notes/` change and no waiver, per repo | recorded per repo (today 25-75 %) | none: the log week only sets the baseline, the hooks are silent |
| M7 | Uncovered-commit rate (after one `warn` week) | same, for the week after `AA_SYNC_HOOKS=warn` | <= 15 % in every app repo, and at least halved against M6 in each repo | above 15 % in any app repo: reminders do not change behaviour, keep `log` and look at the reminder text |
| M8 | Waiver use | `report` counts `No test needed:` / `No note needed:` waivers per repo | recorded; any repo with > 30 % of its code changes waived gets a spec-lens look at the reasons | none |

Decision rule: `warn` is switched on only when M1-M5 pass. `notes-present` in CI moves from WARN to blocking only when
M5 <= 10 % and M7 passes, and only after the tech lead says yes to that change (S284 decision: warn first, measure,
then decide). These numbers are pass/fail criteria for a developer tool on this machine, not product thresholds, so they
live here and not in an admin settings page.

## Decisions

- **Mode switch `AA_SYNC_HOOKS=off|log|warn|block`, default `log`.** An unknown value counts as `log`. `off` turns
  only the sync part off: the Stop dispatcher still runs `stop_open_work.py` first, unchanged, in every mode.
- **`block` acts as `warn` inside the session.** The advisory (4.1 rule 2) only blocks at push/PR. The value exists
  for the later pre-push/CI callers (`change_guard.py check` exits 1 on findings in `block` mode).
- **`warn` at Stop / SubagentStop = refuse the stop once.** Claude Code has no "add context" output for Stop events,
  so a reminder there means one exit 2 with the text on stderr. `stop_hook_active` lets the next stop through, and each
  finding is said once per session + agent (state file), so it never loops.
- **One Stop dispatcher** (`stop-dispatch.sh` -> `stop_dispatch.py`) registered for both `Stop` and `SubagentStop`.
  For `Stop` it calls `stop_open_work.check()` first and returns its block exactly as before; only when that lets the
  stop through does the change guard run. For `SubagentStop` only the change guard runs (`stop_open_work` is about
  the main session checklist).
- **Repo from the file path, not from `cwd`.** `hookio.find_repo()` walks up from `tool_input.file_path` to the nearest
  `.git` (a directory = main checkout, a file = worktree, its `gitdir:` names the main repo). No subprocess, so it
  costs microseconds. Files under `.tmp-session/` of a checkout (checklists, scratch) are ignored; a lane worktree
  under `.tmp-session/wt/` has its own `.git` file and is found first.
- **Stop checks only repos the agent itself wrote.** PostToolUse records each repo top level in
  `.tmp-session/hookstate/<session>-<agent>.json`; Stop / SubagentStop read that list. An agent that wrote nothing
  is never checked (advisory: "chỉ với agent đã tự ghi file").
- **What counts as code.** `change_guard.classify()`: tests (`tests/`, `__tests__/`, `test_*.py`, `*_test.py`,
  `*.test.ts(x)`, `*.spec.ts(x)`, `e2e/`) first; then implementation notes; then docs (`*.md`, `docs/`); then
  schema (`*.sql`, `*.tf`, `*.tfvars`, `*.hcl`: need a note, not a test); then code (`.py .ts .tsx .js .jsx .mjs
  .cjs .sh`: need a test and a note); everything else (json, yaml, css, lock files) needs nothing.
- **Which note.** Issue ids come from the branch name (`feat/aa-1136-...`) and the `Refs AA-...` lines of the
  commits since the merge base. A note counts when `docs/implementation-notes/AA-<n>.md` or `AA-<n>-<lane>.md` of one
  of those ids changed; with no id, any changed notes file counts. Waivers are read from those notes files on disk.
- **Lint in PostToolUse is ruff on one Python file only.** With the repo's own ruff config when one exists between
  the file and the repo top (Booking `backend/`, Partner `api/`), else only fatal rules (`E9,F63,F7,F82`) so CIS
  (flake8) gets no style noise. eslint takes 1-3 s per file (node start), over the 300 ms budget: TS/JS files get no
  lint here, CI and pre-push still lint them. No ruff found -> `lint: unavailable` in the log, no message.
- **Docs impact from the map, cached.** `doc_impact.load_map()` needs PyYAML and ~50 ms; the hook keeps a JSON copy
  of the parsed map (`hookstate/doc-map-cache.json`, keyed by the map's mtime and size) holding the compiled glob
  patterns, so a normal edit never imports yaml. A broken or missing map is a logged note, never an error.
- **Failure = pass.** Every hook catches its own errors, logs them with `error` and exits 0 (the Stop dispatcher
  still returns the `stop_open_work` decision when that part worked). Settings give each new hook a `timeout`.

## Changed

- New `tools/sync/hookio.py`, `tools/sync/change_guard.py` (CLI: `check`, `report`, `commits`).
- New hooks `.claude/hooks/sync-post-edit.sh` + `sync_post_edit.py` (PostToolUse `Edit|Write|MultiEdit`) and
  `.claude/hooks/stop-dispatch.sh` + `stop_dispatch.py` (Stop and SubagentStop).
- `.claude/settings.json`: `PostToolUse` and `SubagentStop` entries added; the `Stop` entry now runs
  `stop-dispatch.sh` instead of `stop-open-work.sh` (that script and `stop_open_work.py` stay, unchanged, and the
  dispatcher imports the latter). Every other entry is unchanged.
- Tests next to the existing hook tests: `test_sync_hookio.py`, `test_sync_change_guard.py`,
  `test_sync_post_edit.py`, `test_stop_dispatch.py`; `test_settings_hooks.py` extended (one Stop dispatcher, the new
  events registered, timeouts present).
- `docs-lint.yml`: `tools/sync/**` added to the path filter so the hook tests run when the library changes.

## Tradeoffs

- Latency is measured inside the script (from the first line to the log write). Interpreter start (~20-40 ms on this
  machine) is not in `latency_ms`; Claude Code's own timeout covers the whole process.
- The state file per session + agent is written with replace-on-write; two hooks of the same agent racing can lose one
  repo entry. Accepted: an agent edits one file at a time in practice, and a lost entry only skips one check.
- No test run at Stop (the advisory's `--select-only` call to the pre-push selector belongs to the app-repo lane).

## Should know

- The main checkout's `.claude/settings.json` had an unstaged local edit by the tech lead (permission allow rules)
  when this lane started; only the lane worktree copy was edited. Merging this PR does not touch that local edit, but
  the tech lead's checkout gets a merge conflict on `git pull` if the local edit is still there: the local part is the
  `permissions.allow` list, the PR part is the `hooks` block.
- Before switching to `warn`: a SubagentStop exit 2 makes a workflow lane agent take one more turn. Lanes must call
  `StructuredOutput` exactly once, so check on one throw-away lane that a reminder after the final answer does not
  break the workflow, or keep SubagentStop at `log` and remind only through PostToolUse.
- The hooks start logging in the next session after merge; nothing needs a restart (Claude Code reads
  `.claude/settings.json` at session start).
