# AA-1166 — ISMS-lite and AIMS-lite: first self-assessments (ASVS L1, AI red-team)

Lane l13-redteam-asvs, S294 (decision D7: ASVS at 0 USD, AI red-team capped at 0.50 USD). The ISMS document pack, the
detailed checklist, its evidence and the red-team report live in the private ISMS location only. This page keeps the
method and the counts, nothing that names a finding.

## Decisions

- **Standard and scope.** OWASP ASVS 5.0.0, Level 1 (70 requirements, the official release CSV), for AA-Partner (CRM API
  and web) and AA-TripPlanner-Web (frontend and Lambdas). Each app is assessed as one system with the edge and identity
  configuration it runs behind (AA-CIS-Infra).
- **Method at 0 USD.** Code and configuration read at one commit of each repo, local checks only (`git grep`,
  `npm audit --package-lock-only --omit=dev`). No request was sent to a live host in this pass.
- **Status per requirement**: pass, fail or n.a. A partly met requirement counts as a fail, with the reason in the
  private note. Controls provided by a managed service (Cognito managed login, the authorization server) count as pass
  and are marked "inherited" in the private checklist.
- **AI red-team.** A fixed set of 16 invented adversarial cases (injection in source facts, exfiltration asks,
  policy-breaking asks, tenant-crossing asks) on the S1, T2 and T9 writers, judged offline by rules; code and
  implementation notes in AA-CIS-App (`scripts/aa1166/`, `services/ai_safety/redteam_set.py`). The CRM draft reply and
  the TripPlanner chat run on their own gateways, not reachable from the CIS gateway: a script in each app is a
  follow-up.

## Tradeoffs

- Reading code instead of probing live hosts keeps the pass free and safe, but a header or cookie set by the edge
  rather than the code is not seen; the next pass adds a short live header check and the monthly ZAP baseline.
- A partly met requirement counted as a fail makes the score stricter than a weighted one; it keeps "readiness" from
  looking better than the evidence.
