# AA-1108 — Platform › Delivery: CI/CD and DORA per app (root repo part)

Lane l7-delivery, S282. Design approved by the tech lead (S282, "Ok hết các đề xuất": all four decisions as proposed).
The CIS part (API, settings CIS 433, page, DEV-01 / DEV-03) has its own notes in AA-CIS-App
`docs/implementation-notes/AA-1108.md`.

## Decisions

- **Data path = option A** of the design: a scheduled root workflow (`.github/workflows/delivery-metrics.yml`, hourly
  + `workflow_dispatch`) with the run's `GITHUB_TOKEN` only. The six repos are public, so their runs, jobs, pull
  requests and deployments are readable without an App token; no new secret, no webhook endpoint, no new table.
  The worker-job alternative (an App token in CIS) was not taken: it adds a secret to the CIS task and a write-capable
  key to a public-facing service for data that is public anyway.
- **Publishing reuses the Docs sync path**: the role behind `DOCS_SYNC_ROLE_ARN` (trusted only by this repo on
  `refs/heads/master`, Put / Delete on `docs-reader/*`) and the bucket in `DOCS_SYNC_BUCKET`. Objects:
  `docs-reader/delivery/summary.json` and `docs-reader/delivery/events/<yyyy>/<mm>/<dd>.ndjson`. The CIS task role
  already reads `docs-reader/*`. Nothing changes in Terraform.
- **Raw events first, OpenTelemetry names.** The collector normalises four event kinds — `cicd.pipeline.run`,
  `cicd.pipeline.task.run`, `vcs.change`, `deployment` — with the CI/CD and VCS semantic-convention attribute names
  (`cicd.pipeline.name`, `cicd.pipeline.result` with the OTel values `success / failure / cancellation / skip /
  timeout / error`, `vcs.change.id`, `vcs.change.time_to_merge`, `deployment.environment.name`, ...). Fields without
  a convention carry the prefix `aa.` (`aa.trigger`, `aa.run_attempt`, `aa.workflow.file`, `aa.docs_only`, ...).
  Every metric is computed from the stored events.
- **The event store between runs is one Actions cache entry on master** (`delivery-store-<run id>`, restored by the
  `delivery-store-` prefix). The Docs sync role has no `GetObject`, so the S3 copy is write-only from CI; the cache is
  the working set (98 days: the 12-week trend plus margin). After saving, the run deletes the previous entry
  (`actions: write`), so the repo holds one entry (root ADR 0021 decision 5 cache budget). If the entry is evicted,
  the next runs rebuild it from GitHub within the request budget.
- **Request budget.** `GITHUB_TOKEN` allows 1,000 requests an hour; a run spends at most 650 (`apps.json`) and stops
  when the rate limit falls to 60. Phases, newest first: run lists of the last 2-3 days, closed pull requests since the
  cursor, deployments since the newest known id, the jobs of deploy runs (any age), backfill of older run days (one day
  of each repo in turn, up to 60 % of the budget), pull request files for the docs-only test (up to 80 %), then the
  jobs of CI runs and of the rest (14 days). The soft shares keep a cold store from spending a whole run on one phase.
  Run lists are fetched one creation day at a time (`created=<day>`, under GitHub's 1,000-result cap per query).
- **Deploy detection uses the deploy workflows, with GitHub Deployments as corroboration.** TripPlanner's deploy
  workflows create no Deployment records and Infra / CIS record non-deploy jobs (probes, eval) under `dev`, so the
  Deployments list alone is not a reliable deploy signal. A deploy = a run of a deploy workflow listed per app in
  `tools/delivery/apps.json`, on the default branch, triggered by push / manual / workflow_run, whose deploy job
  (regex per app) ran. The Deployment records of the environment are matched by commit and time and shown as
  `deployment_records` per deploy. Root's "deploy" is Docs sync (it publishes the docs and catalogue to the admin);
  Infra's is Terraform Apply Dev.
- **Grouping.** Runs of one commit that overlap in time are one app deploy (CIS api + worker and admin, CRM api and
  web). A later run of the same commit is a separate deploy flagged `redeploy`: it is not counted in frequency, CFR or
  rework (it is not a change) but can be the recovery of a failed deploy (a retry after an ECS rollout failure).
- **Failed deploy and rework (decision 1).** Failed = verify red, deploy job failed, rolled back (a later deploy of an
  older commit), its pull request reverted within 48 h, or a `fix` pull request naming its pull request (`#n`) within
  48 h. CFR counts the failed deploys; rework rate counts the deploys that are a rollback or ship a revert / hotfix
  pull request — the two DORA instability keys stay separate.
- **Bots (decision 2).** Author kind from the GitHub user: `aa-agent[bot]` = agent (counted), any other bot = bot
  (left out of lead time, listed under "bot pull requests"), a user = person. A person's login is never stored.
- **Thresholds (decision 4)** are CIS settings (CIS 433, area `delivery`); the summary carries raw numbers with `n`
  and the CIS API colours them.
- **History completeness.** Each repo keeps `runs_complete_since`; windows and trend weeks are clipped to it and pull
  requests merged before it are not matched to a deploy (the first stored deploy would claim them). Weeks before it
  carry `complete: false`.

## Tradeoffs

- Hourly freshness and a cold start that takes a few runs, against $0 and no new attack surface (option B, a
  webhook, would be near real time but needs a secret and a public endpoint).
- Run duration = `updated_at - run_started_at` of the newest attempt (wall time incl. queueing between jobs); job
  minutes are summed per job, rounded up per job, every attempt. Minutes of runs whose jobs are not read yet fall back
  to wall time (`minutes.coverage` says how much is measured by job).
- Day files are partitioned by an event's last-update time; an event that changes later (a re-run) also lands in a
  newer day file. Consumers dedupe by `id`, keeping the newest `time`. Only day files touched by a run are rewritten,
  always from the full store of that day.
- Hotfix detection relies on the fix pull request naming its target (`#n`); agent PR bodies that mention other PRs as
  context can add a false positive, so the reasons are listed per failed deploy for a human check.

## Should know

- **Retention of raw events (400 days)**: enforced by the workflow itself (it lists `docs-reader/delivery/events/`
  and deletes day files older than `raw_retention_days`, Delete is granted); the bucket only expires noncurrent
  versions after 7 days. No lifecycle rule was added in Infra.
- **Follow-ups (no settings mechanism in the root repo):** `headline_days` (28), `trend_weeks` (12),
  `rework_hours` (48), `raw_retention_days` (400), `request_budget` (650) live in `tools/delivery/apps.json`, not in an
  admin-editable setting. The colour thresholds are CIS settings. Moving the rest needs a way for the root workflow to
  read CIS settings (or a CIS-side recompute from raw events).
- The CIS Refresh button re-reads the published file; it cannot start a collection (no GitHub token in CIS). A
  dispatch from the admin needs an App token with `actions: write` on the root repo: follow-up.
- P2 (design §7): alerts on Platform › Alerts, per-test flakiness from JUnit artifacts, the agent / person / bot
  lead-time split on the page, Migration Apply time. P3: the `prod` dimension and incidents in recovery.
- New scheduled workflow: lesson S274 — it must be seen running on schedule within 48 h of merge (live step).
- Tests: `tools/delivery/test_delivery_metrics.py` on `tools/delivery/fixtures/demo_github.json` (an invented repo,
  `example-org/demo-app`, covering every definition); the workflow's `test` job runs them on every pull request that
  touches `tools/delivery/**`.
