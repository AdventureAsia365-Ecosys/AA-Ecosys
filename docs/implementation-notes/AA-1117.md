# AA-1117 — One dated go-live gate (S294, lane l5-golive-gate)

## Decisions

- **Where the list lives:** `docs/ops/go-live/checklist.yaml` (source) and `docs/ops/go-live/README.md` (catalog page
  `PROD-01-go-live-gate`, the rendered table between `golive-gate:begin` / `golive-gate:end` markers). The markers are
  not `gen:` blocks: `tools/docs/gen_sections.py` renders only from its facts snapshot, and this table renders from
  the checklist, so it has its own tool and its own sync check.
- **The S260 OPS-17 report is a dated snapshot, so it is linked, not rewritten.** OPS-17's channel is a new
  `docs/audits/<date>-S<nnn>-go-live-readiness/` folder per run (`docs/reports/catalog.yaml`), and the docs tools treat
  `docs/audits/` as journals. The report (and its `.vi.md`) gets one dated note in section 3 pointing at the live gate.
- **proof vs refs:** `proof` is evidence that the line is met (non-empty = met); `refs` is evidence so far or the
  method to copy (a Dev drill for a prod item). Derived status, no separate `status` field to drift.
- **Owner roles:** tech lead, business owner, engineer on duty (the language convention's roles). A name fails.
- **Anchors are checked:** `#heading` against GitHub-style slugs of the Markdown headings (fenced code skipped,
  duplicates `-1`), `#L<n>` against the line count. A renamed heading turns the gate red, like a deleted file.
- **Go-live date line:** one `kind: date` line; `value` may stay null only with an owner. Once a date is set, an open
  line due after it fails, and reaching the date with open lines fails. If the date line gets a `due` and it passes
  while the value is still null, that fails too (left without a `due` today: no agent-made deadline on the business
  owner).
- **Due dates** are planning dates set on 2026-11-25: decisions and Dev proofs mid/late December, build items
  2027-01-15 with a `due_note` (build week N). The checklist header says to re-date every open line in the PR that
  sets the go-live date.
- **Stdlib only:** a small YAML-subset parser (block mappings and sequences, plain/quoted scalars, `[]` flow lists,
  comments); anything else is an error with a line number. A unit test compares it with PyYAML on the committed file
  when PyYAML is installed (docs-lint has it), so the subset never silently misreads.
- **Workflow:** PRs touching `docs/ops/go-live/**`, the tool, its test or the workflow, plus Monday 02:17 UTC and
  `workflow_dispatch`. No secrets, no AWS, `contents: read`, checkout pinned by SHA like the other root workflows.

## Changed

- Scope asked for "~16 lines": the file has 17 gate lines + 1 date line. Added GL-10 (the one-tenant restore drills
  that already passed on Dev: CIS, TripPlanner, the CRM pilot agency) as the one met line, so the three existing drill
  proofs are linked as proof; the Booking per-partner drill (GL-11) and the prod drill (GL-04) stay open and cite them
  as method.
- The edge rate-limit line (GL-13) records that the S286 D10 decision already exists (regional rate rule now, a
  CloudFront web ACL when prod starts); what is open is the prod ACL with its cost in the reconciled prod figure.
- `docs/ops/README.md` (Prod section) and the `docs/README.md` catalog row PROD-01 link the new page.

## Tradeoffs

- A fixed ISO due date on build items that really depend on an unset go-live date: the issue asks for owner + ISO
  date on every open line, and a red weekly run when the date passes is the point (it forces a re-date). Relative dates
  ("go-live minus 7 days") were rejected: they never go red while the date is unset.
- The PR trigger is path-filtered, so deleting a proof file elsewhere is caught by the weekly run, and also by the
  docs-lint unit-test step (`tools/ops` tests run there, and `test_committed_checklist_is_valid_as_of_its_update`
  checks every link). Past-due lines are deliberately not part of that unit test (evaluated on the `updated` date), so
  an overdue line never reddens unrelated docs PRs.

## Should know

- `check --today YYYY-MM-DD` shows what the weekly run will say on a given day.
- The new workflow is a risky path for change control (`.github/workflows/*`): an independent agent review before merge.

# S297 (lane l7-golive): two gate dates, pilot lines, re-dates

## Decisions

- **Second gate date = `pilot_data`.** One `kind: date` line per gate date (`gate_date: golive` GL-18, `gate_date:
  pilot_data` GL-19, both unset, owner business owner). Each gate line names the date it must be met before
  (`gate_date`, default `golive`, so the old lines need no edit). A `pilot_data` line is bounded by both dates (needed
  before real data, and real users bring real data), a `golive` line only by the go-live date.
- **"Due at either" keeps the ISO due date mandatory.** A line bound to an unset gate date still needs its own ISO due
  date, so it can go red before the date is set (the S294 tradeoff against relative dates stands). Once a gate date is
  set, an open line bound to it and due after it fails, and reaching the date with bound lines open fails.
- **The pilot data date may not fall after the go-live date** (error): go-live means real users, so real data never
  starts later.
- **What-if flags:** `check --golive D --pilot-data D` evaluates proposed dates without editing the file; the page
  comparison uses the file as committed, so a what-if never reports a stale page.
- **No date recorded.** Searched the root docs (ADRs, legal, ops, audits, sessions, tracker) for a go-live date or a
  pilot data date written by the tech lead or the business owner: none. Both stay null with an owner.
- **GL-09 / GL-11 / GL-12 / GL-15 had no proof in the repo**, so each is re-dated to 2026-12-31 with the tech lead as
  owner and a note saying why: GL-09 (2 of 844 tours priced on Dev, no pilot market named), GL-11 (Booking has no
  per-partner export/restore job), GL-12 (only the CRM load test of S269 exists), GL-15 (plan decided and built, switch
  still off). GL-09 and GL-15 move to `pilot_data`; GL-11 and GL-12 stay `golive`.
- **GL-15 re-worded.** The S294 title asked for branch rules on admins; in the S295 security review the tech lead
  declined a GitHub-side required review. The line now tracks the decided control (the human-approval switch of the
  merge gate on, with the tech lead as approver, from the first real data) and its note records the decline.
- **GL-06** moves to `pilot_data`, due 2026-12-31, and links the key ceremony runbook written by lane l1-keys of the
  same session (`docs/ops/runbooks/key-ceremony.md`). The guard checks the link, so this PR merges after that one.
- **GL-16** moves to `pilot_data` (it is the pilot-data rule itself) and cites the S295 decision "no money and no real
  data before counsel reviews the contracts".
- **S295 security review items as pilot lines (GL-20 to GL-22)**, generic wording for the public repo (no resource
  names, IDs or task revisions): deletion and retention paths live or accepted in writing (data protection finding),
  on-demand base for the agency-facing CRM web service from the pilot day (the S295 decision; TripPlanner web when real
  travellers arrive; staff admins stay on Spot), pilot recovery targets in the pilot letter and DPA annex plus the
  "no batch runs in agency hours" rule. Refs point at repo pages and the public summary, never the private report.

## Changed

- `docs/guides/cio.md`: the Dev backup window was 7 days in two rows; it has been 14 days since root ADR 0019 d16 (the
  security baseline says so too). Part of the GL-22 finding; the rest of GL-22 stays open.
- Header line of the rendered table counts the open lines due before the pilot data date; the table has a "Before"
  column.

## Tradeoffs

- Bounding `pilot_data` lines by the go-live date too means one line can fail on either date; the alternative (only
  the pilot date) would let a pilot line stay open past go-live if the pilot never happens.
- 2026-12-31 for every re-dated line is a planning date, not a forecast: it moves the red run from 15/12 to 31/12 and
  forces the next look before the prod build, as the S294 design intended.
