# ADR 0004 — Amendment A1: supply data in Booking, customer-facing supply content in CIS (O7)

- **Status:** Accepted (14/10/2026, S236 — Nghiệp chose the hybrid option C). Separate file referenced from
  `docs/adr/0004-aa-booking-stack-and-bootstrap.md` (O7 row points here).
- **Amends:** ADR 0004 O7 ("All customer-facing content (activities, country text) is authored in CIS.
  Booking keeps commercial fields only"). O7 left open who owns the **facts** about hotels and
  activities, and how CIS gets them.
- **Consistent with:** ADR 0002 (only CIS writes customer-facing content), ADR 0005 decision 1 (all
  price and supplier data in schema `booking`), ADR 0001 decision 6 (contracts, outbox transport,
  read-only published views, no cross-schema writes).
- **Related Linear:** AA-679 (catalog sync), AA-681/682 (trip case, operations — proposals read the
  content), the `bk-002` slice (`suppliers`, `hotels`, `activities`, `entity_media`).

## Context

Hotels, activities and other services have two kinds of data with different owners and editors:

- **Supply and commercial data**: what the contracting team negotiates and maintains with suppliers.
  It changes with contracts and must never leak to customers in raw form (net rates, internal notes).
- **Customer-facing content**: descriptions, highlights and photos that appear in TripPlanner,
  proposals and tenant sites. It must follow CIS's writing rules (brand voice, source fidelity, review)
  and is produced by the CIS pipeline.

Nghiệp's decision (S236): **hybrid** — Booking owns supply + commercial data; CIS writes the
customer-facing description and photos **from** that data.

## Decision

1. **Booking owns supply and commercial data** for hotels, activities and other services (guide,
   transport, entrance, meal), in schema `booking`:
   - identity and facts: name, address, destination (`shared.destinations` id), geo point, star rating,
     room types (name, occupancy, bed types), amenities, check-in/out times, service duration,
     inclusions, pax limits, status (active / inactive);
   - commercial: supplier, contracts, net rates, seasons, cancellation terms, internal notes
     (ADR 0005);
   - edited only in the Booking staff UI, by the `booking-contracting` / `booking-admin` roles
     (ADR 0006 decision 3).
2. **CIS owns customer-facing content** for those entities: description, highlights, "good to know",
   photo set (selection, order, captions, alt text), SEO fields, translations.
   - Generated by a CIS job (`shared.job` kind, LLM through the Model Gateway with cost logging) from
     the Booking supply facts. The writer may only state what the supply data or approved sources say
     (writer source-fidelity policy).
   - Reviewed and **edited only in CIS** (`cis-content` / `cis-admin`), versioned like other CIS
     content.
   - Supplier-provided raw images may be attached in Booking as source material and are passed by
     reference in the contract; the **published photo set is CIS-owned**. A reference is a Booking
     `entity_media` id resolving to an object in a Booking-owned S3 prefix that CIS's task role may read;
     **never a free URL** (CIS would otherwise fetch arbitrary, supplier-typed URLs — SSRF and unlicensed
     images). Each media item carries a usage-rights flag set by contracting; CIS publishes only items
     marked publishable.
   - Supply facts are **untrusted input** to the LLM writer (names, amenity strings and inclusions are
     typed by staff or copied from suppliers): the writer prompt treats them as data, and the review step
     is mandatory before publish, as for tours.
3. **Contracts Booking → CIS** (in `docs/contracts/`, versioned JSON schema):
   - `supply.hotel.v1` and `supply.service.v1` (one schema for activity, guide, transport, entrance,
     meal, discriminated by `service_type`).
   - Envelope as `inquiry.submitted`: `contract`, `version`, `idempotency_key`, `emitted_at`, plus
     `entity_id` (Booking uuid), `supply_version` (monotonic per entity), `change` (`upsert` /
     `deactivate`).
   - Payload = the **facts only** from decision 1. **Never** in the payload: supplier identity,
     contracts, rates, margins, internal notes. The contract schema enforces this with
     `additionalProperties: false`.
4. **Transport:**
   - **Outbox** for changes: Booking writes `booking.outbox` in the same transaction as the supply
     change and exposes it through a read-only view (`booking.v_supply_outbox`). The view selects
     **only** rows whose `contract` is `supply.hotel.v1` / `supply.service.v1`, so other Booking events
     (customers, payments) are never readable through it. CIS's job runner consumes it, idempotent on
     `(contract, idempotency_key)`.
   - **Ordering:** idempotency does not prevent an older event from overwriting a newer one. CIS applies
     an event only if its `supply_version` is greater than the version it has stored for that
     `entity_id`; older or equal versions are recorded as skipped.
   - **Current-state views** for backfill and reconcile: `booking.v_supply_hotels`,
     `booking.v_supply_services` (same field set as the contract).
   - Grants: a Booking migration (`bk-NNN`) grants `SELECT` on these views to the CIS reading role —
     owner repo grants, unguarded (ADR 0004 decision 6).
   - **Known gap:** today the CIS API connects as the RDS master user `aa_cis_admin`, which owns every
     `booking.*` object (DB Migrate runs as it, ADR 0004). The grant above is therefore not what stops CIS
     from reading net rates — CIS can read all of schema `booking` now. Until CIS runs as a non-owner
     application role, "CIS never sees commercial data" is enforced by the contract, the views and code
     review only, not by the database. Tracked as a follow-up below.
5. **CIS → Booking read-back (read-only):**
   - CIS publishes a view keyed by the Booking entity id (`source_system = 'booking'`, `source_id`):
     description, highlights, photo URLs, `content_status` (`draft` / `in_review` / `published` / `stale`),
     `content_version`, and the CIS admin edit URL. AA-835 places it at `catalog.v_supply_content`, not
     `shared.*`, so it reuses the `catalog_owner` recipe and the existing `catalog.*` contract grant to `booking`.
   - A CIS migration grants `SELECT` on it to role `booking` (unguarded, after the role exists).
   - **Booking UI shows these fields read-only** with an **"Edit in CIS"** button linking to the CIS
     admin page. Both admin UIs use the WORKFORCE pool (ADR 0006), so the link usually needs no second
     sign-in (shared managed-login session; after it lapses, a Google redirect with no prompt). The CIS
     page still authorises the **CIS** group (`cis-content` / `cis-admin`): a `booking-contracting`-only
     user who follows the link sees a read-only or 403 page, not an editor. The edit URL in the view is a
     relative CIS admin path built by CIS, never taken from Booking data.
   - Proposals and customer documents built by Booking read **only** rows with
     `content_status = 'published'` from this view; draft, in-review and stale text never reaches a customer.
6. **Change rules:**
   - A material supply change (name, star rating, room types, amenities, inclusions, status) bumps
     `supply_version`. CIS marks the content `stale` and queues a regeneration **as a draft**; human
     edits are never overwritten silently — the reviewer sees the diff.
   - `deactivate` → CIS unpublishes the content (kept, not deleted).
   - A fact that CIS reviewers find wrong is fixed **in Booking** (the CIS UI shows the supply facts
     read-only with an "Edit in Booking" link). CIS never overrides a supply fact in its content.
   - Paid generation runs follow the paid-run rule (trial ~3, then batches ≤ ~50 entities, never the
     whole catalogue unasked).

## Consequences

- **Positive:**
  - one editor per field: contracting edits facts in Booking, content edits text and photos in CIS;
  - net rates and internal notes cannot reach customer content (they are not in the contract);
  - CIS's review, brand and fidelity rules apply to hotels and activities like tours;
  - Booking proposals show the same published text as TripPlanner and tenant sites.
- **Negative / cost:**
  - two more contracts, an outbox consumer and a reconcile path to maintain;
  - content lags supply until the CIS job runs and a reviewer approves;
  - cross-repo ordering: Booking `bk-NNN` (tables, outbox, views, grants) → CIS migration (content
    tables, read-back view, grant to `booking`) → CIS consumer → Booking UI read-back.

## Alternatives considered

- **Booking authors hotel/activity descriptions.** Rejected: violates ADR 0002 and duplicates the CIS
  writing pipeline and review.
- **CIS owns the hotel/activity master (facts and content).** Rejected: facts change with supplier
  contracts and are maintained by contracting staff in Booking next to the rates (ADR 0005).
- **CIS reads Booking tables directly.** Rejected by ADR 0001 decision 6 (published views and outbox only).

## Review notes (S236)

Adversarial review, 14/10/2026, done alongside ADR 0006. Changes:

1. **Photo references are scoped (decision 2).** Supplier images are passed as `entity_media` ids in a
   Booking-owned S3 prefix, never as free URLs, which closes an SSRF and fetch-anything path. A
   usage-rights flag gates publishing.
2. **Supply facts are untrusted LLM input (decision 2).** The prompt treats them as data, and human
   review stays mandatory.
3. **The outbox view is restricted to supply contracts (decision 4).** Without this, a shared outbox view
   would expose customer and payment events to CIS.
4. **Ordering rule (decision 4).** A `supply_version` monotonic check stops a late, older event from
   overwriting newer content. Idempotency alone does not.
5. **The grant gap is stated (decision 4).** CIS connects as the master user that owns `booking.*`, so
   the "facts only" boundary is enforced today by the contract and code review, not by the database.
   This is added as a follow-up.
6. **Cross-app link authorisation (decision 5).** The same pool does not mean the same rights. The CIS
   page still checks CIS groups, and the edit URL is built by CIS.
7. **Published-only read-back (decision 5).** Booking customer documents read only
   `content_status = 'published'`.

Remaining open risks:

- Until CIS stops connecting as `aa_cis_admin`, a CIS bug or compromise can read every Booking
  commercial field (net rates, margins, internal notes) and customer PII.
- Content lags supply. A deactivated or renamed hotel can stay visible in TripPlanner and tenant sites
  until the CIS job runs, and longer for any downstream caches.
